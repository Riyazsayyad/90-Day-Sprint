16 Troubleshooting Scenarios

Cover answers before opening <details>. Option lengths matched.

  1. S01 — Pod OOM: OutOfMemoryError: Metaspace. First fix direction?

    1. Investigate classloader retention.
    2. Double -Xmx heap immediately.
    3. Switch to Serial GC only.
    4. Shrink Eden with -Xmn flag.
    Answer

    A — S06: Metaspace ≠ heap. Class metadata / loader leak.

  2. S05 — GC log: Pause Full (Allocation Failure) 950M->948M(1024M) 3800ms. Meaning?

    950M->948M(1024M) 3800ms

    First action before raising -Xmx?

    Answer

    Live set ~948 MB / 1 GB — Full GC reclaimed ~2 MB in 3.8 s. Retention leak or legit huge live set — heap dump + dominator tree (S08). Not collector tune first.

  3. S02/S03 — Short-lived DTOs survive accidental ref in singleton cache. Symptom?

    1. Premature promotion fills Old gen.
    2. StackOverflow on every request.
    3. Metaspace cleared each Young GC.
    4. TLAB disabled on all threads.
    Answer

    A — Objects should die young but stay reachable → promote → Old grows → longer Mixed/Full GC (S03).

  4. S06 — Tomcat: 150 redeploys, heap flat, Metaspace stair-steps. Cause?

    Answer

    Classloader leak — old WebappClassLoader pinned (ThreadLocal, JDBC driver, shutdown hook). Fix retention; restart JVM. -Xmx irrelevant.

  5. S08 — Thread dump: 48/50 pool threads BLOCKED on same monitor. Queue 8k tasks. First tool already used. Next?

    1. Find lock holder stack in same dump.
    2. Full heap dump before reading dump.
    3. Raise -Xmx to clear queue faster.
    4. Enable -XX:+UseZGC immediately.
    Answer

    A — Thread dump already taken. Find waiting to lock and who holds monitor (M03 S02). Not heap.

  6. S01 — Netty service: Direct buffer memory OOM. Fix?

    1. Release buffers; tune direct pool.
    2. Double -Xmx heap to 16 GB.
    3. MaxMetaspaceSize to 512m only.
    4. -Xss 2m on all threads.
    Answer

    A — Off-heap direct pool (S08). MaxDirectMemorySize guardrail; fix missing release().

  7. S05 — 2 GiB K8s limit. Dev sets -Xmx2048m. OOMKilled, no Java heap OOM. Why?

    Answer

    Heap = entire cgroup — no room for Metaspace, stacks, direct, Code Cache, native GC (S01). Use ~50% MaxRAMPercentage or -Xmx1024m max.

  8. S04 — Nightly ETL, 8 GB heap, 4 s pause OK at 2 AM. Collector?

    1. Parallel GC for throughput.
    2. ZGC for sub-ms pauses.
    3. Serial GC for all cores.
    4. G1 with MaxGCPauseMillis=10.
    Answer

    A — Batch throughput; pauses off-peak acceptable. ZGC/G1 tight pause goals waste CPU.

  9. S02 — TLAB primary benefit in multi-threaded service?

    1. Avoid global Eden lock on most news.
    2. Store static fields per thread.
    3. Replace garbage collection fully.
    4. Compress all objects at alloc time.
    Answer

    A — Per-thread bump allocation in Eden slice.

  10. S02 — Empty object bytes (64-bit, compressed oops typical)?

    1. Sixteen bytes including header.
    2. Zero bytes until first field set.
    3. Four bytes reference only.
    4. Thirty-two bytes always exact.
    Answer

    A — Mark 8 + Klass 4 + padding 4 ≈ 16 bytes typical.

  11. S07 — p99 180 ms first 8 min post-deploy; 35 ms steady. GC logs clean. Cause?

    Answer

    JIT warmup — interpreter → C1 → C2 tiered compile. Also class/cache warming. Not leak if plateau healthy. Confirm with -Xlog:jit+compilation if needed.

  12. S08 — Old gen 92% after Full GC. Histogram: 3M OrderDto. First tool sequence?

    1. Heap dump → dominator tree.
    2. Thread dump only, skip heap.
    3. Restart pod, skip capture.
    4. Lower MaxGCPauseMillis to 50.
    Answer

    A — Retention proof: dump + MAT dominator — find static Map or cache holder (S03).

  13. S06/S08 — Filter sets ThreadLocal per request, never remove(). Pool threads. Slow Metaspace/heap creep. Fix?

    Answer

    try { ... } finally { threadLocal.remove(); } — pool thread retains prior request graph. Classic loader/heap leak pattern.

  14. S06 — Which triggers <clinit> by default?

    1. Class.forName with default args.
    2. ClassLoader.loadClass only.
    3. new Foo[100] array creation.
    4. jmap -histo live snapshot.
    Answer

    A — forName initializes; loadClass does not; arrays skip clinit.

  15. S08 — p99 spike. GC pauses normal. 190/200 threads RUNNABLE at socketRead0. Category?

    1. Downstream I/O latency.
    2. Heap leak — raise Xmx.
    3. Metaspace class leak only.
    4. JIT deoptimization storm.
    Answer

    A — Threads waiting on DB/socket — fix dependency/timeouts, not GC. Incident arc from S08.

  16. S04/S05 — API 24 GB heap, G1 Mixed GC pauses 350 ms, p99 SLO 150 ms. Code clean. Next eval?

    Answer

    Trial ZGC on JDK 21 with baseline metrics — after GC logs prove Mixed GC is culprit. Don't only tighten MaxGCPauseMillis (soft goal). Measure one change (S04).
