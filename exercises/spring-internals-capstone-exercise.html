Scenario 1 — NoSuchBeanDefinitionException

com.shop.ShopApplication lives in com.shop. A @Service BillingService lives in com.payments.BillingService. Also:

shop.billing.enabled=false   # application.yml
@ConditionalOnProperty(name = "shop.billing.enabled", havingValue = "true")
@Component
class BillingClient { }

Checkout constructor needs BillingClient. Startup: NoSuchBeanDefinitionException: BillingClient.

Tasks: root cause (there may be two), discovery path, debug steps, minimal fix.

Reveal answer

Root cause: (1) com.payments is outside default scan (package of ShopApplication + children). (2) Even if scanned, shop.billing.enabled=false makes @ConditionalOnProperty skip registration.

Discovery: Is there a BeanDefinition? /actuator/beans or definition names. Conditions: --debug / /actuator/conditions.

Minimal fix: Move billing under com.shop or scanBasePackages = "com.shop", "com.payments", and set shop.billing.enabled=true in the profile that needs it (or drop the condition). Don’t “fix” with new BillingClient() — you skip the container (S01/S06).

Scenario 2 — NoUniqueBeanDefinitionException

public interface PaymentGateway { Receipt charge(Money m); }

@Service class StripePaymentService implements PaymentGateway {}
@Service class RazorpayPaymentService implements PaymentGateway {}

@Service
class CheckoutService {
  CheckoutService(PaymentGateway gateway) { }
}

Tasks: Why it fails. @Primary vs @Qualifier articulation. When List<PaymentGateway> is better.

Reveal answer

Two beans of type PaymentGateway, injection point unqualified → NoUniqueBeanDefinitionException.

@Primary on Stripe = default when a single gateway is requested. @Qualifier("razorpayPaymentService") (default name) on a parameter when that site must be Razorpay. Use both: Primary for most call sites, Qualifier for the exception.

List<PaymentGateway> when the use-case is “try all / route by currency” — not a silent pick.

Scenario 3 — @Transactional Ignored

@Service
public class OrderService {
  @Transactional
  public void place(PlaceOrder cmd) {
    repo.save(cmd.toOrder());
    this.updateInventory(cmd); // also @Transactional
  }

  @Transactional(propagation = REQUIRES_NEW)
  public void updateInventory(PlaceOrder cmd) { ... }
}

Inventory update rolls back with the outer method; REQUIRES_NEW never starts. Tasks: proxy flow, JDK vs CGLIB, exception rollback, REQUIRES_NEW contrast.

Reveal answer

this.updateInventory is self-invocation: call stays on the target, never re-enters the Spring proxy, so no new tx, no independent commit. Outer REQUIRED (if place was called via proxy) still wraps save+inventory as one tx.

Boot CGLIB class proxy does not rewrite this. Fix: extract InventoryService bean and inject it; or inject self proxy.

If updateInventory threw a checked exception without rollbackFor, even a proxied call might commit — separate bug.

Scenario 4 — Auto-config DataSource

Service A: no user DataSource, starter-jdbc + spring.datasource.url → Hikari appears. Service B: same starter but a @Bean DataSource routingDs() → no second Hikari. Service C: forgot starter → no DataSource, JPA fails.

Tasks: dependency → auto-config → conditions → bean. Tools.

Reveal answer

A: DataSourceAutoConfiguration listed in AutoConfiguration.imports; OnClass true; OnMissingBean true; properties present → Hikari bean.

B: user bean → @ConditionalOnMissingBean(DataSource.class) false → Boot backs off. One pool (yours).

C: no JDBC auto-config match (or class missing) → NoSuchBean later. Debug: --debug Condition Evaluation Report, /actuator/conditions. Exclude only if you must disable despite classpath.

Scenario 5 — Production Latency

Tomcat max=200, Hikari maximum-pool-size=20, p99 8s, CPU 15%. Load spike.

Tasks: chain; Actuator; metrics; thread dump; JVM tie-in.

Reveal answer

Most Tomcat workers blocked acquiring a connection or in socketRead on the 20 connections. Raising Tomcat to 800 worsens queues. Measure: Hikari pending, Tomcat busy, HTTP timers (S08). Dump: /threaddump or jcmd Thread.print (JVM S08). Fix: queries, pool vs DB max_connections, timeouts, maybe VT for waiters — not extra workers without extra DB. Virtual threads do not add connections.

Senior Interview Round — 15 questions

Speak answers first. Then reveal.

  1. IoC vs DI in two sentences.
    Reveal

    IoC: the container owns create/call graph. DI: collaborators are passed in (usually constructors). DI is a technique inside IoC.

  2. What is a bean?
    Reveal

    A container-managed object with a BeanDefinition — not every new, not DTOs/entities.

  3. ApplicationContext vs BeanFactory.
    Reveal

    Context is a BeanFactory plus events, i18n, AOP integration, eager singleton refresh.

  4. Lifecycle order: ctor, inject, @PostConstruct, destroy.
    Reveal

    Constructor → remaining DI → @PostConstruct / init → (proxy after BPP) → @PreDestroy on close (singletons).

  5. Prototype into singleton — 100 HTTP calls.
    Reveal

    One prototype unless ObjectProvider or scoped proxy.

  6. Default scan base.
    Reveal

    Package of @SpringBootApplication and subpackages.

  7. @Primary vs @Qualifier.
    Reveal

    Primary: default candidate of a type. Qualifier: this injection point’s identity. Qualifier wins locally.

  8. Boot 3 auto-config discovery file.
    Reveal

    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. spring.factories EnableAutoConfiguration key removed in 3.0.

  9. User @Bean DataSource — Hikari?
    Reveal

    @ConditionalOnMissingBean false → auto-config backs off.

  10. Why self-invocation skips @Transactional.
    Reveal

    Advice lives on the proxy. this is the target.

  11. Default rollback policy.
    Reveal

    RuntimeException/Error. Checked commits unless rollbackFor.

  12. Filter vs DispatcherServlet.
    Reveal

    Filter: servlet chain around the servlet. DispatcherServlet: Spring MVC front controller (mapping, adapters, converters).

  13. Liveness vs readiness.
    Reveal

    Liveness → restart. Readiness → take traffic. Don’t DB-check liveness.

  14. WebFlux + blocking JDBC.
    Reveal

    If on the event loop, the loop stalls. Don’t. Use MVC±VT or reactive drivers.

  15. Virtual threads vs WebFlux one-liner.
    Reveal

    VT scale blocking imperative code; WebFlux scales non-blocking pipelines.

Final challenge — 2 minutes

Outline aloud: Boot startup → ApplicationContext → BeanDefinitions (scan, @Bean, auto-config + conditions) → instances + lifecycle → AOP proxies / @Transactional → HTTP Tomcat → Filter → DispatcherServlet → Controller → Service → Repo → Actuator for health/metrics. If you skip conditions or proxies, restart the timer.
