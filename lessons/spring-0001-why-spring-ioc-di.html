Why Spring: IoC, DI, Layers & Manual Wiring

~30 minutes · Module 05 Lesson 1 of 9 · builds on Polymorphism, Abstraction, final, JVM process model

Senior Interview Focus: Can you explain Spring without listing annotations? Interviewers want: why object graphs explode, what inversion of control actually inverts, why constructor injection beats field injection, what a bean is (and is not), and how layers + DIP keep a payment service testable. This lesson is the “why.” Lifecycle, scan, auto-config, and proxies come later — do not hide behind them yet.

Primary sources: Spring Framework — IoC Container · Spring Framework — Dependency Injection · Spring Boot — Structuring Your Code

1. Why new Graphs Rot

Must know (interview): Hard-coded construction couples who uses a type to how it is built. Tests, environments, and feature flags all fight that coupling.

CheckoutService
  └─ new StripeClient(apiKey)
       └─ new HttpClient()
            └─ new RetryPolicy()
                 └─ new MetricsSink()   // now every test needs Stripe + HTTP

Pain that shows up in production codebases:

  • Change blast radius — swap Stripe for Razorpay and every new CheckoutService() site changes.
  • Hidden graph — constructors grow; nobody sees the full tree until a NPE in prod.
  • Untestable — cannot inject a fake gateway without bytecode tricks or static mocks.
  • Env chaos — local vs K8s URLs, secrets, pool sizes baked into constructors.
Common misconception: “Spring exists so we type less.” No. Spring exists so composition of the object graph is a first-class, inspectable concern — not scattered new.

2. Manual Wiring First (No Spring)

Write the composition root by hand. This is still valid Java. Spring later automates this same graph.

public final class App {
  public static void main(String[] args) {
    UserRepository repo = new JdbcUserRepository(dataSource);
    UserService service = new UserService(repo);
    UserController controller = new UserController(service);
    // start HTTP server, pass controller
  }
}

Mental model: One place owns construction. Dependencies flow inward through constructors. The rest of the app never calls new on collaborators.

Manual wiring scales until: 80 beans, 3 profiles, 12 optional features. Then you reinvent a container (poorly). That is Spring’s job.

3. IoC — Simple Mental Model

Inversion of Control = you stop being the one who decides when and how objects are created. The framework calls you.

Without IoC (you drive):
  main() → new A() → new B() → new C() → a.run()

With IoC (framework drives):
  framework starts → creates C, B, A → injects → calls your methods
                     (HTTP handler, @Scheduled, CommandLineRunner)

The “control” that inverted is object lifetime + call graph assembly, not business logic. Your charge() method still belongs to you.

Hollywood principle: “Don’t call us — we’ll call you.” Servlet container did this decades before Spring. Spring applied it to plain Java objects.

4. Dependency Injection — How Collaborators Arrive

DI is one technique of IoC: the object does not look up collaborators; they are passed in.

Style Shape Senior judgment
Constructor Foo(Bar bar) + private final Bar bar Default. Required deps, immutable, fully initialized, unit-test with new Foo(mock).
Setter setBar(Bar bar) Optional / reconfigurable. Object can exist half-wired. Use sparingly.
Field @Autowired Bar bar; Works. Hides deps. Hard to test without Spring Test. Reflection. Avoid in application code.

Spring team guidance (Framework reference): constructors for mandatory deps; setters for optional. Constructor-injected beans are returned only after all required collaborators exist — no “use before init.”

You already met this in final: constructor injection + final fields is the Boot 3 house style. Single constructor: @Autowired is optional (Spring 4.3+).

Interview trap: “Field injection is fine because Boot uses it in samples.” Samples optimize for brevity. Production services optimize for testability and required-deps-at-compile-time.

Nice to know: Boot 3.2 / Framework 6.1 stopped guessing parameter names from bytecode. Compile with -parameters (Maven/Gradle plugins do this) or constructor binding / @Qualifier names break in surprising ways.

5. Who Creates What

WITHOUT Spring
  Application code
       │  new + wire
       ▼
  Object graph

WITH Spring
  Application code  ──asks──►  IoC container (ApplicationContext)
                                    │  creates + wires beans
                                    ▼
                               Object graph

Your main still exists — it starts the container (SpringApplication.run). After that, you ask or you get called. You do not assemble 80 constructors yourself.

6. What a Bean Is

A bean is an object whose lifecycle and wiring the Spring container manages. It has a name, a type, a scope, and (usually) dependencies recorded in a BeanDefinition.

  • Is a bean: UserService, DataSource, ObjectMapper if registered.
  • Usually not a bean: JPA entities, request DTOs, Money value objects, loop-local ArrayList.
Must know: Spring does not intercept every new. A DTO you construct in a controller is a plain heap object — see Stack vs Heap. Only registered types enter the container.

7. Layers & Dependency Direction

  HTTP
    │
    ▼
┌─────────────┐
│ Controller  │  translation: HTTP ↔ application commands
└──────┬──────┘
       │ depends on
       ▼
┌─────────────┐
│  Service    │  use-cases, transactions (S06), orchestration
└──────┬──────┘
       │ depends on
       ▼
┌─────────────┐
│ Repository  │  persistence port (interface)
└──────┬──────┘
       │ implemented by
       ▼
┌─────────────┐
│  Database   │  JDBC / JPA (Module 06)
└─────────────┘

Arrows mean compile-time dependency. Upper layers depend on abstractions (interfaces), not on JDBC driver classes. That is DIP in one diagram — you met the idea in Abstraction.

Production relevance: A controller that talks JDBC skips the service layer → no single transaction boundary, no place for authz, untestable HTTP+SQL mash. Seniors defend the layer, not the annotation.

8. DIP — Tiny Payment Gateway

public interface PaymentGateway {
  Receipt charge(Money amount, String customerId);
}

public final class CheckoutService {
  private final PaymentGateway gateway;

  public CheckoutService(PaymentGateway gateway) {
    this.gateway = gateway;
  }

  public OrderId checkout(Cart cart) {
    gateway.charge(cart.total(), cart.customerId());
    return OrderId.newId();
  }
}

public final class StripeGateway implements PaymentGateway { /* HTTP to Stripe */ }
public final class FakeGateway implements PaymentGateway { /* tests */ }

High-level CheckoutService does not import Stripe. Infra implements the interface. Swap in tests with new CheckoutService(new FakeGateway()) — zero Spring required for that unit test.

9. Before / After Spring (Same Graph)

After (stereotype sketch — scanning detail is S03):

@RestController
public class UserController {
  private final UserService service;
  public UserController(UserService service) { this.service = service; }
}

@Service
public class UserService {
  private final UserRepository repo;
  public UserService(UserRepository repo) { this.repo = repo; }
}

@Repository
public class JdbcUserRepository implements UserRepository {
  private final DataSource ds;
  public JdbcUserRepository(DataSource ds) { this.ds = ds; }
}

Container finds types, creates JdbcUserRepository, then UserService, then UserController — same order you wrote by hand. Annotations are metadata, not magic.

10. Why Spring Is More Than Boilerplate

If DI were the whole story, a 40-line composition root would suffice. Spring also provides:

Capability Mechanism (named) When you need it
Lifecycle Bean factory + init/destroy callbacks Warm caches, close pools — S02
Configuration Environment, profiles, properties dev vs prod without recompile — S03–S04
AOP JDK / CGLIB proxies wrapping beans tx, security, metrics without polluting domain — S06
Transactions PlatformTransactionManager + proxy advice commit/rollback around a service method — S06
Testing Test slices, mock beans, Testcontainers later Slice tests without full server
Extensibility Auto-config + conditions + starters Add JDBC → get DataSource unless you defined one — S05

Boot specifically: embedded Tomcat (S07), actuator (S08), opinionated classpath. Framework IoC still sits underneath.

11. IoC Container vs DI — Precise Distinction

Term What it is What it is not
IoC Who controls creation, wiring, and when your code runs Not “using Spring annotations”
IoC container BeanFactory / ApplicationContext holding beans Not the HTTP server
DI Passing collaborators in (constructor/setter/field) Not a synonym for IoC

You can do DI with zero Spring (manual wiring). You can have IoC without constructor DI (Service Locator / getBean lookups — generally worse). Spring’s default story: container + constructor DI.

Common misconception: “DI = IoC.” DI is how dependencies arrive. IoC is who owns the call/create graph.

12. Misconceptions

  1. Spring creates every object. False. Only beans. new OrderRequest(json) is yours.
  2. new is forbidden. False. Forbidden: new of a collaborator that should be a bean inside another bean (you skip the proxy — S06). Allowed: value objects, builders, test fakes, JDK types.
  3. Stereotypes change DI. @Service vs @Component — same container registration for core DI. Specializations are documentation + exception translation later.
  4. Spring replaces OOP. False. Polymorphism and interfaces are the injection points.

13. What Happens When Spring Boot Starts? — Preview Only

java -jar app.jar
        │
        ▼
SpringApplication.run
        │
        ├─ 1. Environment  (properties, profiles, env vars)     → S04
        ├─ 2. ApplicationContext created                         → S02
        ├─ 3. Bean definitions (scan + @Bean + auto-config)      → S03, S05
        ├─ 4. Instantiate + inject + init callbacks              → S02
        ├─ 5. Embedded web server starts (Tomcat by default)     → S07
        └─ 6. Ready — Actuator, traffic                          → S08

Do not memorize this as a 40-step list yet. Remember: environment → definitions → instances → server. Detail in later sections.

Production Relevance

  • Incident: “works locally, missing bean in prod” — usually scan base package or profile/condition (S03–S05), not “Spring broken.”
  • Review smell: @Autowired on 12 fields, no constructor — untestable and circular-deps-prone (S02).
  • K8s: one JVM process (S01 JVM) hosting one ApplicationContext (typical). Beans live on the heap like any objects.

Interview Articulation

“Spring’s IoC container owns the object graph. We declare types and constructor dependencies; the context instantiates and injects them. DI is the passing-in of collaborators — we prefer constructors so deps are required, final, and mockable without starting Spring. A bean is a container-managed object, not every Java object. Layers keep HTTP, use-cases, and persistence from collapsing into one class.”

Interview Traps

  • Equating IoC with DI.
  • Saying field injection is “the Spring way.”
  • Claiming controllers must new services.
  • Promising auto-config details you have not learned (S05).

Senior Interview Questions (open)

  2. Walk a three-layer graph using only new. What did you just invent?
  3. Define IoC in one sentence without the word “annotation.”
  4. Constructor vs field injection — three concrete reasons for constructor.
  5. What is a Spring bean? Give two objects that should not be beans.
  6. Draw Controller → Service → Repository. Which way do source dependencies point?
  7. How does DIP show up in a payment integration?
  8. Is new ArrayList<>() inside a @Service a smell? Why or why not?

Revision Notes

  • Composition root: one owner of new for collaborators.
  • IoC = framework owns create/call graph. DI = pass deps in.
  • Constructor + final = required, testable, initialized.
  • Bean = container-managed. DTOs/entities usually not.
  • Depend on interfaces; infra implements.
  • Boot start preview: env → context → definitions → instances → Tomcat.

Interview One-Liners

  • “DI is a technique; the IoC container is the runtime that applies it.”
  • “If I can new it in a unit test with fakes, constructor injection paid off.”
  • “new of a collaborator inside a bean skips the container — and later the transaction proxy.”
  • “Layers are dependency direction, not folder names.”

Senior MCQs

Cover answers before opening. Option lengths matched.

  1. Q1: IoC primarily inverts which responsibility?

    1. Who creates and wires application objects.
    2. Who writes SQL inside repository classes.
    3. Who allocates heap vs stack for locals.
    4. Who compiles Java sources in Maven.
    View Answer & Explanation

    Answer: A (Who creates and wires application objects.)

    IoC is about object graph assembly and call timing, not SQL, JVM memory, or the compiler.

  2. Q2: Preferred injection style for a required UserRepository?

    1. Constructor plus a final field.
    2. Public setter called after traffic.
    3. Field autowire with no constructor.
    4. Static lookup from a global map.
    View Answer & Explanation

    Answer: A (Constructor plus a final field.)

    Spring team guidance: mandatory deps via constructor. Immutable, testable, fully initialized.

  3. Q3: Which object is typically a Spring bean?

    1. A singleton UserService in the context.
    2. A JSON request DTO per HTTP call.
    3. A JPA entity loaded from a row.
    4. A loop-local ArrayList of IDs.
    View Answer & Explanation

    Answer: A (A singleton UserService in the context.)

    DTOs, entities, and local collections are ordinary heap objects, not container-managed beans.

  4. Q4: DI versus IoC — accurate statement?

    1. DI is one way to implement IoC wiring.
    2. DI and IoC are identical terms always.
    3. IoC means field injection only in Boot.
    4. DI requires Tomcat to exist first.
    View Answer & Explanation

    Answer: A (DI is one way to implement IoC wiring.)

    You can DI by hand with no container. Tomcat is the servlet container (S07), not the definition of DI.

  5. Q5: Correct compile-time dependency direction?

    1. Service depends on PaymentGateway interface.
    2. Service imports Stripe SDK classes only.
    3. Repository depends on RestController types.
    4. Entity depends on DispatcherServlet class.
    View Answer & Explanation

    Answer: A (Service depends on PaymentGateway interface.)

    DIP: high-level policy depends on abstractions. Infra (Stripe) implements the port.

  6. Q6: new HashMap inside a @Service method?

    1. Fine — not a collaborator bean.
    2. Illegal — Spring forbids all new.
    3. Always a circular dependency bug.
    4. Requires @Bean on HashMap always.
    View Answer & Explanation

    Answer: A (Fine — not a collaborator bean.)

    Local JDK structures are not IoC concerns. Smell is new StripeClient() inside the service.
