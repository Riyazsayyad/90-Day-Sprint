Deep Dive: Explicit Locks

~35 minutes · ties to mission · builds on Lesson 2, Lesson 3

Senior Interview Focus: synchronized is the default. Interviewers ask when it is not enough: timed/interruptible acquire, fairness, multiple wait-sets, lock downgrade. They also hunt the trap synchronized never has — forgetting unlock(). This lesson is the java.util.concurrent.locks toolkit, not AQS internals.

Primary sources: Oracle — Lock Objects · Lock javadoc · ReentrantLock · Condition · ReadWriteLock · StampedLock · Oracle — Deadlock / Liveness

1. Why Explicit Locks Exist

Lesson 2: intrinsic locks are block-structured — acquire and release are tied to a synchronized scope. The JVM always unlocks on exit, even via exception. That safety has a cost: you cannot try-and-give-up, time out, interrupt a thread stuck in lock acquisition, choose FIFO fairness, or split waiters onto two condition queues.

java.util.concurrent.locks.Lock exists for those cases. Flexibility means you own unlock. Miss the finally and the lock is gone for the process lifetime of that object.

Auto unlock on exceptionYesOnly if you write finally
tryLock / timed waitNoYes

Multiple wait-setsOne wait set per objectMany Conditions per lock
Hand-over-hand / unlock in other methodAwkwardDesigned for it

Senior default: synchronized until one of those rows is a real requirement. Explicit locks are not "more thread-safe."

2. Lock Interface Contract

Core methods:

  • lock() — block until acquired. Reentrant implementations increment hold count if you already own it.
  • unlock() — release one hold. Wrong thread / not held → typically IllegalMonitorStateException.
  • lockInterruptibly() — like lock() but abort with InterruptedException if interrupted while waiting.
  • tryLock() — return immediately; true if acquired.
  • tryLock(timeout, unit) — wait up to a bound; interruptible.
  • newCondition() — bind a condition queue to this lock.

Always finally

lock.lock();
try {
  // critical section
} finally {
  lock.unlock();
}

For tryLock: unlock only if acquire succeeded.

if (lock.tryLock()) {
  try {
    // work
  } finally {
    lock.unlock();
  }
} else {
  // skip / degrade — never unlock
}

happens-before (same as monitor)

From the Lock javadoc: a successful lock has the same memory effects as a JLS Lock action; a successful unlock matches Unlock. So unlock happens-before the next successful lock on the same Lock — same visibility story as Lesson 2/3. Unsuccessful tryLock does not create that edge. Reentrant lock/unlock of an already-held lock also need not publish new memory effects.

Never synchronized (lockInstance) on a Lock object. That acquires the intrinsic monitor of the lock object — unrelated to lock.lock().

3. ReentrantLock

Same ownership model as synchronized: one owner thread, reentrant hold count, exclusive mutual exclusion. Extra knobs: fairness, interruptible/timed acquire, Conditions, instrumentation.

private final ReentrantLock lock = new ReentrantLock();      // non-fair (default)
private final ReentrantLock fair = new ReentrantLock(true);  // FIFO-ish under contention
  • Reentrancy: nested lock() from the owner increments getHoldCount(). Each unlock() decrements; lock frees at zero.
  • isHeldByCurrentThread(): analog of Thread.holdsLock(monitor) — asserts and tests, not a sync protocol.
  • Fair vs non-fair: fair prefers the longest-waiting thread under contention. Throughput is often much worse. Fairness of the lock is not fairness of the scheduler — a thread can still reacquire immediately if others are not yet queued.
  • Barging trap: untimed tryLock() does not honor fairness. If the lock is free, it takes it even when waiters exist. Timed tryLock(0, SECONDS) respects fairness (and is interruptible).

synchronized vs ReentrantLock — who wins

PickWhen
synchronizedSimple mutual exclusion, wait/notify on one object, you want the compiler/JVM to guarantee unlock. Default in Spring services for tiny critical sections.
ReentrantLockNeed try/timed/interruptible acquire, fairness, multiple Conditions, or lock held across non-nested scopes (rare — document it).

Do not rewrite every synchronized method as ReentrantLock for "performance." Measure. Intrinsic locks are heavily optimized (and Lesson 2's biased/thin/fat story still applies).

4. ReadWriteLock / ReentrantReadWriteLock

Pair of locks: shared read (many readers) or exclusive write (one writer, no readers). Write-unlock happens-before a later read-lock on the same RW lock — readers see the writer's updates.

private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

Object get() {
  rw.readLock().lock();
  try { return snapshot; }
  finally { rw.readLock().unlock(); }
}

void refresh(Object next) {
  rw.writeLock().lock();
  try { snapshot = next; }
  finally { rw.writeLock().unlock(); }
}

Wins when reads dominate and the protected data is non-trivial (cache, config snapshot, directory). Hurts when:

  • Write-heavy — exclusive write serializes everyone; extra RW machinery is waste.
  • Tiny reads — lock overhead dominates the work.
  • Frequent upgrades — see deadlock below.

Downgrade (write → read) is supported

Acquire write, mutate, acquire read while still holding write, then release write. You remain a reader; no other writer sneaks in between.

rw.writeLock().lock();
try {
  mutate();
  rw.readLock().lock(); // downgrade: still exclusive until write unlocks
} finally {
  rw.writeLock().unlock();
}
try {
  observe(); // other readers may join; writers still blocked
} finally {
  rw.readLock().unlock();
}

Upgrade (read → write) deadlocks

Write lock waits until all readers release — including you. Holding the read lock and then calling writeLock().lock() waits forever for yourself. Pattern: release read, acquire write, re-check the invariant (another writer may have run). Or use StampedLock.tryConvertToWriteLock (next section) with a retry loop — still not a free upgrade.

5. StampedLock (Interview Level)

Java 8 capability lock: write, read, and optimistic read. Acquisition returns a long stamp. Release/convert needs that stamp. Does not implement Lock / ReadWriteLock (views exist: asReadLock() etc.).

Optimistic read: tryOptimisticRead() returns a non-zero stamp if no writer currently holds the lock. You copy fields into locals, then validate(stamp). If validate is true, those reads are a consistent snapshot (happens-before from the last write-unlock). If false, a writer ran — retry or take a real read lock.

long stamp = sl.tryOptimisticRead();
double x = this.x;
double y = this.y;
if (!sl.validate(stamp)) {
  stamp = sl.readLock();
  try {
    x = this.x;
    y = this.y;
  } finally {
    sl.unlockRead(stamp);
  }
}
return Math.hypot(x, y);

Prefer over RW lock when reads are very short, writes rare, and you can tolerate retry — e.g. a hot coordinate / versioned snapshot. Do not use as a general Spring-service mutex.

Misuse traps (interview gold):

  • Not reentrant. Nested acquire from the same thread deadlocks or fails. Do not call unknown methods while holding a stamp.
  • No ownership. Another thread can unlock your stamp. Unlike ReentrantLock.
  • Skip validate — you may compute on torn / half-updated fields. That is the whole point of the API.
  • Optimistic mode is weak: writers can invalidate at any time. Side-effecting reads inside the optimistic window are forbidden.

Out of scope: stamp bit layout, formal proofs, AQS.

6. Condition

Lesson 2: one wait set per monitor; wait / notify / notifyAll. Condition splits that into named queues on one Lock.

MonitorCondition
wait()await()
notify()signal()
notifyAll()signalAll()

Same rules: must hold the lock; await atomically releases it and reacquires before return; always while (spurious wakeup + missed predicate). Signalling without holding the lock: ReentrantLock's conditions throw IllegalMonitorStateException.

Classic win: bounded buffer with notFull and notEmpty. A put that frees a slot signals only consumers; a take that frees space signals only producers. One monitor + notifyAll wakes the wrong waiters and burns CPU.

final Lock lock = new ReentrantLock();
final Condition notFull  = lock.newCondition();
final Condition notEmpty = lock.newCondition();

void put(E x) throws InterruptedException {
  lock.lock();
  try {
    while (count == items.length)
      notFull.await();
    items[putptr++] = x;
    if (putptr == items.length) putptr = 0;
    count++;
    notEmpty.signal();
  } finally {
    lock.unlock();
  }
}

E take() throws InterruptedException {
  lock.lock();
  try {
    while (count == 0)
      notEmpty.await();
    E x = items[takeptr++];
    if (takeptr == items.length) takeptr = 0;
    count--;
    notFull.signal();
    return x;
  } finally {
    lock.unlock();
  }
}

Production: use ArrayBlockingQueue — this pattern is for interviews and for when you own the invariant.

7. Deadlock & Liveness

Oracle liveness: deadlock, starvation, livelock. Explicit locks add tools — they do not delete the physics.

  • Lock ordering: always acquire A then B globally. Nested inversion (thread 1: A then B; thread 2: B then A) is the Alphonse/Gaston deadlock from the tutorial.
  • tryLock + backoff: acquire both or release what you hold and retry with a timeout — the tutorial's Safelock idiom. Use when lock order cannot be global (graph of peers).
  • Interruptible acquire: cancellation path when a lock wait is stuck — still need a policy for who retries.
  • Fair locks reduce lock starvation; they can increase latency. They do not fix livelock (threads keep yielding without progress).

8. Classic Bugs

  • Forgot unlock — exception path, early return, or tryLock success then return without finally. No auto-release.
  • Unlock without holding — IllegalMonitorStateException (including unlocking after failed tryLock).
  • Locking the wrong object — synchronized (this) while mutations use a ReentrantLock field (two locks, no exclusion).
  • signal without holding the lock — exception (typical) or lost wakeup (if a custom Condition allowed it).
  • RW upgrade deadlock — read held, write requested.
  • StampedLock optimistic read without validate — silent data corruption.
  • Reentrant call into StampedLock — self-deadlock.

10. Revision Notes

  • Unlock in finally. Always. tryLock unlocks only on success.
  • Unlock → next lock on same Lock is happens-before (successful ops).
  • Untimed tryLock() barges on a fair lock.
  • RW: many readers or one writer. Downgrade yes; upgrade no (deadlock).
  • StampedLock: validate optimistic reads; not reentrant.
  • Condition.await ≡ wait: hold lock, loop on predicate, two queues beat notifyAll for producer-consumer.

11. 5 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Exception in the critical section, unlock not in finally. Result?

    1. Lock stays held after exception.
    2. JVM auto-releases like sync do.
    3. Hold count resets itself to 0.
    4. Fairness flag flips itself on.
    View Answer & Explanation

    Answer: A (Lock stays held after exception.)

    Explicit locks have no block-structured auto-release. That is the price of tryLock and cross-method locking.

  2. Q2: Fair ReentrantLock; another thread is queued. Untimed tryLock() when free?

    1. Succeeds — barging is allowed.
    2. Fails — must honor the queue.
    3. Throws — fairness forbids try.
    4. Blocks — until the queue drains.
    View Answer & Explanation

    Answer: A (Succeeds — barging is allowed.)

    Javadoc: untimed tryLock() takes a free lock even if waiters exist. Timed tryLock(0, SECONDS) honors fairness.

  3. Q3: Thread holds RW read lock, then calls writeLock().lock(). Typical result?

    1. Self-deadlock waiting for itself.
    2. Silent upgrade to write mode.
    3. Read lock converts automatically.
    4. Write lock is shared with reads.
    View Answer & Explanation

    Answer: A (Self-deadlock waiting for itself.)

    Write waits for every reader to leave. You are still a reader. Downgrade (write then read) is the supported direction.

  4. Q4: StampedLock tryOptimisticRead without validate. Risk?

    1. Torn fields used as if consistent.
    2. Stamp becomes reentrant safely.
    3. Write lock is taken automatically.
    4. Happens-before is always granted.
    View Answer & Explanation

    Answer: A (Torn fields used as if consistent.)

    Optimistic mode is a weak read. Only validate(stamp) == true gives the write-unlock happens-before guarantee.

  5. Q5: Condition.await() without holding the ReentrantLock. Typical result?

    1. IllegalMonitorStateException thrown.
    2. Thread sleeps but keeps the lock.
    3. Await upgrades lock to fair mode.
    4. Signal runs without any waiter.
    View Answer & Explanation

    Answer: A (IllegalMonitorStateException thrown.)

    Same discipline as Object.wait(): hold the associated lock. await then releases it atomically.

12. Reasoning Exercises

  1. Pick the lock: (a) request-path metric increment you may drop under load, (b) in-memory catalog searched 10k×/s and rebuilt once a minute, (c) transfer between two accounts with a global lock order, (d) tiny (x,y) point, millions of reads, rare writes. For each: synchronized, ReentrantLock, RW lock, tryLock, or StampedLock?
  2. Fix the buffer: A teammate uses one Condition and signal() after both put and take. Sketch the lost-wakeup / wrong-waker bug. Repair with two Conditions (names + who signals whom).
  3. Fair vs non-fair: A latency SLO cares about p99 wait for a lock, not throughput. Which constructor? What do you tell the interviewer about tryLock() on that lock?
  4. Downgrade trace: Thread W holds write, acquires read, unlocks write. Thread R then acquires read. Thread W2 tries write. Who proceeds, who waits, and why no writer slipped between W's mutate and W's subsequent read?
  5. tryLock timeout design: Two resources, no global order. Write the acquire-both-or-release-held pattern (Oracle Safelock). Where do you sleep/backoff, and why must failed acquires still unlock only the locks you actually got?
