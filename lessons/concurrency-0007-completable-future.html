Deep Dive: CompletableFuture

~40 minutes · ties to mission · builds on L5 Executors/Future, L6 Collections

Senior Interview Focus: Lesson 5 gave you Future — submit, block on get(), done. Production microservices need compose parallel downstream calls, handle failures in-line, and enforce timeouts without callback hell. CompletableFuture is the JDK's answer. Interviewers probe thenCompose vs thenApply, join + CompletionException, and blocking I/O on commonPool.

Primary sources: Oracle — Futures · CompletableFuture javadoc · CompletionStage · JEP 266 — More Concurrency Updates

1. Future Pain → Why CompletableFuture Exists

Lesson 5 ExecutorService.submit returns Future<T>:

  • Blocking only — get() parks the caller until done. Chaining means nested get() calls or manual polling.
  • No composition — "when A finishes, call B" needs your own callbacks or extra threads.
  • Exception handling awkward — failure surfaces as ExecutionException on get(); no pipeline hook.
  • No combine — merging two independent futures requires a third thread or blocking both.
// Future hell — blocks twice, serial even if B could start after A
Future<User> userFut = pool.submit(() -> userClient.get(id));
Future<Orders> ordersFut = pool.submit(() -> orderClient.list(userFut.get().id())); // blocks!
Orders o = ordersFut.get(); // blocks again

CompletableFuture<T> implements Future<T> and CompletionStage<T> — a promise you can chain, combine, and complete manually. Java 8+.

2. Creating Async Work — supplyAsync / runAsync

ExecutorService ioPool = ...; // bounded, named — Lesson 5

CompletableFuture<String> data = CompletableFuture
    .supplyAsync(() -> httpClient.fetch(url), ioPool);

CompletableFuture<Void> sideEffect = CompletableFuture
    .runAsync(() -> auditLog.record(event), ioPool);
FactoryReturnsTask type
supplyAsync(Supplier)CompletableFuture<U>Produces value
runAsync(Runnable)CompletableFuture<Void>Fire-and-forget side effect

Critical production rule: one-arg overloads use ForkJoinPool.commonPool() (Lesson 5). Never put blocking I/O there — starves parallel streams and every other default-async CF site.

Senior line: always pass a dedicated Executor for I/O-bound async. Name it. Bound it. Monitor it.

3. Chaining — Transform & Flatten

MethodInputOutput CF typeUse
thenApply(fn)T → UCompletableFuture<U>Map result (sync stage on completion thread)
thenAccept(consumer)T → voidCompletableFuture<Void>Consume result, no new value
thenRun(action)ignores TCompletableFuture<Void>Run after complete, no access to value
thenCompose(fn)T → CompletableFuture<U>CompletableFuture<U>Flatten nested async (next call depends on first)
thenCombine(other, fn)both T, UCompletableFuture<V>Merge two independent futures when both done
 
CompletableFuture<OrderSummary> pipeline =
    CompletableFuture
      .supplyAsync(() -> userClient.get(userId), ioPool)
      .thenCompose(user -> orderClient.listAsync(user.id()))  // NOT thenApply
      .thenApply(orders -> summarize(orders));

// Parallel fan-in — both start immediately
CompletableFuture<User> userF = CompletableFuture.supplyAsync(() -> loadUser(id), ioPool);
CompletableFuture<Credit> creditF = CompletableFuture.supplyAsync(() -> loadCredit(id), ioPool);

CompletableFuture<Dashboard> dash = userF.thenCombine(creditF, Dashboard::new);

thenApply vs thenCompose (interview gold):

  • thenApply(user -> orderClient.listAsync(user.id())) → CompletableFuture<CompletableFuture<Orders>> — nested hell.
  • thenCompose(user -> orderClient.listAsync(user.id())) → CompletableFuture<Orders> — flat pipeline.

Async variants: thenApplyAsync, thenComposeAsync, etc. run the stage on an executor (default: commonPool). Sync thenApply runs on the thread that completed the previous stage — fast map OK; blocking I/O is not.

4. Error Paths — exceptionally / handle / whenComplete

MethodWhen it runsTransforms result?
exceptionally(fn) Only on failure Yes — recovery value (or rethrow)
handle(fn) Always — gets (result, throwable) Yes — one of them is non-null
whenComplete(action) Always — side effect No — returns same outcome downstream 
CompletableFuture<Price> priced =
  CompletableFuture
    .supplyAsync(() -> pricingService.quote(sku), ioPool)
    .exceptionally(ex -> Price.fallback())           // only on failure
    .handle((price, ex) -> ex != null ? Price.zero() : price) // always
    .whenComplete((p, ex) -> metrics.record(ex));    // logging/metrics
  • exceptionally — fallback / default; if recovery throws, downstream fails.
  • handle — unified success+failure handler; good for "return Either-like result."
  • whenComplete — like finally for observability; exceptions still propagate unless earlier stage handled them.

Failed stage skips normal thenApply callbacks — they jump to exceptionally / handle or fail the chain.

5. Fan-Out / First-Wins — allOf / anyOf

CompletableFuture<User> u = ...;
CompletableFuture<Orders> o = ...;
CompletableFuture<Prefs> p = ...;

CompletableFuture<Void> all = CompletableFuture.allOf(u, o, p);
all.thenRun(() -> {
  // all three complete (maybe exceptionally) — check each .isCompletedExceptionally()
  buildPage(u.join(), o.join(), p.join());
});

CompletableFuture<Object> first = CompletableFuture.anyOf(replica1, replica2, replica3);
// first to complete wins — others keep running unless you cancel
  • allOf — waits for all; result is Void; inspect individuals for values/errors.
  • anyOf — first completion wins; type erasure to Object; others may still run — cancel if wasteful.

6. get vs join — CompletionException

get()join()
Checked exceptionsInterruptedException, ExecutionExceptionNone (unchecked)
Failure wrapperExecutionException with getCause()CompletionException with getCause()
Typical useLegacy / boundary where checked OKStream-style pipelines, lambdas
 
try {
  User u = future.join();
} catch (CompletionException e) {
  Throwable root = e.getCause(); // real RestClientException etc.
}

Inside thenApply, an uncaught exception completes the CF exceptionally — downstream join unwraps via CompletionException.

7. Cancellation & Timeouts (Java 9+)

future.cancel(true);  // mayInterruptIfRunning — task must cooperate (Lesson 1)

// Java 9+ — fail if not done in time
future.orTimeout(2, TimeUnit.SECONDS);

// Java 9+ — supply fallback value on timeout (does not throw TimeoutException)
future.completeOnTimeout(Price.fallback(), 2, TimeUnit.SECONDS);
  • orTimeout — completes exceptionally with TimeoutException if not done in time.
  • completeOnTimeout — completes normally with fallback — good for cache/stale-while-revalidate patterns.
  • Timeouts apply to the CF's completion deadline — chain with thenCompose carefully; each stage can have its own timeout.

8. Pipeline vs Nested Future Hell

// BAD — nested, blocks, hard to read
Orders o = pool.submit(() -> {
  User u = userClient.get(id);           // blocking
  return orderClient.list(u.id());       // blocking
}).get();

// GOOD — declarative pipeline, non-blocking composition
CompletableFuture<Orders> o = CompletableFuture
  .supplyAsync(() -> userClient.get(id), ioPool)
  .thenCompose(u -> orderClient.listAsync(u.id()));

// BETTER for parallel deps — don't serialize independent calls
var userF = supplyAsync(() -> userClient.get(id), ioPool);
var creditF = supplyAsync(() -> creditClient.get(id), ioPool);
return userF.thenCombine(creditF, this::merge);

Senior pattern: fan-out parallel I/O at the top, fan-in with thenCombine / allOf, single error handler at the end. Blocking belongs on the pool thread, not Tomcat worker (Lesson 5).

9. Enterprise Framing

ScenarioPattern
Parallel downstream calls Start all CFs immediately; allOf + join or thenCombine. Don't call get() on first before starting second.
Spring @Async returning CF Controller can return CompletableFuture<Response> — frees servlet thread while work runs on async executor. Must configure a real pool bean — not default per-task thread.
Timeout + fallback completeOnTimeout(fallback, ...) or orTimeout + exceptionally. Match SLA: degrade vs fail.
Aggregating microservice BFF Bounded ioExecutor; per-dependency CF; handle per call for partial failure; CHM for request-scoped cache (L6).
Not WebFlux CF composes async within threads — fine for blocking clients wrapped in supplyAsync. Reactive streams (Reactor) are a different model — out of scope.
Senior line: CompletableFuture is orchestration glue — not a magic fix for blocking I/O without a bounded executor and timeout story.

10. Classic Bugs

  • Blocking I/O on commonPool — default supplyAsync starves JVM-wide parallelism.
  • thenApply instead of thenCompose — nested CompletableFuture<CompletableFuture<...>>.
  • Blocking get() inside thenApply — stalls completion thread; deadlock risk with fixed pool.
  • Serializing independent calls — starting B only after A's get() wastes latency.
  • Ignoring exceptionally — silent failure until terminal join.
  • allOf without checking exceptional completion — join throws even if allOf itself "succeeded."
  • anyOf without cancelling losers — wasted downstream load.
  • Heavy work in sync thenApply on commonPool completion thread — use thenApplyAsync(..., pool).

11. Revision Notes

  • Future = block + no compose. CF = chain + combine.
  • supplyAsync/runAsync — always pass executor for I/O.
  • thenCompose flattens; thenApply maps.
  • thenCombine / allOf = parallel deps; anyOf = first wins.
  • join → CompletionException; unwrap getCause().
  • orTimeout fails; completeOnTimeout degrades.
  • Don't block commonPool. Don't block Tomcat thread on get().

12. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: thenApply vs thenCompose when next step is async?

    1. thenCompose — flattens nested CF.
    2. thenApply — flattens nested CF.
    3. thenRun — flattens nested CF.
    4. thenAccept — flattens nested CF.
    View Answer & Explanation

    Answer: A (thenCompose — flattens nested CF.)

    thenApply wrapping a CF gives CF<CF<T>>. thenCompose is monadic flatMap — the interview distinction.

  2. Q2: supplyAsync(() -> jdbc.query()) one-arg overload. Risk?

    1. Blocks ForkJoin common pool.
    2. Runs only on main thread.
    3. Throws RejectedExecution always.
    4. Creates unbounded platform threads.
    View Answer & Explanation

    Answer: A (Blocks ForkJoin common pool.)

    Default executor is commonPool(). JDBC blocks — starves parallel streams and other default-async CF work.

  3. Q3: future.join() when stage failed. Thrown type?

    1. CompletionException wrapping cause.
    2. ExecutionException wrapping cause.
    3. InterruptedException wrapping cause.
    4. RejectedExecutionException cause.
    View Answer & Explanation

    Answer: A (CompletionException wrapping cause.)

    join is unchecked. Real failure is e.getCause(). get() uses checked ExecutionException.

  4. Q4: exceptionally vs handle on success path?

    1. handle runs; exceptionally skips.
    2. exceptionally runs; handle skips.
    3. Both always transform result.
    4. Neither runs on success path.
    View Answer & Explanation

    Answer: A (handle runs; exceptionally skips.)

    exceptionally only on failure. handle always — gets (result, ex) with one null.

  5. Q5: allOf(f1, f2, f3) all complete. f2 failed. allOf result?

    1. Completes normally; f2 join throws.
    2. allOf itself completes exceptionally.
    3. allOf cancels f1 and f3 always.
    4. allOf blocks until f2 retries.
    View Answer & Explanation

    Answer: A (Completes normally; f2 join throws.)

    allOf completes when all stages finish (including exceptionally). Check isCompletedExceptionally() per future before join.

  6. Q6: completeOnTimeout(fallback, 2, SECONDS) fires. Outcome?

    1. Completes normally with fallback.
    2. Completes exceptionally with timeout.
    3. Cancels without any completion.
    4. Blocks caller for two seconds.
    View Answer & Explanation

    Answer: A (Completes normally with fallback.)

    completeOnTimeout is graceful degradation. orTimeout completes exceptionally with TimeoutException.

13. Reasoning Exercises

  1. Rewrite Future hell: Three sequential blocking HTTP calls today via submit().get(). Sketch CF pipeline with one thenCompose chain + bounded ioExecutor.
  2. Parallel BFF: Dashboard needs User, Orders, Recommendations (independent). Start all three without waiting. Combine with allOf. One service down — design partial page with handle per call.
  3. Timeout policy: Pricing SLA 500ms; catalog SLA 2s. Where attach orTimeout vs completeOnTimeout? What does the client see?
  4. Thread budget: Tomcat 200 threads, ioExecutor core 50 max 100. Controller does cf.get() on servlet thread. Under load what breaks first?
  5. thenApply trap: thenApply(u -> repo.findAsync(u.id())) — return type? Fix. What breaks at join if unfixed?
  6. anyOf replicas: Three read replicas, anyOf first response. How cancel the other two? What if slow replica returns stale data after fast one?

Questions? Ask your coach — CF composition shows up in every microservices interview.
