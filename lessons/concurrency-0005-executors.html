Deep Dive: Executors & Thread Pools

~40 minutes · ties to mission · builds on Lesson 1 (raw threads vs pools), Lesson 4 (locks done)

Senior Interview Focus: Lesson 1 said "don't spawn new Thread() per request." This lesson is how production actually runs work: bounded pools, queue backpressure, rejection policies, graceful shutdown, and sizing heuristics. Interviewers love factory-method traps (newCachedThreadPool, unbounded LinkedBlockingQueue in fixed pools) and "what happens when the queue is full?"

Primary sources: Oracle — Executors · Executor · ExecutorService · ThreadPoolExecutor · Executors · ForkJoinPool.commonPool

1. Why Executors Over new Thread()

Lesson 1: each platform thread costs native stack memory (~1 MB order of magnitude), kernel scheduling, and JVM bookkeeping. Under HTTP spikes, new Thread(task).start() per request creates an unbounded thread count → context-switch storm, OOM, or thrashing.

An executor separates task definition (Runnable / Callable) from thread lifecycle. A fixed set of worker threads pulls work from a queue. You get:

  • Reuse — amortize thread creation cost.
  • Bounds — cap concurrency + queue depth → predictable memory and load.
  • Policy — what to do when saturated (reject, block caller, drop).
  • Lifecycle — one place to shutdown instead of hunting stray threads.
Senior line: raw threads are fine for demos; executors are how you survive production traffic.

2. Executor → ExecutorService → ThreadPoolExecutor

TypeRole
Executor Minimal: execute(Runnable) — fire-and-forget. No lifecycle API.
ExecutorService Extends Executor + submit (returns Future), invokeAll/invokeAny, shutdown/shutdownNow, awaitTermination.
ThreadPoolExecutor Concrete pool: core/max threads, keep-alive, work queue, thread factory, rejection handler. The implementation you configure in production.

Submission model (ThreadPoolExecutor):

  1. If running threads < corePoolSize → create thread, run task.
  2. Else if queue not full → enqueue task.
  3. Else if running threads < maximumPoolSize → create thread, run task.
  4. Else → RejectedExecutionHandler.
  submit task
      │
      ├─ threads < core? ──yes──► new worker, run now
      │
      ├─ queue has room? ──yes──► enqueue
      │
      ├─ threads < max? ──yes──► new worker, run now
      │
      └─ else ──► reject policy

Key insight: the queue sits between core and max. A bounded queue forces you to grow toward maxPoolSize before rejecting; an unbounded queue may never grow past core — tasks pile up in memory instead.

3. Runnable vs Callable & Future Basics

RunnableCallable<V>
ReturnsvoidTyped result V
Checked exceptionCannot throw (use unchecked)May throw Exception
Submit APIexecute(r) or submit(r) → Future<?>submit(callable) → Future<V>
 
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Integer> fut = pool.submit(() -> {
  return restClient.fetchCount(); // may throw
});

// later on caller thread:
try {
  Integer n = fut.get(2, TimeUnit.SECONDS); // blocks until done or timeout
} catch (TimeoutException e) {
  fut.cancel(true); // may interrupt worker if running
} catch (ExecutionException e) {
  Throwable cause = e.getCause(); // real failure from Callable
}
  • get() — block until complete; wraps failure in ExecutionException.
  • get(timeout, unit) — bounded wait; TimeoutException if not done.
  • cancel(mayInterruptIfRunning) — if not started, never runs; if running and true, sends interrupt (task must cooperate — Lesson 1).
  • isDone() — true after normal completion, exception, or cancellation.
  • isCancelled() — cancelled before completion.

Interview trap: execute() swallows nothing — uncaught exceptions go to the thread's UncaughtExceptionHandler. submit() stores the exception; you only see it on get().

Out of scope here: CompletableFuture composition (Module 03 S07).

4. ThreadPoolExecutor Knobs

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                              // corePoolSize
    16,                             // maximumPoolSize
    60L, TimeUnit.SECONDS,          // keepAlive — idle threads above core die after this
    new ArrayBlockingQueue<>(100),   // work queue
  new ThreadFactory() { /* name threads */ },
    new ThreadPoolExecutor.CallerRunsPolicy()
);

Core vs max vs keepAlive

  • corePoolSize — baseline workers kept alive even when idle (unless allowCoreThreadTimeOut(true)).
  • maximumPoolSize — hard cap on concurrent workers.
  • keepAliveTime — threads above core that are idle longer than this are terminated.

Queue choice (shapes behavior)

QueueBehaviorTypical use
LinkedBlockingQueue (unbounded) Never "full" → pool stays at core; tasks accumulate in heap newFixedThreadPool trap — hidden OOM under load
ArrayBlockingQueue (bounded) Fixed capacity → pushes pool toward max, then reject Production default when you want backpressure
SynchronousQueue Zero capacity — handoff; no storage; submit blocks until a worker takes it newCachedThreadPool — grows threads aggressively
PriorityBlockingQueue Ordered by priority — rare; know ordering contract Scheduled / priority workloads

ThreadFactory

Name threads (billing-worker-%d), set daemon flag, uncaught-exception handler, or wrap for MDC/logging context. Debugging thread dumps without names is pain.

ThreadFactory named = r -> {
  Thread t = new Thread(r);
  t.setName("report-pool-" + t.getId());
  t.setUncaughtExceptionHandler((th, ex) -> log.error("pool death", ex));
  return t;
};

5. Executors Factory Methods — What They Build + Traps

FactoryWhat you getTrap
newFixedThreadPool(n) Fixed core=max=n, unbounded LinkedBlockingQueue Queue grows forever — no backpressure, OOM under spike
newCachedThreadPool() core=0, max=Integer.MAX_VALUE, SynchronousQueue, 60s keepAlive Unbounded thread creation — fine for short tasks, lethal under sustained load
newSingleThreadExecutor() One worker, unbounded queue — serialized execution Hidden queue growth; use when strict ordering matters
newScheduledThreadPool(n) Delayed / periodic tasks Still need bounds on delayed work volume
newWorkStealingPool() ForkJoinPool-style work stealing Different semantics — deques, not classic TPE queue story
Senior line: treat Executors helpers as interview trivia. Production pools are usually explicit ThreadPoolExecutor with bounded queue + named threads + metrics.

6. Rejection Policies — When to Pick Each

Triggered when pool is at maxPoolSize and queue is full (or handoff fails for SynchronousQueue).

PolicyBehaviorWhen
AbortPolicy (default) Throws RejectedExecutionException Fail fast — caller handles retry / 503. APIs that must not silently drop.
CallerRunsPolicy Runs task on the submitting thread Natural backpressure — slows producers (e.g. batch ingest). Risk: blocks HTTP thread if misused.
DiscardPolicy Silently drops the task Only for loss-tolerant telemetry / sampling — document it.
DiscardOldestPolicy Drops head of queue, retries submit Freshness over completeness (latest price tick wins).

Custom handler: log + metric + dead-letter queue. Interviewers want you to name the policy and the user-visible outcome (503 vs slow vs lost event).

7. Graceful Shutdown

pool.shutdown();           // no new tasks; queued work still runs
// optional: pool.awaitTermination(30, SECONDS);

List<Runnable> dropped = pool.shutdownNow(); // interrupt workers, drain queue into returned list
pool.awaitTermination(30, SECONDS);          // wait for workers to finish
  • shutdown() — orderly: stop accepting; finish what's queued.
  • shutdownNow() — aggressive: interrupt running tasks, return unstarted tasks. Tasks must handle interrupt (Lesson 1).
  • awaitTermination — block until idle or timeout. Pair with retry loop in app shutdown hooks.

Spring / Tomcat: container calls lifecycle stop on beans and connectors — your @PreDestroy or DisposableBean should shut down custom pools the same way. Leaked pools keep JVM alive or lose in-flight work.

8. ForkJoinPool.commonPool — Parallel Streams Tie-In

Module 02: parallelStream() uses ForkJoinPool.commonPool() — shared JVM-wide, sized ~ Runtime.getRuntime().availableProcessors() - 1 (with floor). Work-stealing deque, not the classic TPE queue model.

  • CPU-bound fork/join splits benefit from stealing idle workers.
  • Blocking I/O on common pool starves every other parallel stream and CompletableFuture.supplyAsync default — Lesson 2/Streams framing.
  • Custom ForkJoinPool for isolated parallel work is the fix when you must parallelize CPU locally without polluting common pool.

Executors lesson = general task pools; FJP = divide-and-conquer. Both are threads under the hood (Lesson 1).

9. Pool Sizing Heuristics

WorkloadHeuristicWhy
CPU-bound ~ cores or cores + 1 More threads than cores → context switch, cache thrash, no speedup
I/O-bound cores × (1 + wait/compute) — Little's law thinking Threads block on DB/HTTP; while one waits, another can run
Mixed microservice Separate pools per dependency class One slow downstream must not exhaust the pool for everything

Example: 8 cores, task spends 90% waiting on DB → rough target 8 × (1 + 9) ≈ 80 — start conservative, measure queue depth, p99 latency, and CPU. Tuning is empirical.

Bounded always wins over "infinite threads fix I/O." Unbounded growth masks overload until the process dies.

10. Enterprise Framing

LayerWhat runs where
Tomcat / Jetty worker threads One thread per in-flight HTTP request (bounded connector thread pool). Your service code runs here — don't block it on unbounded custom work.
Spring @Async Submits to a configured TaskExecutor (often ThreadPoolTaskExecutor). Default if misconfigured can be SimpleAsyncTaskExecutor (new thread per task!) — always define a bean with core/max/queue/rejection.
Custom app pools Reports, webhooks, bulk export — dedicated bounded pool + rejection + metrics (queue size, active count, rejected tasks).
Backpressure Full queue + Abort → 503 / retry-after. CallerRuns → slows ingress. Message bus → consumer lag. Pick story that matches SLA.
Senior line: HTTP thread handles the request; offload slow/fire-and-forget to a named pool you can shut down and observe.

11. Classic Bugs

  • Unbounded fixed pool — newFixedThreadPool under load → million-task queue, GC pause, OOM.
  • Cached pool under sustained load — thousands of threads, scheduler collapse.
  • CallerRuns on HTTP thread — saturation runs work on Tomcat worker → cascading latency.
  • Never shutdown — non-daemon workers prevent clean deploy; thread leak on hot reload.
  • submit exception swallowed — never call get() → silent failure.
  • Blocking on common pool — parallel stream + JDBC inside → global starvation.
  • Shared mutable state without sync — pool doesn't fix races; Lessons 2–4 still apply.

Later sections (not here): CompletableFuture (S07), concurrent collections / atomics (S06), virtual threads, deep AQS / work-stealing internals.

12. Revision Notes

  • TPE: core → queue → max → reject. Queue type changes everything.
  • execute vs submit — exception path differs.
  • Future.get / cancel / isDone — blocking and interrupt semantics.
  • Fixed pool trap = unbounded queue. Cached pool trap = unbounded threads.
  • Abort = fail fast; CallerRuns = backpressure; Discard* = lossy.
  • shutdown orderly, shutdownNow interrupt, awaitTermination wait.
  • CPU ≈ cores; I/O ≈ cores × wait ratio; measure in prod.
  • commonPool = shared; no blocking I/O there.

13. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: newFixedThreadPool(8) under heavy load. First failure mode?

    1. Unbounded queue grows until OOM.
    2. Pool rejects at eight threads.
    3. Creates ninth thread immediately.
    4. Tasks run on common pool.
    View Answer & Explanation

    Answer: A (Unbounded queue grows until OOM.)

    Fixed factory uses unbounded LinkedBlockingQueue. Pool stays at 8 workers; tasks accumulate in the queue — no RejectedExecutionException until memory gives out.

  2. Q2: Core=4 max=16 bounded queue full all workers busy. Next submit?

    1. Rejected per handler policy.
    2. Always blocks until queue slot.
    3. Always spawns unbounded threads.
    4. Runs on ForkJoin common pool.
    View Answer & Explanation

    Answer: A (Rejected per handler policy.)

    At max threads with full queue, TPE cannot accept work — default AbortPolicy throws. CallerRuns would run on submitter instead.

  3. Q3: submit(Callable) throws inside task. When seen?

    1. On Future.get as ExecutionException.
    2. Immediately on calling thread.
    3. Never if pool has two threads.
    4. Only after shutdownNow is called.
    View Answer & Explanation

    Answer: A (On Future.get as ExecutionException.)

    submit captures failure into the Future. Caller must get() (or isDone + get) to surface ExecutionException with getCause().

  4. Q4: newCachedThreadPool under sustained blocking I/O. Risk?

    1. Unbounded thread count exhaustion.
    2. Queue blocks at core size.
    3. Only one thread ever runs.
    4. Tasks always run in caller.
    View Answer & Explanation

    Answer: A (Unbounded thread count exhaustion.)

    SynchronousQueue + max=Integer.MAX_VALUE → each blocked submit spawns another thread. Classic production foot-gun.

  5. Q5: CallerRunsPolicy when pool saturated. Effect?

    1. Submitter thread runs the task.
    2. Oldest queued task is dropped.
    3. RejectedExecutionException is thrown.
    4. Task is sent to common pool.
    View Answer & Explanation

    Answer: A (Submitter thread runs the task.)

    Backpressure: producer slows down. Dangerous if submitter is a Tomcat HTTP worker — latency propagates to clients.

  6. Q6: parallelStream with JDBC inside map. Main risk?

    1. Starves ForkJoin common pool.
    2. Creates daemon threads only.
    3. Bypasses happens-before rules.
    4. Forces single-thread execution.
    View Answer & Explanation

    Answer: A (Starves ForkJoin common pool.)

    Blocking I/O on common pool ties up shared workers — other parallel streams and default async stall. Use dedicated executor or sequential/stream off common pool.

14. Reasoning Exercises

  1. Design a pool: Bulk PDF export — 30s CPU + 200ms S3 upload per job, peak 200 jobs/min. Propose core, max, queue size, rejection policy. Defend each number.
  2. Factory trap: Teammate uses Executors.newFixedThreadPool(50) for incoming webhooks. Draw the failure timeline under 10× traffic spike. Rewrite as explicit ThreadPoolExecutor.
  3. Shutdown story: App receives SIGTERM during deploy. Order: stop accepting HTTP, drain in-flight, shutdown custom pool, awaitTermination. What if a task ignores interrupt after shutdownNow?
  4. Future contract: Three submit calls; you need all results or fail the batch in 5s. Sketch invokeAll vs manual get(timeout) + cancel siblings on first failure.
  5. Tomcat + @Async: Controller returns 202 immediately; work runs async. Where can CallerRunsPolicy still block the client? How do you fix it?
  6. Sizing: 4 cores, each task 5ms CPU + 95ms HTTP. Rough pool size? What metric tells you you're too high? Too low?
