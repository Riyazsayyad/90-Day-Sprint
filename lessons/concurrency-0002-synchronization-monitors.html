Deep Dive: Synchronization & Monitors

~28 minutes · ties to mission · builds on Lesson 1, java.lang.Object

Senior Interview Focus: You already know threads share the heap and that BLOCKED means waiting on a monitor. Now own the lock model: what synchronized actually guarantees, why counter++ is not atomic, how wait() differs from sleep(), and when intrinsic locks are the wrong tool. Interviewers love the broken-counter trace and the "which object is the lock?" question.

Primary sources: Oracle — Intrinsic Locks and Synchronization · Oracle — Guarded Blocks (wait/notify) · JLS Chapter 17 — Threads and Locks

1. Why Synchronization Exists

Module 00 taught you: heap is shared, stack is per-thread. Module 03 Section 01 warned: two threads reading/writing the same field without coordination → data races.

A data race is when two threads access the same memory location, at least one is a write, and there is no happens-before relationship between them. The JVM does not promise a sensible result — you may see lost updates, torn reads, or "works on my laptop" flakiness under load.

Lost update (classic)

class Counter {
  int count = 0;
  void increment() { count++; } // NOT atomic — read, add, write
}

Two threads both read count == 5, both write 6. Expected 7, got 6. One increment vanished.

Check-then-act (enterprise trap)

if (!cache.containsKey(key)) {   // Thread A checks — absent
  cache.put(key, loadFromDb());  // Thread B checks — absent, both load
}

Even if each line looks safe alone, the compound action is not atomic. Spring singleton services with mutable fields hit this constantly unless designed thread-safe.

2. Critical Section & Mutual Exclusion

A critical section is code that touches shared mutable state. Mutual exclusion means at most one thread executes that section at a time for a given lock.

Java's built-in mechanism: every object carries an intrinsic lock (monitor lock). synchronized acquires it before entering and releases it on exit — even if an exception escapes.

3. JVM Monitor Model (Interview Level)

You met monitors briefly in java.lang.Object: wait(), notify(), Mark Word lock bits. Here is the operational model:

  • Every object has one monitor (intrinsic lock) and one wait set.
  • Entry queue: threads blocked trying to enter synchronized on this monitor → Thread.State.BLOCKED.
  • Wait set: threads that called wait() on this object → WAITING / TIMED_WAITING.
  • Owner: at most one thread holds the lock at a time.

Mark Word lock states (preview)

The object header's Mark Word tracks lock state. HotSpot optimizes:

StateMeaning
BiasedLock biased toward one thread — uncontended fast path
Thin / lightweightSimple stack-based lock via CAS when low contention
Fat / inflatedFull monitor with native mutex + wait set under heavy contention

You do not tune these in application code. Senior value: explain why uncontended synchronized is cheap and why lock convoys under contention hurt throughput — thread dumps show piles of BLOCKED.

4. synchronized Methods vs Blocks

Instance method — locks this

public synchronized void transfer() {
  // implicitly: synchronized (this) { ... }
}

Static method — locks the Class object

public static synchronized void resetAll() {
  // implicitly: synchronized (MyService.class) { ... }
}

Instance lock and class lock are different monitors. A static synchronized method does not block an instance synchronized method on the same object unless they share the same lock object.

Block — explicit lock object

private final Object lock = new Object();

void update() {
  synchronized (lock) {
    // only threads using THIS lock object block each other
  }
}

Interview rule: synchronization protects the lock object you chose — not "the method" or "the class" abstractly. Two blocks on different objects do not exclude each other.

5. Reentrancy

A thread that already holds a monitor may acquire it again. Each acquire must be matched by a release (nested synchronized blocks/method calls unwind correctly).

public synchronized void outer() {
  inner(); // same thread re-enters same monitor — legal
}
public synchronized void inner() { /* ... */ }

Without reentrancy, code calling synchronized helpers from synchronized methods would self-deadlock. This is why Java monitors are reentrant.

6. wait / notify / notifyAll

From Object — now with concurrency framing:

  • Caller must own the object's monitor → else IllegalMonitorStateException.
  • wait() atomically releases the lock and places the thread in the object's wait set.
  • On notify() / notifyAll(), a waiter moves to re-enter the lock; it does not run until it re-acquires the lock.
  • sleep() does not release monitors — different from wait().

Always wait in a while loop

synchronized (lock) {
  while (!conditionMet()) {
    lock.wait();
  }
  // work — condition still true after re-acquire
}

Reasons: spurious wakeups (allowed by spec), another thread may steal the condition between notify and your re-entry, multiple waiters with notifyAll().

Default: prefer notifyAll() unless you have a massive homogeneous pool and proven single-waiter semantics.

Producer–consumer sketch

class Drop {
  private String message;
  private boolean empty = true;

  public synchronized void put(String msg) {
    while (!empty) { wait(); }
    message = msg;
    empty = false;
    notifyAll();
  }

  public synchronized String take() {
    while (empty) { wait(); }
    String msg = message;
    empty = true;
    notifyAll();
    return msg;
  }
}

Oracle's guarded-block pattern — same lock guards both the condition and the wait/notify calls.

7. IllegalMonitorStateException

Thrown when:

  • wait(), notify(), or notifyAll() called without holding that object's monitor.
  • (Related) LockSupport.unpark misuse — different API, same "wrong state" family.

Common bug: calling someObject.wait() while holding a different lock than someObject.

8. Atomicity vs Visibility (Preview — S03 Next)

AtomicityAction completes as one indivisible stepYes — only one thread in block

synchronized provides both. volatile provides visibility + ordering for single reads/writes, not compound check-then-act. Full JMM rules → Section 03.

9. Classic Bugs & Interview Traps

  • Unsynchronized counter: count++ — fix with synchronized block or AtomicInteger (later).
  • Wrong lock object: two methods synchronize on different objects — no mutual exclusion.
  • String literal lock: synchronized ("LOCK") — interned strings share monitors across the JVM → accidental coupling. Use private final Object lock = new Object().
  • Lock during I/O: holding monitor while calling DB/HTTP blocks all other threads on that lock — throughput killer.
  • notify without changing condition: waiter wakes, while-loop re-checks, loops forever if state wrong.

10. When synchronized Is Fine vs java.util.concurrent

synchronized is fine when:

  • Simple invariants on a few fields
  • Short critical sections, no I/O inside lock
  • Coarse-grained guarding of a small object's state

Reach for java.util.concurrent (Sections 04–06) when:

  • Need timed/try locks, fair ordering, read/write split
  • Executor pools, concurrent maps, latches, semaphores
  • High contention — explicit locks + better structures reduce convoys
Senior line: start with the simplest correct lock; measure; upgrade when contention or API limits bite.

11. Enterprise Framing

  • Spring singleton beans: one instance, many request threads. Mutable fields (counters, caches without sync) = latent races. Prefer immutable state, concurrent collections, or confine mutation to a single-thread executor.
  • Shared service cache: check-then-act on HashMap is unsafe. ConcurrentHashMap.computeIfAbsent (Section 06) or synchronized guard around the whole check+put.
  • Thread-safe by design: minimize shared mutable state; make races structurally impossible before sprinkling synchronized.

12. Revision Notes

  • Data race = concurrent access, at least one write, no synchronization.
  • Every object has a monitor; synchronized acquires/releases it.
  • Instance method → this; static → Class; block → object you name.
  • wait releases lock; sleep does not. Always while + prefer notifyAll.
  • synchronized = atomicity + visibility; volatile deep dive is next section.

13. 5 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Instance synchronized method locks which monitor?

    1. The instance monitor (this).
    2. The class monitor (Class).
    3. The thread monitor (Thread).
    4. The stack monitor (Stack).
    View Answer & Explanation

    Answer: A (The instance monitor (this).)

    JLS: instance synchronized methods lock the monitor of the object invoked (this). Static methods lock the Class object instead.

  2. Q2: Calling wait() on a held monitor does what?

    1. Releases lock and suspends.
    2. Keeps lock and suspends.
    3. Releases lock and terminates.
    4. Keeps lock and terminates.
    View Answer & Explanation

    Answer: A (Releases lock and suspends.)

    wait() adds the thread to the wait set and releases the monitor so others can enter. sleep() suspends without releasing locks.

  3. Q3: Why guard wait() with a while loop?

    1. Guard against spurious wakeup.
    2. Guard against thread death.
    3. Guard against daemon shutdown.
    4. Guard against GC collection.
    View Answer & Explanation

    Answer: A (Guard against spurious wakeup.)

    Also: other threads may change the condition before you re-acquire. Re-test the predicate every time you wake.

  4. Q4: Static synchronized method locks what?

    1. The Class object monitor.
    2. The instance monitor (this).
    3. The Thread object monitor.
    4. The Method object monitor.
    View Answer & Explanation

    Answer: A (The Class object monitor.)

    Static synchronized methods lock the Class object for the declaring class — not any instance.

  5. Q5: Two threads unsynchronized increment—result?

    1. Lost updates are possible.
    2. Lost updates are impossible.
    3. Deadlock is always guaranteed.
    4. JVM throws on second write.
    View Answer & Explanation

    Answer: A (Lost updates are possible.)

    count++ is read-modify-write. Without synchronization or atomics, increments can be lost — no exception, just wrong counts.

  3. Lock object: Class has synchronized void a() and synchronized void b(). Thread 1 in a() calls b(). Deadlock or OK? Why?
  4. wait/notify bug: Producer calls notify() outside synchronized block. What exception? Fix it.
