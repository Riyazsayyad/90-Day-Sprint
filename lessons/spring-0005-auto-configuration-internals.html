Spring Boot Auto-Configuration Internals

~40 minutes · Module 05 Lesson 5 of 9 · deepest theory lesson · builds on S04, classloaders / fat JAR

Senior Interview Focus: Auto-config is not magic. It is: classpath entries listed in AutoConfiguration.imports + @Conditional* + “back off if user already defined the bean.” Can you answer “why did this DataSource appear?” and “why didn’t it?” with --debug / Condition Evaluation Report?

Primary sources: Using Auto-configuration · Creating Auto-configuration · Boot 3 — imports file

1–2. Why Auto-Config Exists; Framework vs Boot

Spring Framework: IoC, MVC, AOP, tx — you wire or scan your classes.

Spring Boot: opinions + starters + embedded server + auto-configuration: if JDBC is on the classpath and you did not define a DataSource, Boot creates one from spring.datasource.*.

Goal: 80% of apps share the same 50 @Bean methods. Encode them once. Let conditions skip the rest.

3. @SpringBootApplication — Three Meta-Annotations

@SpringBootApplication
    = @SpringBootConfiguration   → @Configuration (your app config)
    + @EnableAutoConfiguration   → import auto-config classes (this lesson)
    + @ComponentScan             → your package tree (S03)

You can split them. Almost nobody does. Know the split for interviews.

4–5. What @EnableAutoConfiguration Triggers

@EnableAutoConfiguration
        │
        ▼
AutoConfigurationImportSelector
        │  reads from every JAR on the classpath:
        ▼
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
        │  one FQCN per line
        ▼
Candidate auto-config classes (filtered by conditions + exclude)
        │
        ▼
Imported as BeanDefinitions (lite @AutoConfiguration, proxyBeanMethods=false)

Must know (Boot 3): Auto-config registration is the imports file. META-INF/spring.factories key EnableAutoConfiguration was removed in 3.0. Other spring.factories keys still exist. Interviewers still say “spring.factories” — correct them politely: “for auto-config, imports file since 2.7/3.0.”

Fat JAR: Boot’s nested loader (LaunchedURLClassLoader) still exposes those META-INF files from nested jars.

6. Anatomy of an Auto-Config Class

@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@EnableConfigurationProperties(DataSourceProperties.class)
@Import(DataSourcePoolMetadataProvidersConfiguration.class)
public class DataSourceAutoConfiguration {
  // nested @Configuration classes with more @ConditionalOn*
}
  • @AutoConfiguration — stereotype; can declare before/after other auto-configs (ordering).
  • Must not be component-scanned. Only loaded via the imports file.
  • Inner beans typically @ConditionalOnMissingBean(DataSource.class).

7–8. Conditions Deep Dive + JDBC Story

Need a DataSource bean?
  │
  ├─ spring-jdbc / DataSource class on classpath?     @ConditionalOnClass
  ├─ User already defined DataSource?                 @ConditionalOnMissingBean → SKIP
  ├─ spring.datasource.url (or embedded DB) present?
  └─ Web vs none — sometimes extra conditions
           │
           ▼
     Hikari DataSource bean created

Add spring-boot-starter-data-jpa → Hibernate + DataSource auto-config light up. Remove the starter → conditions fail → beans gone. Classpath-driven behavior.

9–11. Convention, Risk, Back-off

Benefit: empty app + starter-web = Tomcat + DispatcherServlet.

Risk: surprise beans (Redis connection to localhost in prod because starter-data-redis sneaked in). Always know your dependency tree.

Back-off (must know): you declare @Bean DataSource myDs() → @ConditionalOnMissingBean(DataSource.class) is false → Hikari auto-config does not create a second pool. Your bean wins.

12. Exclude

@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
public class ShopApplication { }

Or spring.autoconfigure.exclude=.... Use when you must not have a DataSource (library, batch with custom routing) and conditions aren’t enough.

13. Debugging Workflow

  1. java -jar app.jar --debug (or logging.level.org.springframework.boot.autoconfigure=DEBUG)
  2. Read Condition Evaluation Report — Positive matches vs Negative matches with the failing condition named
  3. Actuator /actuator/conditions (S08) in a secured management port
  4. /actuator/beans — is the bean in the factory at all?
Must know: the report names the condition class that failed — e.g. OnClassCondition, OnBeanCondition. That is the mechanism. Not “Spring decided not to.”

14. Scenario: “Why did Spring create this bean?”

Trace: which starter brought which auto-config class → which condition was true → which @Bean method. Example: Hikari because DataSourceAutoConfiguration matched and you set spring.datasource.url.

15. Scenario: “Why didn’t Spring create this bean?”

Negative match. Typical: class missing (forgot starter), OnMissingBean lost (you already defined one), property matchIfMissing=false and key absent, exclude, wrong web application type (servlet vs reactive — S09).

16. Tiny Custom Auto-Config (Illustrative)

my-starter.jar
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
      com.acme.MeowAutoConfiguration

@AutoConfiguration
@ConditionalOnClass(CatClient.class)
class MeowAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean
  CatClient catClient() { return new CatClient(); }
}

Not a starter-authoring course. Enough to know libraries ship this file — not @ComponentScan of the library.

Mental Model

dependency on classpath
        +
AutoConfiguration.imports lists a class
        +
@Conditional* all true
        +
@ConditionalOnMissingBean still true
        =
bean appears

Auto-config ≠ magic.

Misconceptions

  • “Boot scans all JARs for @Component.” Libraries should not. Auto-config is explicit imports.
  • “spring.factories still registers auto-config on Boot 3.” No.
  • “I cannot override Boot beans.” You can — MissingBean pattern, or exclude.

Production Relevance

Unexpected Mongo client in a service that only needed a driver transitively — extra connections, extra failure modes. Review mvn dependency:tree like you review BeanDefinitions. Fat JAR classloader still participates (JVM S06).

Interview Articulation

“@EnableAutoConfiguration loads classes listed in AutoConfiguration.imports on the classpath. Each class is a bundle of conditional @Bean methods. If I already define a DataSource, OnMissingBean is false and Boot backs off. I debug with the Condition Evaluation Report from --debug or /actuator/conditions, not by guessing.”

Revision Notes

  • imports file → candidates → conditions → beans.
  • OnMissingBean = user override hook.
  • exclude = sledgehammer.

Interview One-Liners

  • “A starter is a POM plus auto-config, not a runtime daemon.”
  • “Negative matches are the answer key.”
  • “My DataSource bean is the feature, not a fight with Boot.”

Senior MCQs

  1. Q1: Boot 3 auto-config class names live in?

    1. AutoConfiguration.imports under META-INF/spring.
    2. Only web.xml in the WAR root.
    3. The module-info.java provides list.
    4. JDK META-INF/services of java.sql.
    View Answer & Explanation

    Answer: A (AutoConfiguration.imports under META-INF/spring.)

  2. Q2: User defines @Bean DataSource. Hikari auto-config?

    1. Backs off via @ConditionalOnMissingBean.
    2. Always creates a second pool anyway.
    3. Deletes the user bean at runtime.
    4. Promotes DataSource to request scope.
    View Answer & Explanation

    Answer: A (Backs off via @ConditionalOnMissingBean.)

  3. Q3: @SpringBootApplication does not include?

    1. @EnableAspectJAutoProxy by default here.
    2. @SpringBootConfiguration alias.
    3. @EnableAutoConfiguration trigger.
    4. @ComponentScan of the app package.
    View Answer & Explanation

    Answer: A (@EnableAspectJAutoProxy by default here.)

    The three are Configuration + EnableAutoConfiguration + ComponentScan. AOP is separate (S06), though Boot enables proxying when needed.

  4. Q4: Best tool for “why wasn’t X auto-configured?”

    1. Condition Evaluation Report (--debug).
    2. Only jmap histogram of the heap.
    3. HashMap load factor in the JDK.
    4. Replacing all beans with enums.
    View Answer & Explanation

    Answer: A (Condition Evaluation Report (--debug).)

  5. Q5: spring.factories EnableAutoConfiguration key on Boot 3?

    1. Removed for auto-config registration.
    2. The only supported discovery mechanism.
    3. Required alongside Tomcat XML.
    4. Used only by WebFlux Netty.
    View Answer & Explanation

    Answer: A (Removed for auto-config registration.)

  6. Q6: Auto-config classes should be?

    1. Listed in imports — never component-scanned.
    2. Annotated @RestController in default package.
    3. Loaded by Thread.currentThread only.
    4. Compiled without -parameters always.
    View Answer & Explanation

    Answer: A (Listed in imports — never component-scanned.)

  7. Q7: Adding starter-data-redis suddenly creates a factory. Why?

    1. Classpath + imports + matching conditions.
    2. JVM JIT inlined Redis into Tomcat.
    3. @Primary on Object always includes Redis.
    4. GC created it as a safepoint side effect.
    View Answer & Explanation

    Answer: A (Classpath + imports + matching conditions.)

  8. Q8: exclude = DataSourceAutoConfiguration.class means?

    1. That auto-config class is not imported.
    2. JDBC driver is deleted from the JDK.
    3. All @Repository beans become prototypes.
    4. Actuator health is forced down.
    View Answer & Explanation

    Answer: A (That auto-config class is not imported.)
