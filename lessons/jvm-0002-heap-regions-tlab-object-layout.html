Heap Regions, TLAB & Object Layout

~35 minutes · ties to mission · builds on S01 Runtime Architecture, Klass Word, Allocation Lifecycle, Mark Word

Senior Interview Focus: Can you explain why a REST handler allocating 10,000 short-lived DTOs per second is usually fine, but a 2 GB static cache is a different GC problem? Can you sketch an object's bytes on the heap — header, fields, padding — and say when compressed oops apply? This lesson connects generational theory to the physical layout you already met in OOP.

Primary sources: Oracle — GC Ergonomics · OpenJDK — Compressed Oops · Aleksey Shipilëv — Objects Inside-Out

1. Generational Heap Layout

HotSpot splits the Java heap into generations based on an empirical observation: most objects die young. Collecting only the young region is fast; scanning the entire heap every time would not scale.

┌─────────────────────────────── Java Heap (-Xmx) ───────────────────────────────┐
│  Young Generation                          │  Old Generation (Tenured)       │
│  ┌──────── Eden ────────┐ ┌─S0─┐ ┌─S1─┐    │  long-lived objects, promoted   │
│  │  new allocations     │ │    │ │    │    │  caches, singletons, pools     │
│  └──────────────────────┘ └────┘ └────┘    │                                 │
└────────────────────────────────────────────────────────────────────────────────┘
Region Role Typical ratio (ergonomic defaults)
Eden All new objects start here (via TLAB — below) Largest slice of Young
Survivor S0 / S1 Hold objects that survived at least one Young GC; only one active at a time during copy Small (often ~10% of Young each)
Old (Tenured) Objects that survived enough Young collections or were pre-tenured Grows until -Xmx cap

Young GC (Minor collection): scans Eden + active Survivor, copies live objects. STW but typically short. Detail in S03.

Old GC (Major / Mixed): scans Old generation. Slower, less frequent. Long-lived data dominates pause risk here.

2. Object Journey — Eden → Survivor → Old

  1. Allocation: new OrderDto() lands in Eden (usually inside caller thread's TLAB).
  2. Request ends: local references gone → object unreachable → dies in Eden. Next Young GC reclaims it — never copied.
  3. Survives one Young GC: copied from Eden (or from the inactive Survivor) into the other Survivor space. GC age in Mark Word incremented.
  4. Survives repeatedly: bounced between S0 and S1. Each survival bumps age.
  5. Promotion: when age reaches -XX:MaxTenuringThreshold (default 15, collector may lower dynamically) or Survivor is full, object moves to Old.
  6. Pre-tenuring: very large objects may skip Young entirely and go straight to Old (-XX:PretenureSizeThreshold — often ~50% of Young on some collectors).
Request lifecycle (typical REST handler):

  new DTO, new List, parse JSON  ──► Eden
  handler returns, refs dropped   ──► eligible
  Young GC                        ──► reclaimed (never promoted)

Singleton cache loaded at startup ──► Eden first
  survives many Young GCs         ──► S0 ↔ S1
  age threshold hit               ──► Old (stays until unreachable)

This is the bridge from Object Lifecycle: allocation is step 2; generational movement is what happens before step 5 (reclamation).

3. TLAB — Fast, Lock-Free new

In S01 you saw TLAB preview. Here is the mechanism:

  • Each application thread gets a private Thread-Local Allocation Buffer — a contiguous chunk carved from Eden.
  • Allocation inside TLAB = increment an offset pointer (bump-the-pointer). No lock. Nanoseconds.
  • TLAB exhausted → thread requests a new TLAB from Eden (brief synchronization) or falls back to shared slow path.
  • Objects larger than TLAB remaining space (or huge objects) may allocate outside TLAB / pre-tenure.
Senior sound bite: "Multi-threaded services stay fast because most new never contends on a global heap lock — each thread bumps its own TLAB in Eden."
Concept Detail
Why thread-safe without lock Only one thread writes into its TLAB slice; other threads have separate slices.
TLAB waste Last object in a TLAB may leave unusable slack; refilled on next allocation burst.
Tuning flags -XX:+UseTLAB (default on), -XX:TLABSize, -XX:ResizeTLAB — rarely touched in prod; know they exist.

4. Object Layout Deep Dive

You met headers in Class vs Object and java.lang.Object. On-heap layout (HotSpot, 64-bit, compressed oops on — typical prod):

┌──────────────── Object in Heap ────────────────┐
│ Mark Word          (8 bytes)                   │
│ Klass pointer      (4 bytes compressed)        │
│ instance fields    (primitives + ref slots)    │
│ padding            (align to 8-byte boundary)  │
└────────────────────────────────────────────────┘

4.1 Mark Word (8 bytes on 64-bit)

One word, multiplexed — meaning changes with object state:

State Mark Word holds (simplified)
Normal / unlocked GC age (4 bits), identity hashcode (lazy-computed, shifted), unused bits
Biased lock Thread ID of biased owner — fast path for uncontended synchronized
Thin lock Lock record pointer — lightweight contention
Fat lock Pointer to monitor structure — heavy contention
GC mark During collection, used for forwarding / mark bits

GC age — survival count used for promotion decisions. Identity hashcode — computed once on first hashCode() without override, then cached in Mark Word if space allows.

4.2 Klass pointer

Points to class metadata in Metaspace (vtable, field layout, type info). Enables getClass(), instanceof, virtual dispatch. With compressed class pointers, 4 bytes instead of 8.

4.3 Instance fields & padding

Fields laid out per class definition (reordering possible for packing). JVM pads object size to 8-byte alignment on 64-bit — affects "empty object = 16 bytes" interview answer.

4.4 Empty object size (interview)

Typical 64-bit HotSpot with compressed oops + compressed class pointers: Mark (8) + Klass (4) + padding (4) = 16 bytes for a plain empty instance.
Without compression: often 16 bytes header alone or more with alignment rules — always say "depends on JVM flags and JDK version."

5. Compressed Oops & Compressed Class Pointers

64-bit pointers are 8 bytes. Most heaps are < 32 GB — HotSpot can store 32-bit compressed references that encode offsets into the heap base.

  • -XX:+UseCompressedOops (default when heap ≤ ~32 GB) — 4-byte object references in headers and arrays.
  • -XX:+UseCompressedClassPointers — 4-byte Klass pointers (requires compressed oops on most configs).
  • Heap base — JVM maps a contiguous region; compressed ref + base = real address.
  • > 32 GB heap — compressed oops often disabled → larger headers, more memory per object, different tuning tradeoffs.
Interview: "Compressed oops let 64-bit JVM use 32-bit refs for heap pointers, cutting object header and array overhead — but typically only while heap stays under the ~32 GB compressed-oops range."

6. Array Layout vs Plain Objects

Arrays are objects too — special layout:

┌──────────────── Array Object ──────────────────┐
│ Mark Word                                      │
│ Klass pointer  (points to array class metadata)│
│ array length   (4 bytes)                       │
│ elements[0..n] (primitives or ref slots)       │
│ padding                                        │
└────────────────────────────────────────────────┘
Type Header overhead Per-element cost
int[] ~12–16 bytes + alignment 4 bytes per int (no per-element object)
Integer[] ~12–16 bytes + alignment 4-byte ref each → separate Integer object on heap (boxing cost)
Object[] ~12–16 bytes + alignment 4-byte compressed ref per slot; elements are separate objects

Senior trap: new byte[1_000_000] ≈ 1 MB + header — one array object. List<Byte> with boxing = millions of tiny objects → Young GC pressure.

7. False Sharing Preview

When two threads update different fields that land in the same CPU cache line (64 bytes typical), cores invalidate each other's caches — throughput collapse.

  • Not a GC issue — hardware + layout issue.
  • @Contended (JVM internal / sun.misc) pads hot counters; LongAdder stripes across cells.
  • Arrays of mutable longs used as per-thread counters packed tightly → classic false sharing.

Full perf module (M07) later. Know the term for interviews when discussing concurrent counters next to object headers.

8. Enterprise Framing — Young vs Old Pressure

Pattern Generation impact Prod symptom
Per-request DTOs, JSON nodes, stream intermediates Eden churn — die young Frequent short Young GC pauses (usually OK); high allocation rate
Spring singleton beans, connection pools, session caches Promote to Old Stable Old occupancy; Full GC risk if unbounded
Static ConcurrentHashMap cache without eviction Entries + keys in Old Old gen grows until Full GC or OOM — not a "Young GC tuning" fix
parallelStream() on large collections Spike of short-lived pipeline objects Eden spike; watch allocation rate + commonPool (M02/M03)
Loading entire DB result into List<Entity> Large object graphs in Old if retained Heap pressure, long GC pauses — paginate/stream from DB
On-call framing: "High Young GC frequency with low pause times often means healthy short-lived allocation — fix retention in Old, not Eden size, unless allocation rate is genuinely excessive."

9. Classic Mistakes

  • "More Eden = always better." Steals from Old; can increase promotion rate or Full GC risk.
  • Assuming boxing is free — each Integer is a full object (16+ bytes) vs 4 bytes in int[].
  • Ignoring array header — small arrays cost disproportionate overhead.
  • Disabling compressed oops on 8 GB heap — wastes memory for no benefit.
  • Tuning GC before fixing unbounded Old-gen cache — collector can't fix a leak.

Out of scope: full GC algorithms (S03), collector selection (S04), Metaspace/class loading (S06), escape analysis / scalar replacement detail (S07).

10. Revision Notes

  • Young = Eden + S0 + S1; Old = tenured long-lived objects.
  • Most objects die in Eden; survivors copy between Survivors then promote.
  • TLAB = per-thread Eden slice; bump-pointer, lock-free for most new.
  • Object = Mark Word + Klass + fields + padding; Mark holds GC age, hash, lock state.
  • Compressed oops = 4-byte refs when heap ≤ ~32 GB (typical).
  • Arrays add length field; primitive arrays dense, object arrays hold refs.
  • Request DTOs → Young churn; caches/singletons → Old pressure.

11. Reasoning Exercises

  1. Service allocates 50 MB/s of short-lived JSON parsing objects. Old gen stable. Problem?

    Answer

    Often no structural problem. High Young GC rate expected. Tune only if pause times violate SLO. Reduce allocation (parser reuse, streaming) if CPU spent in GC is too high.

  2. -Xmx40g on 64-bit. Compressed oops still on?

    Answer

    Likely disabled — above ~32 GB threshold. Object headers and refs grow; factor into capacity planning.

  3. Two-field class: long id and boolean flag. Why might object be 24+ bytes not 17?

    Answer

    16-byte header + 8-byte long + 1-byte boolean + padding to 8-byte alignment → 24 or 32 bytes depending on field order and JVM packing.

  4. Thread A and B each increment adjacent volatile long counters in one shared object. Low contention but slow. Cause?

    Answer

    False sharing — same cache line invalidated across cores. Not a lock issue. Stripe counters (LongAdder) or pad fields (M07).

12. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Default first allocation region for new object?

    1. Eden via thread TLAB.
    2. Old generation directly always.
    3. Metaspace next to class data.
    4. Survivor S0 before Eden always.
    View Answer & Explanation

    Answer: A (Eden via thread TLAB.)

    New instances start in Eden unless pre-tenured as humongous/large. TLAB provides fast thread-local bump allocation.

  2. Q2: Object survives third Young GC. Likely location?

    1. Active Survivor or promoting.
    2. Still only in Eden always.
    3. Code Cache as native copy.
    4. Stack frame of creator thread.
    View Answer & Explanation

    Answer: A (Active Survivor or promoting.)

    Live objects are copied from Eden/Survivor on each Young GC. After several survivals, promotion to Old is likely.

  3. Q3: TLAB main performance benefit?

    1. Avoid Eden lock on most news.
    2. Store static fields per thread.
    3. Skip garbage collection forever.
    4. Compress objects at alloc time.
    View Answer & Explanation

    Answer: A (Avoid Eden lock on most news.)

    Per-thread bump allocation in a private Eden slice removes global synchronization on the hot path.

  4. Q4: Mark Word stores which at unlock idle state?

    1. GC age and hash metadata.
    2. Full vtable method list copy.
    3. All instance field values.
    4. Bytecode of constructor body.
    View Answer & Explanation

    Answer: A (GC age and hash metadata.)

    Normal state uses Mark Word for age, identity hash, and later lock encoding under contention.

  5. Q5: -XX:+UseCompressedOops typical limit driver?

    1. Heap size near thirty-two GB.
    2. Thread count exceeds core count.
    3. Metaspace exceeds one gigabyte.
    4. Direct memory exceeds Xmx value.
    View Answer & Explanation

    Answer: A (Heap size near thirty-two GB.)

    Compressed oops encode 32-bit offsets into heap base; above ~32 GB heap they are usually disabled.

  6. Q6: int[1_000_000] vs million Integer objects?

    1. Array one object — far less overhead.
    2. Both use identical heap bytes.
    3. Array stores in Metaspace only.
    4. Boxed form has no extra headers.
    View Answer & Explanation

    Answer: A (Array one object — far less overhead.)

    Primitive array: one header + 4M bytes payload. Boxed: ~1M objects each with 16+ byte headers.
