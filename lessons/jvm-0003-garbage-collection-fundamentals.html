Garbage Collection Fundamentals

~35 minutes · ties to mission · builds on GC Roots & References, S02 Generations, Monitors

Senior Interview Focus: Interviewers probe whether you understand reachability (not "delete when null"), what a pause actually blocks, and why a cache in a static Map is a GC problem not a "memory leak in C sense." You should explain Minor vs Major GC, reference strengths with when the collector acts, and why p99 latency often matters more than average throughput for APIs.

Primary sources: Oracle — Java GC Introduction · Oracle — java.lang.ref · JVM Spec — GC Roots

1. Why GC Exists — Trade-offs

Approach Pros Cons
Manual (C/C++ free) Predictable dealloc timing; no collector pauses Use-after-free, double-free, leaks — security + stability risk at scale
Automatic (Java GC) Developer focuses on business logic; fewer dangling-pointer bugs Pause times, CPU overhead, non-deterministic reclamation timing

Java bets: developer productivity and safety beat perfect determinism. Your job in production is to shape allocation and retention so GC stays within SLO — not to micromanage every free.

2. Reachability from GC Roots

GC does not run when you assign null. It runs when memory pressure triggers a collection, then asks: is this object reachable from any GC root via strong references?

You covered roots in Object Lifecycle. Production-complete root set:

GC Root Example Why it matters
Thread stacks Local refs in active stack frames Request-scoped objects alive while handler runs
Static fields private static Map<K,V> CACHE Classic accidental retention — lives for JVM lifetime
JNI global refs Native code holding Java objects Native libs can pin objects invisible to Java code
Synchronized monitor refs Thread blocked in synchronized(obj) JVM keeps monitor object reachable while thread waits (Lesson 2)
Class loaders / JVM internals Loaded classes, JMX beans, some thread locals Metaspace + heap cross-links (S06 preview) 
void handle() {
    Order o = load();     // o reachable from stack root
    process(o);
}   // frame popped → o eligible unless retained elsewhere

static List<Order> LOG = new ArrayList<>();
LOG.add(o);             // now reachable from static root → never collected

Unreachable ≠ immediately freed. Eligible for collection on next GC cycle in that generation. Visibility to other threads is a separate JMM topic — see volatile & JMM; GC only cares about reference graph integrity at safepoint.

3. Reference Strengths — When the Collector Runs Each

Expand oop-0005 with collector timing (not finalize):

Strength Collected when Typical use
Strong Never while reachable from roots Normal fields, locals, collections
Soft (SoftReference) After heap is tight — collector clears soft refs before throwing OOM, usually after stronger refs processed Memory-sensitive caches (image thumbnails, parsed docs) — "keep until we need RAM back"
Weak (WeakReference) Next GC cycle when only weakly reachable — regardless of heap fullness WeakHashMap keys, canonicalization maps, class loader adjacency
Phantom (PhantomReference) After object finalized/deallocated — ref enqueued; get() always null Post-mortem cleanup via ReferenceQueue + Cleaner (off-heap resource release)
Interview ordering: Strong survives longest → Soft cleared under memory pressure → Weak at next GC → Phantom signals "object memory gone, run cleanup action."

4. GC Phase Vocabulary

All collectors compose variants of these ideas:

Phase What happens
Mark Traverse from roots; mark live objects
Sweep Reclaim unmarked space; may leave fragmentation
Compact Move live objects together; updates references; eliminates fragmentation
Copy Copy live objects to fresh region; abandon old region in one go — no sweep fragmentation

Copying vs Mark-Sweep-Compact

Strategy Where used Trade-off
Copying Young generation (Eden → Survivor) Fast when few survivors; needs spare space (from-space / to-space)
Mark-Sweep-Compact Old generation (classic) Works in place; compact phase is costly (longer pauses)

5. Stop-The-World vs Concurrent Phases

  • Stop-The-World (STW): all application mutator threads paused at safepoints. GC (or part of it) runs. Your API handlers literally stop making progress.
  • Concurrent: GC threads work while app threads run — with barriers/bookkeeping so app and collector don't corrupt the heap. Still usually has some short STW phases.

Pause = wall-clock time your service threads are frozen at safepoints. Metrics:

  • Throughput — % time app runs vs GC (batch jobs care)
  • Latency / p99 — tail pause hits slowest requests (APIs care)
Enterprise framing: A 50 ms average pause sounds fine until p99 is 800 ms during Mixed GC — that's user-facing timeout territory. Measure pause distribution, not just mean.

6. Generational Hypothesis (Bridge from S02)

Hypothesis: most objects die young; few survive long.

  • Collect Young often — small live set, copying collector, short pause.
  • Collect Old rarely — large graph, expensive mark/compact.
  • Promotion — survivors age in Survivor spaces then move Old (S02).

7. Minor GC vs Major / Full GC

Term Typical scope Frequency / pause
Minor / Young GC Eden + Survivors Often; usually milliseconds
Major GC Old generation Less often; can be hundreds of ms+
Full GC Entire heap + often class metadata cleanup Rare in healthy apps; long STW — incident signal

Naming caveat: logs vary by collector (G1 "Young" vs "Mixed" — S04). Fundamentals: know what generation is being collected and whether app threads paused.

Healthy API service pattern:

  Minor GC  ████░░░░████░░░░████   frequent, small pauses
  Major/Mixed GC  ░░░░█░░░░░░█░░░   occasional, watch p99
  Full GC  ░░░░░░░░░░░█░░░░░░░   rare — investigate

8. Safepoints — Why Threads Must Pause

From S01: GC must see a consistent reference graph. If threads moved references mid-copy, the heap corrupts.

  • JVM inserts safepoint polls in bytecode (loops, method returns, etc.).
  • At safepoint, thread stack roots are frozen and scannable.
  • Long counted loops without safepoint poll → "GC stuck waiting for thread" (rare but real in tight native/math loops).

Thread dumps, deoptimization, and some lock operations also use safepoints — GC isn't the only reason.

9. Classic Bugs

9.1 Accidental retention

  • Static collections — static List<Event> buffer never cleared; every event pinned until restart.
  • Inner class holding outer — non-static inner holds implicit this$0 → entire outer graph retained.
  • ThreadLocal leak (preview) — pool thread + ThreadLocal without remove() after request → previous request's graph stuck on thread. Brutal with Tomcat worker pools.
  • Listener registries — forgot to unregister callback on shutdown.

9.2 Premature promotion

Short-lived objects that survive one or two Young GCs due to timing (not true long-lived data) get promoted to Old. Old fills faster → more Major GC → longer pauses.

  • Cause: allocation burst + unlucky GC timing, Survivor too small, -XX:MaxTenuringThreshold too low.
  • Fix direction: reduce unnecessary retention in request path; tune Survivor/tenuring (S05) after proving with GC logs — not guesswork.

10. Enterprise — p99 Latency vs Throughput

Workload GC priority Why
REST / gRPC APIs Low pause (p99, p999) STW pause = stalled request; SLA breach on tail
Batch ETL / report generation Throughput Total jobs/hour; occasional long pause OK if bounded
Real-time pricing / gaming Hard pause ceiling Sub-10 ms pauses may matter — collector choice critical (S04)

What seniors monitor: GC pause times (p99), allocation rate, promotion rate, Old gen occupancy trend, Full GC count. Alert on Full GC frequency, not every Minor GC.

Out of scope: G1 vs ZGC comparison (S04), flag cookbook (S05), heap dump walkthrough (S08). JMM visibility — concurrency-0003 only.

11. Revision Notes

  • GC reclaims unreachable objects, not "null" objects on demand.
  • Roots: stacks, statics, JNI, monitors, JVM internals.
  • Strong → Soft (memory pressure) → Weak (next GC) → Phantom (post-death queue).
  • Mark / sweep / compact / copy — building blocks of all collectors.
  • STW = app frozen; concurrent reduces but rarely eliminates pauses.
  • Minor = Young; Major/Full = Old / whole heap — watch p99 not just average.
  • Safepoints freeze stacks for consistent root scan.
  • Static maps + ThreadLocal = classic retention; premature promotion fills Old.

12. Reasoning Exercises

  1. WeakHashMap used for session cache keyed by user. User logs out, no other refs. When is entry collected?

    Answer

    Key held via weak reference. Next GC when key only weakly reachable — entry can be reclaimed. Not instant on logout; on next GC cycle. For immediate eviction, remove explicitly or use TTL cache (Caffeine).

  2. Minor GC every second, 5 ms pause. Old gen flat. API p99 stable. Action?

    Answer

    Often none. Healthy short-lived allocation pattern from S02. Optimize only if GC CPU % too high or pauses grow. Don't chase Minor GC count alone.

  3. Thread pool worker holds ThreadLocal<Map> with request context, never remove(). Symptom?

    Answer

    Each reused thread retains prior requests' maps → Old gen grows, effective leak. Fix: finally { threadLocal.remove(); } or scoped context (VT era: prefer explicit propagation).

  4. SoftReference cache of 500 MB images. Heap fills. What happens before OOM?

    Answer

    GC clears soft references to reclaim memory — cache entries dropped progressively. OOM only if even after clearing soft refs there isn't enough heap for new strong allocations.

13. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Object eligible for GC when?

    1. No strong path from any root.
    2. Variable assigned null immediately.
    3. Method that created it returns only.
    4. finalize method has never run yet.
    View Answer & Explanation

    Answer: A (No strong path from any root.)

    Reachability defines life. null and method return are common ways to break reachability, but collection happens later on GC cycle.

  2. Q2: WeakReference to object. Only weak refs remain. When collected?

    1. Next GC cycle regardless of heap.
    2. Only when heap is nearly full.
    3. Never until JVM shutdown.
    4. Immediately on last strong drop.
    View Answer & Explanation

    Answer: A (Next GC cycle regardless of heap.)

    Weak refs are cleared aggressively at GC. Soft refs wait for memory pressure.

  3. Q3: Young GC typically uses which strategy?

    1. Copy live objects to Survivor.
    2. Compact entire Old generation.
    3. Sweep Metaspace class bytes.
    4. Flush thread stacks to disk.
    View Answer & Explanation

    Answer: A (Copy live objects to Survivor.)

    Young gen copying collector exploits few survivors. Old gen uses mark-sweep-compact variants.

  4. Q4: Stop-the-world pause means what for API thread?

    1. Thread frozen at safepoint.
    2. Only GC threads stop running.
    3. Network sockets auto-close always.
    4. Heap is expanded without lock.
    View Answer & Explanation

    Answer: A (Thread frozen at safepoint.)

    Mutators pause so roots and heap are consistent. Request latency includes pause time.

  5. Q5: static HashMap grows forever in service. GC issue?

    1. Accidental retention from static root.
    2. WeakReference on every key by default.
    3. Objects move to Code Cache area.
    4. Minor GC cannot run while map exists.
    View Answer & Explanation

    Answer: A (Accidental retention from static root.)

    Static field is a GC root. All reachable entries stay alive — looks like leak, is retention.

  6. Q6: Backend API SLO on p99 latency. Metric first?

    1. GC pause p99 not average only.
    2. Young GC count per minute only.
    3. Total heap bytes allocated ever.
    4. Number of loaded classes only.
    View Answer & Explanation

    Answer: A (GC pause p99 not average only.)

    Tail pauses drive tail latency. Mean pause hides Mixed/Full GC spikes.
