Actuator, Health, Metrics & Production Configuration

~30 minutes · Module 05 Lesson 8 of 9 · builds on JVM diagnostics, conditions

Senior Interview Focus: Observability is how you keep a JVM service honest in K8s. Can you map liveness vs readiness to probes, name which Actuator endpoint you hit first on a latency spike, and say what must never be public? Actuator is the app view; jcmd/JFR is the JVM view — both.

Primary sources: Spring Boot Actuator · Endpoints · Metrics

1–2. Why Observability; What Actuator Is

Without signals you guess. Actuator exposes HTTP/JMX endpoints and wires Micrometer meters. It is a Boot feature (auto-config), not a replacement for logs or traces.

3. Endpoints (What Each Is For)

Endpoint Question it answers
/health Should this instance take traffic / is process alive?
/info Build version, git commit — deploy verification
/metrics Named meters (JVM, Tomcat, Hikari, HTTP)
/loggers Runtime log level (dangerous if public)
/threaddump Same idea as jstack — app-level dump
/heapdump hprof — huge, sensitive, last resort
/conditions Auto-config report (S05)
/beans /env /configprops Wiring and property values — secrets risk

4. Exposure — Never Public Full Actuator

Must know: By default web exposure is limited (health often). Do not include=* on the public 8080. Pattern:

  • management.server.port=8081 — not on the LoadBalancer
  • NetworkPolicy: only kubelet / Prometheus scrape
  • Auth on sensitive endpoints if the port is reachable

/env and /heapdump on the internet = incident.

5–7. Health, Liveness, Readiness, K8s

Liveness  → kubelet: restart the container if deadlocked / stuck
Readiness → Service: remove from LB if cannot accept traffic (warming, downstream down)

Boot 2.3+: /health/liveness and /health/readiness (or groups). Custom HealthIndicator for “can I reach Redis?” — usually readiness, not liveness (don’t restart-loop because Redis blipped).

Trap: liveness pinging the database → DB outage = crashloop. Liveness = process health. Readiness = dependency health.

8–10. Micrometer

Meters (counters, timers, gauges) → registry (Prometheus, OTLP, …). You don’t implement scrape format by hand.

Metrics that matter:

  • HTTP latency / error rate (server requests)
  • JVM memory, GC pause (ties Module 04)
  • Tomcat threads busy / max
  • Hikari: active, pending, timeout
@Timed("checkout.place")
public OrderId place(PlaceOrder cmd) { ... }

// or
registry.counter("payments.failed", "provider", "stripe").increment();

Nice to know: Cardinality explosion (per-user tags) kills Prometheus. Tag bounded sets only.

11–12. Production Config & Secrets

  • Profiles: prod in the cluster only
  • Env vars / K8s Secret / Vault — not git
  • Externalized config (S04) — 12-factor

13. Incident: Latency Spike — First Moves

1. HTTP metrics: p99, error ratio, in-flight
2. Hikari pending / Tomcat busy  → pool story (S07)
3. /threaddump or jcmd Thread.print  → BLOCKED vs socketRead (JVM S08)
4. GC metrics — if CPU in GC, Module 04 path
5. Do not heapdump first on a giant heap under load

14. Actuator vs jcmd

Actuator: needs HTTP, security, may miss native deadlocks if the web thread pool is stuck. jcmd from the pod: works if the JVM still answers attach. Seniors use both.

Production Relevance

Probes misconfigured = rolling deploy never becomes Ready, or pods killed during GC pause (liveness timeout too aggressive). Heapdump endpoint left open = PII on the internet.

Interview Articulation

“Actuator exposes health and metrics. Liveness is ‘restart me’; readiness is ‘stop sending traffic.’ I scrape Micrometer via a private management port. On latency I look at HTTP timers, thread and connection pool gauges, then a thread dump. Heapdump and /env stay locked down. JVM tools remain valid when HTTP is already dead.”

Revision Notes

  • Management port + least exposure.
  • Liveness ≠ dependencies.
  • Hikari + Tomcat + HTTP timers.
  • Conditions endpoint debugs S05.
  • Actuator + jcmd complementary.

Interview One-Liners

  • “Restart loops from a DB health check are a liveness mistake.”
  • “include=* on 8080 is a finding, not a convenience.”
  • “Metrics first, dumps second, heapdump last.”

Senior MCQs

  1. Q1: Redis down. Which probe should fail?

    1. Readiness — stop traffic, don’t crashloop.
    2. Liveness — kubelet must always restart.
    3. Neither — hide all health endpoints.
    4. Only heapdump should turn red.
    View Answer & Explanation

    Answer: A (Readiness — stop traffic, don’t crashloop.)

  2. Q2: Safe public exposure?

    1. Minimal health — never env/heapdump on 8080.
    2. include=* on the LoadBalancer port.
    3. /loggers open without auth globally.
    4. /beans to the whole internet always.
    View Answer & Explanation

    Answer: A (Minimal health — never env/heapdump on 8080.)

  3. Q3: First metric family on API latency spike?

    1. HTTP timers plus pool/thread gauges.
    2. Only Metaspace class count.
    3. Git commit hash from /info.
    4. Disk UUID of the container image.
    View Answer & Explanation

    Answer: A (HTTP timers plus pool/thread gauges.)

  4. Q4: /actuator/conditions helps debug?

    1. Why auto-config beans appeared or not.
    2. Native thread creation in the kernel.
    3. G1 region size exclusively.
    4. Whether records are on the heap.
    View Answer & Explanation

    Answer: A (Why auto-config beans appeared or not.)

  5. Q5: HTTP actuator dead, JVM alive. Next?

    1. jcmd from the pod — attach still works.
    2. Only retry /heapdump on 8080.
    3. Disable GC to free the servlet pool.
    4. Restart etcd in the cluster first.
    View Answer & Explanation

    Answer: A (jcmd from the pod — attach still works.)

  6. Q6: High-cardinality userId tags on timers?

    1. Dangerous — explodes time series.
    2. Required for Micrometer to work.
    3. Replaces the need for logs.
    4. Forces CGLIB off globally.
    View Answer & Explanation

    Answer: A (Dangerous — explodes time series.)
