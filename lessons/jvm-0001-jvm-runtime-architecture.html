JVM Runtime Architecture & Memory Areas

~30 minutes · ties to mission · builds on Stack vs Heap, Class in Metaspace, Threads Share Heap

Senior Interview Focus: Interviewers expect you to map a running Spring Boot pod to concrete JVM structures — not recite textbook diagrams. Can you explain what docker stats / cgroup memory includes vs what -Xmx caps? Where do class definitions live vs object instances? Why is a heap OOM fix different from Metaspace or direct-buffer OOM? This lesson stitches together what you already learned in OOP and Concurrency into one production mental model.

Primary sources: Oracle — java launcher (SE 21) · JVM Spec — Runtime Data Areas · Oracle — GC Ergonomics (memory pools)

1. JDK vs JRE vs JVM — What Actually Runs in Prod

Component What it is Prod relevance
JVM The virtual machine: bytecode interpreter + JIT + GC + thread scheduler + memory manager This is the process. One JVM instance per typical Java service container.
JRE JVM + core class libraries (rt.jar era; now modular jmods on the module path) Historical term. Modern deployments ship a JRE subset or full JDK inside the image.
JDK JRE + developer tools (javac, jlink, jcmd, jmap, etc.) Build stage uses full JDK. Runtime image often uses jlink-trimmed runtime or distroless JRE.

Container reality: Kubernetes sees one OS process — usually java -jar app.jar or a shell wrapper around it. That process is the JVM. cgroup memory limit must cover:

  • Java heap (-Xmx)
  • Metaspace (class metadata — not in -Xmx)
  • Thread stacks (platform threads × stack size; virtual threads are much cheaper)
  • Code Cache (JIT-compiled native code)
  • Direct / native memory (NIO direct buffers, Netty, JNI, compression dictionaries)
  • JVM native overhead (GC structures, card tables, etc.)
Senior trap: setting -Xmx to 100% of container limit guarantees OOMKill. Leave headroom for off-heap areas — rule of thumb 25–40% below cgroup cap depending on stack count and Netty usage.

Layer Count in typical microservice Notes
OS process 1 per pod/container (usual case) Crash = pod restart. kill -9 = hard stop, no GC cleanup.
JVM instance 1 per process Owns all memory pools below. One GC subsystem, one Metaspace (per class loader tree).
Application threads Many (Tomcat workers, pool threads, GC threads, JIT compiler threads) Share heap + Metaspace. Each has private stack. Races = unsynchronized heap writes.

Production threads you'll see in a thread dump:

  • http-nio-8080-exec-N — servlet request workers
  • pool-N-thread-M — your ExecutorService
  • ForkJoinPool.commonPool-worker-N — parallel streams
  • GC Thread#N — garbage collector workers
  • C1/C2 CompilerThreadN — JIT tiers (detail in S07)
  • VM Thread — safepoint coordination (below)

All of them share the same heap. That's why HashMap in a singleton Spring bean is everyone's problem.

3. Runtime Memory Areas — The Full Map

From Lesson 3 (OOP) you know stack vs heap. Here is the complete HotSpot map senior engineers keep in their head:

Area Scope Stores Grows / reclaimed by
Heap Shared (all threads) Object instances, arrays -Xms / -Xmx. GC reclaims unreachable objects (S03).
Stack (per thread) Private per thread Stack frames, local primitives, reference slots Fixed per thread (-Xss). Popped on method return — no GC.
Metaspace Shared (class loaders) Class metadata, method bytecode, vtables, static fields Native memory. Grows until class loaders collected (S06). -XX:MaxMetaspaceSize.
Code Cache Shared JIT-compiled machine code Native. -XX:ReservedCodeCacheSize. Swept when full.
Direct / Native memory Shared (process) NIO direct buffers, Netty pooled buffers, JNI allocations Not in heap. Limited by -XX:MaxDirectMemorySize (default ≈ -Xmx).
PC Registers Per thread Current bytecode instruction address JVM-managed, tiny — rarely discussed in interviews.

Heap generations (preview for S03): Young (Eden + Survivor) + Old. Most objects die young. Long-lived caches, singletons, session state → Old. TLABs live inside Eden.

                    │ class metadata  │
                    │ static fields   │

                             │ Klass pointer
┌──────────── Heap ──────────┼──────────────────────────┐
│  Young (Eden + S0 + S1)    │   Old Generation         │

4. What Lives Where — Primitives, References, Statics

Reconcile Class vs Object with the full map:

Thing Where Interview one-liner
Local int x = 5 Stack frame (actual value) Value lives in the frame; dies when method returns.
Local String s = "hi" Reference on stack → object on heap Variable is a pointer slot; "hi" may be in string pool on heap.
Instance field private int age Inside object on heap Even primitives inside objects are heap-resident.
static int count Metaspace (with class metadata) One copy per class loader, not per instance.
static final List<T> CACHE Static reference in Metaspace → List object on heap Reference slot in Metaspace; the list and its elements are heap objects.
Class definition / bytecode Metaspace Loaded once per class loader. java.lang.Class is a heap mirror.
Method local array new int[1000] Heap (arrays are objects) Reference may be on stack; array body always heap.

Trace exercise

public class OrderService {
    private static final Map<Long, Order> CACHE = new ConcurrentHashMap<>();

    public Order find(long id) {
        int retries = 3;                          // (A)
        Order cached = CACHE.get(id);             // (B)
        if (cached == null) {
            Order fresh = repository.load(id);    // (C)
            CACHE.put(id, fresh);
            return fresh;
        }
        return cached;
    }
}

Reasoning (cover answers, then check):

  1. (A) retries — stack (primitive local).
  2. (B) cached reference — stack; CACHE static ref — Metaspace; ConcurrentHashMap object + entries — heap.
  3. (C) fresh reference — stack; Order instance — heap.

5. TLAB Preview — Why Allocation Is Fast

Every new hitting a global Eden lock would bottleneck multi-threaded services. HotSpot gives each thread a Thread-Local Allocation Buffer (TLAB) — a small private slice of Eden.

  • Allocation inside TLAB = bump-the-pointer (move an offset) — no lock, nanoseconds.
  • TLAB full → thread gets a new TLAB or allocates slowly in shared Eden.
  • Very large objects may bypass TLAB and go straight to Old (threshold: -XX:PretenureSizeThreshold).

You already met TLABs in Stream Fundamentals (short-lived pipeline objects). Full mechanics — sizing, waste, tuning — in S02 (Object Allocation).

Interview sound bite: "Most ephemeral objects never contend on a global heap lock because TLABs make allocation mostly thread-local bump-pointer."

6. Safepoints & Stop-The-World Preview

The JVM must pause application threads at well-defined moments to:

  • Run GC root scanning and compaction (S03)
  • Deoptimize / recompile hot methods (S07)
  • Dump threads (jcmd Thread.print, kill -3)
  • Revoke biased locks, walk stacks for roots

A safepoint is a bytecode location where the thread can safely stop and expose a consistent stack/heap view. Between safepoints, a thread may be mid-method.

Stop-The-World (STW): all mutator threads blocked at safepoints while VM work runs. Short STW pauses (milliseconds) are normal; multi-second STW = production incident (S03–S05).

Thread dump connection: When you capture a dump, each thread's stack trace is a snapshot at a safepoint. That's why all threads show a coherent state — and why "RUNNABLE" in a dump doesn't mean "on-CPU right now" (it can mean runnable-but-not-yet-scheduled).

Thread-1: RUNNABLE at Safepoint
  at com.app.OrderService.find(OrderService.java:42)
  ...

GC Thread#2: RUNNABLE
  at GC work...

Concurrent collectors (G1, ZGC) reduce but don't always eliminate STW phases. Detail in S03.

7. Enterprise OOM Triage — Three Different Beasts

Senior on-call skill: read the exception class and message — fixes are not interchangeable.

Error Typical message What ran out Common causes Fix direction
Heap OOM Java heap space -Xmx heap Memory leak, unbounded cache, huge collections, loading too much data per request Heap dump / MAT (S08), fix retention, paginate, raise -Xmx only after proving need
Metaspace OOM Metaspace / class metadata Class metadata area Classloader leak (hot redeploy, dynamic proxies, Groovy/bytecode gen), too many class loaders Find leaking loader, limit generated classes, -XX:MaxMetaspaceSize as guardrail not cure
Direct buffer OOM Direct buffer memory Off-heap direct memory Netty, NIO, gRPC, large off-heap buffers without release Pool sizing, leak detection, -XX:MaxDirectMemorySize, fix missing release()
Unable to create native thread unable to create native thread OS thread / stack budget Unbounded new Thread(), thread pool misconfig, ulimit Bounded executors, virtual threads for I/O, lower -Xss, raise ulimit
StackOverflowError Stack overflow Thread stack depth Infinite recursion, very deep XML/JSON parsing Fix recursion, streaming parser — not a heap problem
On-call scenario: Pod OOMKilled by Kubernetes but no Java heap dump. cgroup killed the process because total memory (heap + metaspace + direct + stacks + native) exceeded limit — even if -Xmx looked fine. Check container limit vs -Xmx headroom first.

8. Classic Production Mistakes

  • "We raised -Xmx to fix Metaspace OOM." Wrong pool. Classes kept generating; heap change irrelevant.
  • "Heap is 70% used so we're fine." Ignores direct memory spike during Netty upgrade.
  • Static Map cache without bounds — heap leak disguised as "performance optimization."
  • Assuming primitives are "light" on heap — a new int[50_000_000] is ~200 MB on heap regardless.
  • Thread dump shows BLOCKED everywhere — heap healthy but thread starvation; not a GC lesson (concurrency module).

Out of scope (later sections): collector algorithms (S03–S04), full GC tuning flags (S05), classloader delegation (S06), JIT tiers (S07), MAT heap dump walkthrough (S08).

9. Revision Notes

  • Prod container runs one JVM process — not "the JDK."
  • Many threads, one shared heap + Metaspace; stacks are private.
  • Locals/refs on stack; objects on heap; statics in Metaspace (object refs point to heap).
  • TLAB = fast thread-local Eden allocation; detail in S02.
  • Safepoints enable GC, JIT, thread dumps; STW = all threads paused.
  • Heap OOM ≠ Metaspace OOM ≠ direct OOM — read the message, fix the right pool.

10. Reasoning Exercises

  1. Microservice pod limit 512 MiB. You set -Xmx512m. Healthy?

    Answer

    No. Metaspace, thread stacks, Code Cache, and direct memory also consume cgroup budget. JVM will be OOMKilled. Target ~60–75% of limit for -Xmx unless you have precise off-heap measurements.

  2. After redeploying 200 times without restart, Metaspace grows monotonically. Heap stable. Leak?

    Answer

    Likely classloader leak — old loaders not collectable because something still references them. Classic hot-reload / agent / dynamic codegen pattern. Not a heap leak.

  3. Thread dump shows 400 http-nio-exec threads all RUNNABLE at socketRead0. Heap 40%. Problem?

    Answer

    Not heap. Threads blocked in I/O — downstream slowness or missing timeouts. Fix latency/backpressure; virtual threads may help (M03 L8). GC tuning won't help.

  4. static final byte[] BUFFER = new byte[1_000_000] — where does the byte array live?

    Answer

    Static reference in Metaspace; byte array object on heap. One array shared by all instances under that class loader.

11. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Docker cgroup OOMKill with -Xmx at 70% of limit. Likely cause?

    1. Off-heap exceeded remaining budget.
    2. Heap alone always equals cgroup.
    3. JVM ignores container limits always.
    4. Only Code Cache uses off-heap.
    View Answer & Explanation

    Answer: A (Off-heap exceeded remaining budget.)

    Metaspace, stacks, direct buffers, and native GC structures sit outside -Xmx. Total process RSS must fit the cgroup.

  2. Q2: Where does static reference field store its pointer?

    1. Metaspace with class metadata.
    2. Inside each instance on heap.
    3. On the main thread stack only.
    4. Code Cache next to JIT code.
    View Answer & Explanation

    Answer: A (Metaspace with class metadata.)

    Static fields live with the class definition. The referenced object itself is on the heap.

  3. Q3: TLAB primary benefit in multi-threaded service?

    1. Avoid global Eden lock on most news.
    2. Store static fields per thread.
    3. Replace garbage collection entirely.
    4. Move all objects to Old gen faster.
    View Answer & Explanation

    Answer: A (Avoid global Eden lock on most news.)

    TLABs let threads allocate via bump-pointer in a private Eden slice. Full sizing in S02.

  4. Q4: Thread dump taken during GC safepoint. What is true?

    1. Stacks are consistent snapshot points.
    2. Threads mid-bytecode show half frames.
    3. Only RUNNABLE threads appear.
    4. Heap contents printed inline always.
    View Answer & Explanation

    Answer: A (Stacks are consistent snapshot points.)

    Safepoints freeze mutators at safe locations so VM can walk stacks. That's why dumps are coherent.

  5. Q5: OutOfMemoryError: Metaspace. First sensible action?

    1. Investigate classloader retention.
    2. Double -Xmx heap immediately.
    3. Disable garbage collection.
    4. Shrink thread stack -Xss only.
    View Answer & Explanation

    Answer: A (Investigate classloader retention.)

    Metaspace stores class metadata. Leaked loaders or unbounded dynamic class generation are the usual suspects — not heap size.

  6. Q6: Local int x = 42 inside running method. Location?

    1. Current thread stack frame.
    2. Heap next to object header.
    3. Metaspace with static data.
    4. Direct buffer off-heap area.
    View Answer & Explanation

    Answer: A (Current thread stack frame.)

    Primitive locals live in the stack frame's local variable array. Instance field primitives live inside heap objects.
