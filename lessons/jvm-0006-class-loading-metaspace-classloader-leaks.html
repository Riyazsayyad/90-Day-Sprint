Class Loading, Metaspace & Classloader Leaks

~35 minutes · ties to mission · builds on S01 Metaspace, static & clinit, Init Order, S05 MaxMetaspaceSize

Senior Interview Focus: Can you walk through class loading phases and say exactly when <clinit> runs? Can you explain why redeploying a WAR 200 times without restart blows Metaspace — and why raising -Xmx won't help? Know delegation, when SPI breaks it, and the three classic classloader leak patterns (ThreadLocal, JDBC drivers, redeploy).

Primary sources: JVM Spec — Loading, Linking, Initialization · Oracle — ClassLoader · Oracle — Class Loaders

1. Class Loading Phases

Before any new Foo(), the JVM must load class Foo. Three high-level phases:

Phase What happens Interview note
Loading Find bytecode (.class / JAR), define Klass structure in Metaspace, create java.lang.Class mirror on heap Binary name → bytes → metadata
Linking Verify bytecode safety · Prepare static fields (defaults, no user code) · Resolve symbolic refs (may be lazy) Verification is not "run your static block" yet
Initialization Execute <clinit> — static field assignments + static blocks in source order First active use triggers this (below)

Parent class initialized before child. Interfaces initialized when a class implementing them is initialized (rules have edge cases — parent-first is the safe interview answer).

2. When <clinit> Runs — Tie to Static Blocks

From static lesson: static blocks compile into one <clinit> method. Runs once per class per defining class loader.

Triggers initialization (first active use):

  • new MyClass() — instance creation
  • Access static field declared in class (not inherited without override confusion)
  • Invoke static method declared in class
  • Class.forName("com.app.Config") — with initialization (default)
  • Reflection on class for first time in certain operations

Does NOT trigger child init alone:

  • Creating array new MyClass[10] — loads MyClass but does not run <clinit>
  • Accessing static field that is compile-time constant (static final primitive or String literal) — may be inlined without loading class
public class Config {
    static { System.out.println("clinit"); }  // runs once on first active use
}

// First call prints "clinit":
Config.getUrl();

// Array — no clinit:
Config[] arr = new Config[10];

Failed <clinit> → ExceptionInInitializerError; later use → NoClassDefFoundError.

3. Classloader Hierarchy & Delegation

Bootstrap (null in Java API)  — rt/java.base, core JDK classes
        ↑
Platform (Extension)        — JDK modules / endorsed libs
        ↑
Application (System)        — your classpath / -cp / JAR
        ↑
Custom loaders              — Tomcat Webapp, Spring nested JAR, OSGi bundle

Delegation model (default): child asks parent to load first. Parent can't → child tries. Ensures java.lang.String always comes from bootstrap — security + single definition.

Loader Loads
Bootstrap java.*, core modules — C++ inside JVM; ClassLoader.getParent() returns null
Platform JDK modules not in bootstrap (historical "extension")
Application Your app classpath — ClassLoader.getSystemClassLoader()
Custom Per-deploy unit — Tomcat WebappClassLoader, plugin frameworks

4. Breaking Delegation — SPI & Fat JARs

Default delegation fails when parent needs classes implemented by child:

  • Service Provider Interface (SPI): ServiceLoader — JDBC drivers, logging backends. Parent API (java.sql.Driver) in bootstrap; implementation in app JAR. META-INF/services/ registration.
  • Spring Boot fat JAR: nested JARs use custom LaunchedURLClassLoader — parent-last or modified delegation so app libs don't clash with embedded container. Deep internals → M05; interview: "Boot doesn't use plain AppClassLoader on flat classpath."
  • OSGi / JPMS (awareness): module boundaries and explicit exports break naive single hierarchy — know name for interview breadth.

5. Class.forName vs ClassLoader.loadClass

API Initialization? Typical use
Class.forName("com.foo.Bar") Yes — runs <clinit> JDBC Class.forName(driver) — register driver static block
Class.forName(name, false, loader) No if second arg false Load without triggering static init
loader.loadClass("com.foo.Bar") No — link only, defer init Frameworks that want control over init timing
Interview trap: "loadClass and forName are the same" — false. forName initializes by default; loadClass does not.

6. Metaspace vs PermGen (Pre-Java 8)

PermGen (Java 7−) Metaspace (Java 8+)
Location Fixed region inside JVM heap Native memory — not in -Xmx
Growth Fixed max — -XX:MaxPermSize Grows with loaded classes; -XX:MaxMetaspaceSize cap
OOM message PermGen space Metaspace
Interview story "Hot redeploy + class versions = PermGen OOM" Same leak pattern — different pool name

Metaspace fixed the "tiny fixed PermGen" problem but did not fix classloader leaks. Unlimited growth → cgroup OOMKill if no MaxMetaspaceSize.

7. Classloader Leaks — Classic Patterns

A classloader is collectible only when no strong references to it exist and all its loaded classes are unreachable. Leaks pin the entire loader graph + all its classes in Metaspace.

7.1 Redeploy without restart

Tomcat / app server creates new WebappClassLoader per deploy. Old loader should die. If something still references old loader → old classes never unloaded → Metaspace stair-steps up each deploy.

7.2 ThreadLocal + loaded class

// Request filter sets ThreadLocal holding UserContext from webapp classloader
threadLocal.set(new UserContext());

// Pool thread reused — never threadLocal.remove()
// Thread holds ref → ThreadLocalMap → Value → Class from OLD loader

Brutal in servlet thread pools. Fix: finally { threadLocal.remove(); }. Virtual threads: same discipline (M03 L8).

7.3 JDBC driver registration

Legacy pattern: driver JAR static block registers with DriverManager (held by bootstrap/system refs). Redeploy loads new driver class; old driver + loader pinned.

Modern: JDBC 4+ SPI (META-INF/services/java.sql.Driver) + DriverManager.deregisterDriver on shutdown; use connection pool that manages lifecycle.

7.4 Other common pins

  • Custom shutdown hooks referencing webapp classes
  • Static singletons in container scope referencing old context
  • Thread started by old deployment still running
  • APM / Hibernate bytecode agents holding transformed class refs

8. When Can a ClassLoader Be GC'd?

  1. No strong references to the ClassLoader instance
  2. No strong references to any Class objects it defined
  3. No threads have stack frames executing methods from those classes
  4. All instances of loaded classes unreachable

Metaspace for that loader's metadata reclaimed when loader is collected — not before. This is why one stray ThreadLocal can retain megabytes of class metadata.

9. Enterprise Patterns

Scenario Classloading impact Practice
Spring Boot fat JAR Custom loader, nested JARs, many classes at startup Accept one-time Metaspace footprint; avoid duplicate agent instrumentation
Dev hot-reload (Spring DevTools, JRebel) Reloads classes / loaders frequently Dev-only; restart periodically; never compare dev Metaspace to prod
Prod Stable loader tree No redeploy-without-restart on long-lived pods — roll new pod instead (K8s)
Hibernate / bytecode enhancement Runtime-generated subclasses (proxies) More classes in Metaspace; monitor MaxMetaspaceSize
APM agents (Datadog, New Relic) Instrument every loaded class Agent overhead + Metaspace; align agent version with JDK

K8s framing: immutable deployments → new pod = fresh JVM = clean loaders. Metaspace leaks from redeploy are a **app-server-on-long-lived-JVM** smell more than stateless K8s — but ThreadLocal + pool threads still bite everywhere.

Out of scope: bytecode verification algorithms, ASM/Javassist, deep LaunchedURLClassLoader (M05), JPMS encyclopedia.

10. Revision Notes

  • Load → link (verify, prepare, resolve) → init (<clinit>).
  • Init on first active use; arrays don't run clinit.
  • Bootstrap → Platform → Application; parent delegation default.
  • SPI / fat JAR break naive delegation.
  • forName initializes; loadClass does not.
  • PermGen story = Metaspace story with different pool name.
  • Leaks: redeploy, ThreadLocal, JDBC drivers, long-lived threads.
  • Loader GC'd only when zero strong refs to loader + its classes.

11. Reasoning Exercises

  1. Class.forName("com.mysql.cj.jdbc.Driver") in static app init. Side effect?

    Answer

    Runs driver <clinit> — registers with DriverManager. Needed for legacy explicit load; JDBC 4+ SPI often makes this unnecessary.

  2. 200 Tomcat redeploys, Metaspace 2 GB, heap stable. Cause?

    Answer

    Classloader leak — old WebappClassLoader instances pinned. Find ThreadLocal, threads, DriverManager, shutdown hooks. Restart JVM or fix leak; -Xmx irrelevant.

  3. new Config[100] — does Config clinit run?

    Answer

    No. Array creation loads class for element type but does not initialize it. No static blocks execute.

  4. Child class first accessed. Parent clinit order?

    Answer

    Parent <clinit> runs first, then child. Superclass static state ready before subclass static init.

12. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Static block runs in which loading phase?

    1. Initialization after linking.
    2. Loading before bytes read.
    3. Verify step of linking only.
    4. Every new object constructor.
    View Answer & Explanation

    Answer: A (Initialization after linking.)

    Static blocks compile to <clinit> executed during class initialization, not during load or verify alone.

  2. Q2: Default classloader delegation order?

    1. Parent asked to load first.
    2. Child always loads before parent.
    3. Bootstrap loads application classes.
    4. No hierarchy on JDK twenty-one.
    View Answer & Explanation

    Answer: A (Parent asked to load first.)

    Child delegates up so core JDK classes have single bootstrap definition.

  3. Q3: loadClass vs forName default difference?

    1. forName runs clinit by default.
    2. loadClass always runs clinit first.
    3. Both skip initialization always.
    4. forName only works for arrays.
    View Answer & Explanation

    Answer: A (forName runs clinit by default.)

    ClassLoader.loadClass resolves without initializing. Class.forName(name) initializes unless initialize flag is false.

  4. Q4: Java eight plus class metadata lives in?

    1. Metaspace native memory area.
    2. Fixed PermGen inside heap.
    3. Eden young generation only.
    4. Per-thread stack frames only.
    View Answer & Explanation

    Answer: A (Metaspace native memory area.)

    PermGen removed in Java 8. Metaspace is off-heap; capped with MaxMetaspaceSize.

  5. Q5: Classic redeploy Metaspace leak cause?

    1. Old classloader still referenced.
    2. Heap Xmx set far too low.
    3. Too many Eden TLAB slices.
    4. Compressed oops disabled only.
    View Answer & Explanation

    Answer: A (Old classloader still referenced.)

    Pinned loader retains all its class metadata. ThreadLocal and JDBC registration are frequent culprits.

  6. Q6: new Foo[50] triggers Foo clinit?

    1. No — array creation skips init.
    2. Yes — same as new Foo().
    3. Only if Foo has static block.
    4. Only on JDK eight and older.
    View Answer & Explanation

    Answer: A (No — array creation skips init.)

    Array creation loads the element class but does not run static initialization.
