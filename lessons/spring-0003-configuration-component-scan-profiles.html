@Configuration, @Bean, Component Scanning & Profiles

~30 minutes · Module 05 Lesson 3 of 9 · builds on S02

Senior Interview Focus: “Bean not found” is a scan/profile/@Bean-name problem until proven otherwise. Can you explain where Boot scans from, when to use @Bean vs @Component, and why calling another @Bean method from a @Configuration class returns the singleton? Profiles in K8s are how prod accidentally gets H2.

Primary sources: Classpath Scanning · Java-based Configuration · Boot Profiles

1. Stereotypes — Same DI, Different Intent

Annotation Meaning Core DI difference?
@Component Generic scanned bean Baseline
@Service Application service None for wiring
@Repository Persistence adapter Exception translation via advisor (nice to know)
@Controller / @RestController MVC handler Discovered by RequestMappingHandlerMapping (S07)

Must know: For constructor injection, @Service vs @Component is documentation. Do not invent magic.

2. Component Scanning Flow

@SpringBootApplication
        │  meta: @ComponentScan (default: this package + below)
        ▼
ClassPathBeanDefinitionScanner
        │  finds @Component (and meta-annotated)
        ▼
BeanDefinition registered  (name: decapitalized class, or @Component("id"))
        │
        ▼
S02 pipeline: instantiate → DI → init

Mental model: Scan writes definitions. Refresh instantiates. If the class is not a definition, you never get a bean — regardless of how pretty the constructor is.

3. Package Boundaries — #1 “Bean Not Found”

com.acme.shop.ShopApplication   ← @SpringBootApplication here
com.acme.shop.api.HelloController          scanned ✓
com.acme.payments.StripeConfig             NOT scanned ✗  (sibling of shop)

Default scan base = package of the annotated application class and subpackages, not the whole JAR. Fix: move code under the app package, or @ComponentScan("com.acme") / @SpringBootApplication(scanBasePackages = ...).

Trap: putting main in com.acme and accidentally scanning every library component. Too wide is also a bug (duplicate beans, slow start).

4. @Configuration and @Bean

@Configuration
public class ClockConfig {
  @Bean
  Clock utcClock() {
    return Clock.systemUTC();
  }
}

You own construction. Useful for types you cannot annotate (JDK, third-party ObjectMapper).

5. @Component Class vs @Bean Method

Use @Component on your class when Use @Bean when
You own the source; simple ctor DI Third-party type, explicit construction, multiple variants
Stereotype communicates layer Conditional setup (S04) around one factory method

6. @Configuration Method Interception (Interview-Level)

Full @Configuration classes are CGLIB-enhanced (unless proxyBeanMethods = false). Calling utcClock() from another @Bean method in the same class hits the container, not a second new Clock — you get the singleton.

@Configuration
public class TimeConfig {
  @Bean Clock clock() { return Clock.systemUTC(); }

  @Bean Ticker ticker() {
    return new Ticker(clock()); // same Clock bean, not a second instance
  }
}

@AutoConfiguration / lite mode uses proxyBeanMethods = false — then clock() really runs again. Boot auto-config classes are lite. App @Configuration defaults to proxied. Do not confuse the two (S05).

Nice to know: @Configuration(proxyBeanMethods = false) is faster to start; you must inject beans as method parameters instead of calling sibling methods.

7–8. @Profile

@Configuration
@Profile("dev")
public class DevMailConfig {
  @Bean MailSender mailSender() { return new LoggingMailSender(); }
}

Activate: spring.profiles.active=dev (env, CLI, K8s). Multiple profiles: comma-separated. Profile-specific files: application-prod.yml (S04).

Production pitfalls:

  • Laptop accidentally prod → hits real Stripe.
  • K8s missing SPRING_PROFILES_ACTIVE → default profile, missing prod DataSource bean.
  • @Profile("!prod") forgotten — H2 on in prod.

9. Common Mistakes

Symptom Cause
NoSuchBeanDefinitionException Outside scan, missing @Component/@Bean, wrong profile, condition false (S04)
NoUniqueBeanDefinitionException Two @Bean of same type — S04 @Primary/@Qualifier
Unexpected bean Scan too wide; name clash (foo vs method name)

Default @Bean name = method name. @Bean("utc") overrides. Duplicate names overwrite or fail depending on context — don’t rely on overwrite.

10. Bridge to S02

This lesson fills the first box: how BeanDefinitions get registered. S02 already covered instantiate → init. S05 adds a third registration source: auto-configuration imports.

Production Relevance

Most “it works on my machine” Boot tickets: main class in the wrong package after a refactor, or profile not set in the Deployment env. First debug step: log ApplicationContext.getBeanDefinitionNames() or Actuator /beans (S08) — is the definition even there?

Interview Articulation

“Boot scans the application class package and below for @Component. Third-party types I register with @Bean on a @Configuration class. @Configuration is CGLIB-proxied so @Bean methods return the singleton when they call each other. If a bean is missing, I check scan base, profile, and bean name before I blame autowiring.”

Revision Notes

  • Scan = package of main + children.
  • Stereotypes ≈ documentation for DI.
  • @Bean for types you don’t own.
  • Full @Configuration intercepts @Bean calls → singleton.
  • Profiles gate definitions; env must match.

Interview One-Liners

  • “If it’s not a BeanDefinition, injection cannot save you.”
  • “Sibling @Bean calls go through the container on a proxied @Configuration.”
  • “Wrong scan package is the boring answer — and usually the right one.”

Senior MCQs

  1. Q1: Main in com.acme.app. Bean in com.other.svc missing. Why?

    1. Default scan does not include sibling packages.
    2. @Service is invisible to the container always.
    3. Tomcat cannot load classes outside java.lang.
    4. Constructor injection forbids other packages.
    View Answer & Explanation

    Answer: A (Default scan does not include sibling packages.)

  2. Q2: @Service versus @Component for constructor DI?

    1. No wiring difference — stereotype is intent.
    2. @Service is prototype; @Component is singleton.
    3. @Component cannot be constructor-injected.
    4. @Service skips BeanDefinition registration.
    View Answer & Explanation

    Answer: A (No wiring difference — stereotype is intent.)

  3. Q3: Third-party Jackson ObjectMapper as a bean?

    1. @Bean factory method on a @Configuration class.
    2. Put @Component on the library class in JDK.
    3. Only field injection into ObjectMapper works.
    4. Must subclass DispatcherServlet first.
    View Answer & Explanation

    Answer: A (@Bean factory method on a @Configuration class.)

  4. Q4: Full @Configuration: @Bean a() { return x; } @Bean b() { return new B(a()); }

    1. a() call is intercepted — one X singleton.
    2. a() always runs twice creating two X.
    3. Illegal Java — methods cannot call methods.
    4. Forces request scope on both beans.
    View Answer & Explanation

    Answer: A (a() call is intercepted — one X singleton.)

  5. Q5: @Profile("prod") bean missing in cluster. First check?

    1. spring.profiles.active / SPRING_PROFILES_ACTIVE.
    2. Whether the class is declared final only.
    3. GC collector choice in the Dockerfile.
    4. Whether HashMap load factor is 0.75.
    View Answer & Explanation

    Answer: A (spring.profiles.active / SPRING_PROFILES_ACTIVE.)

  6. Q6: Default name of @Bean Clock utcClock()?

    1. utcClock — the method name.
    2. Clock — the return type always.
    3. clockConfig — the class name only.
    4. anonymous — beans cannot have names.
    View Answer & Explanation

    Answer: A (utcClock — the method name.)
