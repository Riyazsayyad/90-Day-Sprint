Deep Dive: Thread Fundamentals & Lifecycle

~25 minutes · ties to mission · Cheat sheet

Senior Interview Focus: Interviewers rarely ask you to subclass Thread. They probe whether you know start() vs run(), thread states under load, daemon shutdown rules, why raw thread creation is a production smell, and how this connects to the shared heap you already studied. Parallel streams (Module 02) sit on top of this model — you already used the shared pool; now you own the primitives underneath.

Primary sources: Oracle — Defining and Starting a Thread · Oracle — Thread javadoc (SE 23) · Oracle — Processes and Threads

1. Why Threads Exist (Enterprise Framing)

A Spring Boot service handling 500 HTTP requests cannot run them one-after-another on a single call stack. Threads let the JVM keep many units of work in progress — waiting on DB I/O, computing, or coordinating — without blocking the whole process.

You already saw one abstraction: parallel streams fork work onto ForkJoinPool.commonPool(). That pool is made of threads. This module starts at the primitive those pools manage.

2. Process vs Thread

Concept Process Thread
What it is OS-isolated program with own address space Unit of execution inside a process
Memory Private virtual memory Shares process heap; owns its own stack
Failure isolation Crash usually stops the process Uncaught exception kills that thread; JVM may keep running
Cost Heavy to create / switch Lighter than a process (platform threads still non-trivial)

JVM mental model (ties to Stack vs Heap): one JVM process → one shared Heap + Metaspace → many threads, each with a private call stack (frames, locals, operand stack). Shared mutable heap objects are where races live.

3. Concurrency vs Parallelism (Bridge from Streams)

  • Concurrency: Multiple tasks in progress. May time-slice on one core. Classic for I/O-bound request handling.
  • Parallelism: Multiple tasks executing at the same instant on multiple cores. Classic for CPU-bound splits (parallel streams).

Interview line: concurrency is about structure (overlapping work); parallelism is about execution (simultaneous cores). You can have concurrency without parallelism (single core + blocking I/O). Parallel streams are a parallelism tool — not a general concurrency framework.

4. Platform Threads vs Virtual Threads (Preview)

Per the Thread javadoc:

  • Platform thread: Typically 1:1 with an OS kernel thread. Large stack. Limited resource. Suitable for all task types. Can be daemon or non-daemon.
  • Virtual thread (Java 21+): User-mode thread scheduled by the JVM onto a small pool of carrier platform threads. Cheap; designed for blocking I/O at scale. Always daemon. Not for long CPU-bound work.

This lesson focuses on platform thread fundamentals — you need them to understand pools, locks, and the JMM. Virtual threads get their own section later; do not invent them as a free speedup for CPU work.

5. Creating Work: Runnable vs Extending Thread

Oracle's tutorial prefers separating the task from the execution vehicle.

Preferred: implement Runnable (or lambda)

Runnable task = () -> System.out.println(
    "running on " + Thread.currentThread().getName());

Thread t = new Thread(task, "worker-1");
t.start(); // schedules a new thread; returns immediately to caller

Legacy: subclass Thread

class Worker extends Thread {
  @Override public void run() { /* work */ }
}
new Worker().start();

Why Runnable wins: your task class can still extend something else; the same task can run on an Executor, a virtual thread, or a test harness without being locked into the Thread type hierarchy. Production code almost never subclasses Thread.

Modern: Thread.Builder (Java 21+)

Thread.ofPlatform().name("worker-1").start(task);
Thread.ofVirtual().name("vt-1").start(task);

6. The Critical Trap: start() vs run()

Call What happens
t.start() JVM schedules a new thread. That thread eventually invokes run(). Caller continues concurrently.
t.run() Ordinary method call on the current thread. No new thread. No concurrency.

Calling run() directly is a classic junior bug and a favorite interview trap. Also: a thread may be started only once. A second start() throws IllegalThreadStateException.

7. Thread Lifecycle (getState())

Thread.State (via t.getState()) — interview-ready names:

NEW ──start()──► RUNNABLE ◄──► BLOCKED / WAITING / TIMED_WAITING
                      │
                      └── run ends / uncaught ──► TERMINATED
  • NEW: constructed, not started.
  • RUNNABLE: executing or ready to execute (includes waiting for CPU — Java does not expose a separate "RUNNING").
  • BLOCKED: waiting to enter a synchronized monitor held by another thread.
  • WAITING: waiting indefinitely (Object.wait(), LockSupport.park(), join() without timeout).
  • TIMED_WAITING: waiting with a timeout (sleep, wait(timeout), join(timeout)).
  • TERMINATED: run finished (normal or via uncaught exception after handler runs).

Production note: thread dumps (jstack, VisualVM) show these states. A pile of BLOCKED threads on one monitor is a lock contention smell. A pile of WAITING on a pool queue may be healthy idle workers.

8. Coordination Basics: join, sleep, interrupt

join()

worker.join() — current thread waits until worker reaches TERMINATED. Use when the caller needs the worker's result before continuing (or prefer higher-level Future.get() later).

sleep()

Thread.sleep(ms) — current thread enters TIMED_WAITING. Does not release monitors you hold. Rarely correct for production coordination (prefer locks, latches, conditions).

interrupt()

Cooperative cancellation. t.interrupt() sets the interrupt status. Blocking methods (sleep, join, wait, many I/O ops) throw InterruptedException and clear the status. Your code should either restore the interrupt flag (Thread.currentThread().interrupt()) or exit cleanly — never swallow and continue as if nothing happened.

try {
  Thread.sleep(1000);
} catch (InterruptedException e) {
  Thread.currentThread().interrupt(); // restore status
  return; // stop work
}

9. Daemon vs Non-Daemon

  • Non-daemon: keeps the JVM alive. main starts as non-daemon. Worker pools are usually non-daemon unless you deliberately want fire-and-forget.
  • Daemon: JVM can exit when only daemon threads remain. Useful for background helpers (e.g. cache cleaner) that must not block shutdown.

Set before start: t.setDaemon(true). Virtual threads are always daemon. Unstarted non-daemon threads do not block shutdown — only started ones count.

10. Uncaught Exceptions

An exception that escapes run() does not crash the JVM by default. It goes to the thread's UncaughtExceptionHandler (or the thread group's / default handler), then the thread terminates. In a servlet container, a dead worker with a silent handler = mysterious capacity loss. Always log in handlers for long-lived pools.

11. Why Production Rarely Calls new Thread()

Spawning unbounded raw threads under load → OOM / native thread exhaustion. No reuse, no queueing policy, no metrics. Senior answer:

Prefer an ExecutorService (fixed/cached/work-stealing pool) with bounded queues and rejection policy. Raw Thread is for teaching and rare special cases — not for request paths.

Executors are the next major section. You already met one: ForkJoinPool.commonPool() behind parallel streams.

12. Shared State Warning (Foreshadow)

Two threads reading/writing the same heap field without coordination → data races. Visibility and atomicity are not guaranteed by "it worked on my machine." Next lessons: synchronized, volatile, the Java Memory Model. Until then: treat shared mutable state as unsafe unless proven otherwise.

13. Revision Notes

  • Process = address space; thread = stack + shared heap.
  • start() schedules; run() is just a method on the current thread.
  • States: NEW → RUNNABLE ↔ BLOCKED/WAITING/TIMED_WAITING → TERMINATED.
  • Prefer Runnable / builders; prefer executors over raw threads in production.
  • Daemon threads do not keep the JVM alive; restore interrupt status on catch.

14. 5 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Calling thread.run() instead of start() does what?

    1. Runs task on current thread.
    2. Starts new OS kernel thread.
    3. Queues task on common pool.
    4. Creates daemon virtual thread.
    View Answer & Explanation

    Answer: A (Runs task on current thread.)

    run() is a normal method invocation. Only start() asks the JVM to schedule a new thread that will then call run().

  2. Q2: Which Thread.State means waiting on a monitor enter?

    1. BLOCKED waiting for lock.
    2. WAITING waiting for lock.
    3. RUNNABLE waiting for lock.
    4. NEW waiting for lock.
    View Answer & Explanation

    Answer: A (BLOCKED waiting for lock.)

    BLOCKED is specifically for threads waiting to enter a synchronized block/method. WAITING covers wait()/join()/park() without timeout.

  3. Q3: Best default way to define concurrent work?

    1. Implement Runnable then submit.
    2. Extend Thread then override.
    3. Extend Thread then sleep.
    4. Implement Thread then submit.
    View Answer & Explanation

    Answer: A (Implement Runnable then submit.)

    Oracle and production practice separate task from thread. Runnable (or Callable) plugs into executors and builders; subclassing Thread burns your single inheritance slot.

  4. Q4: When can the JVM exit despite live threads?

    1. Only daemon threads remain.
    2. Only non-daemon threads remain.
    3. Any NEW threads remain.
    4. Any BLOCKED threads remain.
    View Answer & Explanation

    Answer: A (Only daemon threads remain.)

    Shutdown begins when all started non-daemon threads have terminated. Remaining daemon threads are abandoned.

  5. Q5: Why avoid new Thread per HTTP request?

    1. Unbounded create risks exhaustion.
    2. Thread start always throws error.
    3. Runnable cannot run on pools.
    4. join always blocks forever.
    View Answer & Explanation

    Answer: A (Unbounded create risks exhaustion.)

    Each platform thread costs native memory and scheduling. Under spike load, unbounded creation OOMs the process. Use a bounded executor with a queue and rejection policy.

15. Reasoning Exercises

  1. Trace: Write a main that starts two threads printing 0..4. Explain why output order is non-deterministic without synchronization.
  2. Bug hunt: A teammate writes new Thread(task).run() and says "concurrency is broken." Fix and explain.
  3. Lifecycle: Start a thread that sleep(5000). From main, print getState() before start, after start (briefly), and after join().
  4. Interrupt: Loop in a worker checking Thread.interrupted(). From main, interrupt after 1s and confirm clean exit with flag restored in a catch path.
  5. Daemon: Start a daemon thread with an infinite loop. Let main return. Observe JVM exit — contrast with non-daemon.
