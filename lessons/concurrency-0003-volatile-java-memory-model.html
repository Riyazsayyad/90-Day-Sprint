Deep Dive: volatile & the Java Memory Model

~30 minutes · ties to mission · builds on Lesson 2, Stack vs Heap

Senior Interview Focus: synchronized gives atomicity + visibility — but coarse locks hurt throughput, and not every shared field needs a monitor. Interviewers probe: why a plain boolean shutdown can loop forever, what volatile actually guarantees (and what it does not), and why broken double-checked locking was a JDK-era classic. This is the bridge from "locks work" to "why java.util.concurrent exists."

Primary sources: Oracle — Memory Consistency Errors · Oracle — Atomic Access · JLS Chapter 17 — Threads and Locks · JSR-133 FAQ (Doug Lea)

1. Why synchronized Alone Isn't Always Enough

Lesson 2 taught: synchronized provides mutual exclusion and visibility (unlock happens-before next lock). That is correct — but production code often needs:

  • Visibility without holding a lock — e.g. a shutdown flag read in a hot loop while another thread sets it once.
  • Lower overhead — acquiring a monitor on every read of a status flag serializes threads unnecessarily.
  • One-way publication — writer initializes state once; many readers need to see it without synchronizing every read.

Senior framing: use the weakest synchronization that is correct. Over-synchronizing is a latency and deadlock-risk smell.

2. The Hardware Reality (Interview Level)

Threads share the heap, but CPUs cache memory locally for speed. Without coordination:

  • Store buffers / caches: Thread A writes flag = true — Thread B may still see false from its cache.
  • Instruction reordering: Compiler and CPU may reorder independent statements if the single-thread result is unchanged — breaking naive multi-thread assumptions.

You do not need to model cache lines in interviews. You need one line: without a happens-before edge, the JMM allows stale reads and surprising orderings. "It worked on my machine" is not a memory model.

3. Java Memory Model (JMM)

The JMM (formalized by JSR-133, Java 5+) defines which values a read is allowed to observe. It is a contract between your code, the compiler, and the runtime — not a description of one CPU.

Programmers reason in happens-before. The JVM may reorder and cache — but cannot break happens-before guarantees.

Memory consistency error: different threads have inconsistent views of what should be the same data. Fix: establish happens-before between writer and reader.

4. happens-before Rules (Core Set)

If action A happens-before B, then A's effects are visible to B. Key edges for interviews:

RuleMeaning
Program orderWithin one thread, earlier statements happen-before later ones
Monitor unlock → lockUnlock on monitor M happens-before every subsequent lock on M
volatile write → readWrite to volatile v happens-before every subsequent read of v
Thread.startEverything before start() happens-before actions in the new thread
Thread.joinAll actions in thread T happen-before join() returns
TransitivityIf A hb B and B hb C, then A hb C

The volatile rule is powerful: a read of volatile v sees the latest write to v and (transitively) prior writes that happened-before that write in the writer thread.

5. volatile Semantics

volatile on a field means:

  • Reads and writes go through main memory semantics — no stale cached copy indefinitely.
  • Writes establish happens-before with subsequent reads of that variable.
  • Reordering constraints: volatile accesses cannot be reordered with each other; post-JSR-133, normal field accesses around volatiles are also constrained.

What volatile does NOT do

volatile int count = 0;
void increment() { count++; } // STILL BROKEN — read-modify-write

volatile makes each individual read/write visible — not compound operations. For atomic counters → AtomicInteger (Section 06) or synchronized.

7. long and double Without volatile

JLS: reads/writes of long and double are atomic only when declared volatile (or accessed under synchronization). Without that, a read may see a "torn" value — high 32 bits from one write, low 32 from another.

Modern 64-bit JVMs often make this safe in practice — but the language contract still matters in interviews and for portability.

8. final Fields & Safe Publication (Preview)

If an object's final fields are set in the constructor and the reference is published safely, readers see fully constructed final values without extra synchronization on those fields.

Safe publication means the reader's first access to the object happens-after construction completes via one of:

  • Static initializer (class init is JVM-synchronized)
  • Storing ref into volatile field
  • Storing ref under synchronized and releasing lock
  • Thread.start() passing the object to the new thread

Unsafe: publishing this from constructor (escape) — another thread may see partially constructed state.

9. Double-Checked Locking (Interview Classic)

Broken (pre-JSR-133 / missing volatile)

// BROKEN — do not use
class BrokenSingleton {
  private static BrokenSingleton instance;

  static BrokenSingleton getInstance() {
    if (instance == null) {
      synchronized (BrokenSingleton.class) {
        if (instance == null) {
          instance = new BrokenSingleton(); // reordering hazard
        }
      }
    }
    return instance;
  }
}

Another thread may see a non-null reference to a partially constructed object (reordered writes). Also: without volatile, the outer null check has no happens-before with the writer.

Correct — volatile holder (idiom)

class SafeSingleton {
  private static volatile SafeSingleton instance;

  static SafeSingleton getInstance() {
    SafeSingleton local = instance;
    if (local == null) {
      synchronized (SafeSingleton.class) {
        local = instance;
        if (local == null) {
          instance = local = new SafeSingleton();
        }
      }
    }
    return local;
  }
}

volatile on instance publishes the fully constructed object. Production today: prefer enum singleton or holder-class idiom — but know DCL for interviews.

Holder class idiom (no volatile needed)

class Holder {
  private static class LazyHolder {
    static final Holder INSTANCE = new Holder();
  }
  static Holder getInstance() { return LazyHolder.INSTANCE; }
}

JVM class initialization is synchronized — safe lazy init without explicit locks in application code.

10. Classic Bugs

  • Flag without volatile: worker loop never exits after main sets shutdown = true.
  • Stale config: reload thread writes new settings; request threads read cached values forever.
  • DCL singleton: returns broken half-built instance.
  • volatile counter: still loses increments — wrong tool.
// Bug: shutdown may never be seen
boolean shutdown = false;

void worker() {
  while (!shutdown) { doWork(); }
}

void stop() { shutdown = true; }

// Fix:
volatile boolean shutdown = false;

Senior line: volatile = visibility for one variable's write/read chain. Atomics = CAS for compound updates. synchronized = multi-statement invariants + wait/notify.

12. Revision Notes

  • No happens-before → stale reads and reorderings allowed.
  • volatile write → read establishes visibility (and transitively prior writes in writer).
  • volatile does not make count++ atomic.
  • DCL needs volatile holder; holder-class / enum safer in production.
  • long/double need volatile or sync for atomicity guarantee.

13. 5 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: volatile int count; count++ is safe?

    1. No — compound op not atomic.
    2. Yes — volatile makes all atomic.
    3. Yes — if only two threads.
    4. No — unless count is final.
    View Answer & Explanation

    Answer: A (No — compound op not atomic.)

    count++ is read-modify-write. volatile only guarantees visibility of individual reads/writes, not the whole operation.

  2. Q2: Write to volatile v guarantees what?

    1. Later read of v sees it.
    2. Later read of v may miss.
    3. All fields become volatile.
    4. All threads stop immediately.
    View Answer & Explanation

    Answer: A (Later read of v sees it.)

    Volatile write happens-before subsequent volatile read of same variable. Transitivity pulls in prior writes in the writer thread.

  3. Q3: Broken DCL singleton lacks what?

    1. Volatile on instance field.
    2. Final on instance field.
    3. Static on instance field.
    4. Private on instance field.
    View Answer & Explanation

    Answer: A (Volatile on instance field.)

    Without volatile, another thread can see a non-null reference to a partially constructed object due to reordering.

  4. Q4: long read without volatile may be?

    1. Torn across two 32-bit halves.
    2. Always atomic on all JVMs.
    3. Blocked until monitor held.
    4. Promoted to double width.
    View Answer & Explanation

    Answer: A (Torn across two 32-bit halves.)

    JLS: 64-bit primitives are only guaranteed atomic when volatile or accessed under synchronization.

  5. Q5: Shutdown flag never seen — fix?

    1. Declare flag as volatile.
    2. Declare flag as final.
    3. Declare flag as static.
    4. Declare flag as transient.
    View Answer & Explanation

    Answer: A (Declare flag as volatile.)

    Writer thread's shutdown = true needs happens-before with reader's check. volatile establishes that edge without a lock.
