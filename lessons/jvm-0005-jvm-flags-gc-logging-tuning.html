JVM Flags, GC Logging & Tuning

~35 minutes · ties to mission · builds on S04 Collector Choice, S01 OOM Map, Stack vs Heap

Senior Interview Focus: Can you read a unified GC log line and extract pause time, cause, and heap before/after? Can you explain why prod sets -Xms = -Xmx and why a 32 GB bare-metal heap config kills a 2 GB pod? Flags are levers — interviewers want judgment: measure first, tune second, fix retention before either.

Primary sources: Oracle — java command (SE 21) · Unified JVM Logging · Oracle — G1 Tuning

1. Heap Sizing — -Xms / -Xmx

Flag Meaning Prod note
-Xms Initial heap size JVM may grow heap from here up to -Xmx
-Xmx Maximum heap size Hard cap for object heap — not total process memory

Why equal -Xms = -Xmx in production

  • Avoids repeated heap resize cycles as load ramps — resize can trigger extra GC and OS allocation churn.
  • Predictable memory footprint for capacity planning and K8s resource requests.
  • Eliminates "heap still growing" surprises during traffic spike.

Dev laptops may use smaller -Xms to save RAM. Prod APIs: set both to the same validated value.

Container: -XX:MaxRAMPercentage

JDK 10+ reads cgroup memory limit and can derive heap ergonomically:

-XX:MaxRAMPercentage=75.0
-XX:InitialRAMPercentage=75.0
  • Percentage of container-detected RAM — not host RAM.
  • Still leaves room for Metaspace, stacks, direct memory, native GC structures (S01).
  • Don't set 100%. 50–75% common for Spring + Netty; validate with metrics.
  • Explicit -Xmx overrides percentage-based defaults when both set — know precedence on your JDK.
12-factor trap: copying -Xmx32g from bare-metal into a 2 GiB K8s pod → instant OOMKill. Size for the container.

2. Metaspace — -XX:MaxMetaspaceSize

Class metadata lives off-heap in Metaspace — not counted in -Xmx.

  • By default Metaspace grows until OS limit — unbounded growth can OOMKill the process.
  • -XX:MaxMetaspaceSize=256m — hard cap; fail fast with OutOfMemoryError: Metaspace instead of silent cgroup kill.
  • When it blows up: Spring fat classpath, Hibernate enhancement, bytecode agents (APM, Mockito inline), dynamic proxies, Groovy/scripting, hot redeploy without restart.
  • Fix: classloader leak investigation (S06), not bigger -Xmx.

3. GC Logging — Unified JVM Logging (-Xlog)

Java 9+ replaced legacy -XX:+PrintGCDetails with unified logging. Enable from day one:

-Xlog:gc*,gc+heap=debug,gc+age=trace,safepoint:file=/var/log/gc.log:utctime,level,pid,tags:filecount=5,filesize=20M

3.1 What to extract from a log line

Example G1 Young GC (simplified — format varies slightly by JDK):

[2026-09-15T10:23:01.456+0000][info][gc] GC(142) Pause Young (Normal) (G1 Evacuation Pause)
  142M->48M(512M) 12.345ms
Field Meaning
GC(142) GC cycle number — correlate across log
Pause Young (Normal) / Mixed Cause / type — Young vs Mixed vs Full
142M->48M(512M) Heap before → after (capacity) — live set dropped 142→48 MB of 512 MB cap
12.345ms Pause time — STW duration for this event

3.2 Reading for incidents

  • Pause time trending up + heap after GC rising → retention / Old gen filling (S03).
  • Frequent Full GC with tiny reclaim → leak or heap undersized for live set.
  • Humongous allocations — look for humongous tags in detailed G1 logs.
  • Correlate GC timestamp with APM trace p99 — prove GC caused latency spike.

4. Key G1 Knobs — What They Do (Not Gospel Recipes)

You chose G1 in S04. Interviewers ask what these mean — not "always set X":

Flag / concept What it does Tuning caution
-XX:MaxGCPauseMillis Soft pause goal G1 adapts toward (default 200) Lower = more frequent GC, may hurt throughput; not a hard cap
-XX:G1HeapRegionSize Size of each G1 region (1–32 MB, power of 2) Larger regions → fewer regions but bigger humongous threshold
IHOP (InitiatingHeapOccupancyPercent) Old gen occupancy % that starts concurrent marking cycle Too low → marking overhead; too high → Mixed GC rushed under pressure
-XX:G1MixedGCCountTarget Spread Old region reclaim across N Mixed GCs Smoother pauses vs longer reclaim tail
-XX:ParallelGCThreads / ConcGCThreads STW worker count / concurrent marker threads Match CPU limits in K8s — don't assume all host cores
Senior rule: change one knob at a time under representative load. Document before/after pause p99 and throughput.

5. When Tuning Helps vs Hurts

Tuning helps Tuning hurts / wastes time
Proven GC pauses breach SLO after code is clean Retention leak still present — flags mask symptoms
Heap consistently at cap with healthy reclaim pattern Copy-paste flags from different heap size / workload
Load test reproduces prod allocation rate Tuning on idle dev laptop
Collector swap (G1 → ZGC) with metrics baseline 20 flags changed at once — impossible to attribute

Correct sequence: enable GC logs → load test → fix retention/allocation → set heap/container ratio → adjust pause goal or collector → individual G1 knobs last.

6. OOM Types — Map to Fix

Expand S01 triage table for on-call:

Error Pool First fix direction
Java heap space -Xmx heap Heap dump, find dominator tree, paginate, bound caches; raise -Xmx only if live set is legitimate
Metaspace Class metadata Classloader leak, agents, dynamic codegen; MaxMetaspaceSize as guardrail
unable to create native thread OS thread budget Bounded pools, VT for I/O, lower -Xss, raise ulimit
Direct buffer memory Off-heap NIO Netty pool sizing, MaxDirectMemorySize, fix missing release
GC overhead limit exceeded GC spending >98% time with <2% reclaim Heap too small for live set or severe leak — not "tune IHOP"

7. OutOfMemoryError vs StackOverflowError

From Stack vs Heap:

  • OutOfMemoryError — a memory pool exhausted (heap, Metaspace, direct, native threads). JVM may continue if only one thread failed allocation — often process unhealthy soon after.
  • StackOverflowError — thread's stack exceeded depth limit (infinite recursion, deep XML/JSON). Not heap. Fix algorithm / use iterative parser. Flag: -Xss increases stack per thread — multiplies across thread count.
void recurse() { recurse(); }  // StackOverflowError — stack frames, not heap

List<byte[]> leak = new ArrayList<>();
while (true) leak.add(new byte[10_000_000]);  // OutOfMemoryError: Java heap space

8. Enterprise — 12-Factor JVM in Docker

  • Config in environment — JAVA_OPTS / JDK_JAVA_OPTIONS in K8s manifest, not baked into JAR.
  • Stateless processes — heap doesn't assume local disk; logs to stdout/file with rotation sidecar.
  • Port binding — one JVM per container; resources match resources.limits.memory.
  • Disposability — fast startup; don't need 10 min heap warm-up if -Xms=-Xmx.
  • Dev/prod parity — same major JDK, same collector family, similar heap ratio (not same absolute GB).

Starter template (2 GiB pod, Spring API)

ENV JAVA_OPTS="\
  -XX:InitialRAMPercentage=50.0 \
  -XX:MaxRAMPercentage=50.0 \
  -XX:MaxMetaspaceSize=256m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/tmp/heapdump.hprof \
  -Xlog:gc*:file=/tmp/gc.log:utctime,level,tags:filecount=3,filesize=10M"

Adjust percentages after observing RSS in staging. Add -XX:+UseZGC only after G1 data proves need (S04).

Out of scope: custom GC implementation, JFR full course (S08), Spring Actuator metrics catalog (M05).

9. Revision Notes

  • Prod: -Xms = -Xmx for stable footprint.
  • Containers: MaxRAMPercentage — never 100%; validate off-heap headroom.
  • MaxMetaspaceSize — guardrail for class metadata; fix loader leaks.
  • GC logs: pause time, cause, before→after heap.
  • G1 knobs: pause goal, region size, IHOP — understand before changing.
  • Tune under load; fix retention first.
  • OOM message tells which pool; StackOverflow = stack not heap.

10. Reasoning Exercises

  1. GC log: Pause Full (Allocation Failure) 890M->885M(1024M) 4200ms. Interpretation?

    Answer

    Full GC reclaimed only 5 MB in 4.2 s — live set ~885 MB near 1 GB cap. Likely leak or legitimately huge live set. Heap dump before raising -Xmx.

  2. -Xmx raised 4→8 GB. Metaspace OOM continues. Next?

    Answer

    Wrong pool. Investigate class loading / agents / classloader retention. Set MaxMetaspaceSize to fail fast while debugging.

  3. Dev sets MaxGCPauseMillis=50 on batch job. Throughput drops 30%. Why?

    Answer

    Aggressive pause goal → more frequent, smaller collections → more GC CPU overhead. Batch may prefer Parallel GC or default 200 ms goal.

  4. 2 GiB pod, MaxRAMPercentage=90, OOMKilled no Java OOM. Cause?

    Answer

    Heap ~1.8 GiB leaves almost nothing for Metaspace, threads, direct, native. cgroup kills process. Lower to ~50–60%.

11. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Why set -Xms equal -Xmx in prod?

    1. Avoid heap resize churn at ramp.
    2. Disable garbage collection fully.
    3. Force Metaspace into heap area.
    4. Required for compressed oops only.
    View Answer & Explanation

    Answer: A (Avoid heap resize churn at ramp.)

    Fixed heap size gives predictable memory and avoids growth-triggered GC during load increase.

  2. Q2: MaxRAMPercentage applies to what?

    1. Container-detected memory limit.
    2. Host physical RAM always only.
    3. Metaspace size cap exclusively.
    4. Per-thread stack size bytes.
    View Answer & Explanation

    Answer: A (Container-detected memory limit.)

    JDK reads cgroup limit to derive ergonomic heap sizing in containers.

  3. Q3: GC log 200M->80M(512M) 15ms means?

    1. Heap shrank live set in pause.
    2. Metaspace was fully cleared.
    3. Stack overflow was recovered.
    4. Thread count dropped by half.
    View Answer & Explanation

    Answer: A (Heap shrank live set in pause.)

    Before→after heap usage of 512M capacity; 15ms STW pause for that GC event.

  4. Q4: IHOP on G1 controls what?

    1. When concurrent marking starts.
    2. Thread stack depth maximum.
    3. TLAB size per thread bytes.
    4. Direct buffer pool cap limit.
    View Answer & Explanation

    Answer: A (When concurrent marking starts.)

    Initiating Heap Occupancy Percent triggers concurrent mark based on Old gen fill level.

  5. Q5: StackOverflowError indicates failure in?

    1. Thread call stack depth.
    2. Java heap object allocation.
    3. Metaspace class metadata.
    4. Direct byte buffer off-heap.
    View Answer & Explanation

    Answer: A (Thread call stack depth.)

    Stack overflow is per-thread stack — recursion or deep parsing. Not heap OOM.

  6. Q6: First step before aggressive GC flag tuning?

    1. Load test with GC logs enabled.
    2. Set Xmx to host RAM size.
    3. Disable all safepoint polls.
    4. Switch to Serial GC always.
    View Answer & Explanation

    Answer: A (Load test with GC logs enabled.)

    Measure pause distribution and retention under representative load before changing knobs.
