Servlet Stack: Tomcat, Filters & MVC Dispatch

~35 minutes · Module 05 Lesson 7 of 9 · builds on threads, pools, virtual threads

Senior Interview Focus: One HTTP request occupies a Tomcat worker for the whole blocking JDBC call. Can you walk Client → Tomcat → Filter → DispatcherServlet → Controller → Service, name where a correlation ID is set, and diagnose 200 Tomcat threads vs 20 Hikari connections? This is production, not servlet certification.

Primary sources: DispatcherServlet · Boot Servlet Web · Graceful Shutdown

Mental Model — Request Path

                     Tomcat worker thread  (or virtual thread if enabled)

1. Embedded Tomcat in Boot

starter-web pulls Tomcat. Boot creates a TomcatServletWebServerFactory, starts a connector on server.port (8080). No external catalina install. The JVM process is the server (JVM S01).

You can switch to Jetty/Undertow via starters. Same servlet programming model.

2. Platform / Request Threads

Classic: pool of platform threads (server.tomcat.threads.max, default 200). Each in-flight blocking request holds one thread. You sized pools in Executors — same math: threads ≈ concurrent blocking work, not QPS.

Boot 3.2+: spring.threads.virtual.enabled=true — Tomcat can run requests on virtual threads (VT). Helps blocking I/O. Does not help CPU-bound work. Pinning still applies (synchronized, native).

3. Connector (Practical)

Acceptor takes the TCP connection; worker runs the servlet. Timeouts: connection, keep-alive. You rarely tune protocol internals in interviews — you tune max threads, accept count, and downstream pools.

4. Servlet Filter Chain

Filters wrap the servlet. Ordered (@Order / FilterRegistrationBean). Typical: correlation ID into MDC, security, metrics.

@Component
public class CorrelationFilter extends OncePerRequestFilter {
  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                  FilterChain chain) throws ServletException, IOException {
    String cid = Optional.ofNullable(req.getHeader("X-Correlation-Id"))
        .orElse(UUID.randomUUID().toString());
    MDC.put("cid", cid);
    try {
      chain.doFilter(req, res);
    } finally {
      MDC.clear(); // ThreadLocal leak otherwise — JVM S06 / concurrency
    }
  }
}
Must know: MDC is ThreadLocal. Forget clear() on a pool thread → leaked IDs (and classloader leaks on redeploy). Virtual threads: still clear; cheaper threads ≠ optional hygiene.

5–8. DispatcherServlet & MVC

  • DispatcherServlet — front controller. One servlet mapping /.
  • HandlerMapping — path + method + consumes → handler method.
  • HandlerAdapter — invokes that method (you don’t call it).
  • Argument resolvers — @RequestBody, @PathVariable, Principal.
  • HttpMessageConverter — JSON via Jackson, etc.

404 vs 405 vs 415: mapping miss vs method vs media type — interview precision.

9. @ControllerAdvice

Exception → HTTP mapping in one place. After the controller throws, before the response is committed. Not a substitute for Filter errors that never reach the dispatcher.

10–12. Blocking Path & Exhaustion

Tomcat max = 200
Hikari max = 20
Inbound: 200 slow queries

  20 threads:  in JDBC (have a connection)
 180 threads:  blocked waiting on Hikari pool
 Cost: 180 platform stacks + timeouts + tail latency
 Thread dump: socketRead0 / HikariProxyConnection.getConnection  (JVM S08)

Must know: Fix the bottleneck (query, pool size vs DB, timeouts). Raising Tomcat to 2000 without DB capacity makes GC and context switching worse.

Virtual threads: waiting on Hikari still serializes on 20 connections. VT does not multiply database capacity.

13. Filter vs HandlerInterceptor vs @ControllerAdvice

Filter HandlerInterceptor @ControllerAdvice
Layer Servlet Spring MVC MVC exception / binding
Sees All requests to the servlet Mapped handlers (not raw static if bypassed) Controller exceptions
Use Auth gateway, CID, CORS Handler-specific metrics, model API error JSON

Spring Security is a filter chain — out of scope for internals here; know it sits before DispatcherServlet.

14. Correlation ID

Propagate X-Correlation-Id to downstream HTTP and logs. Actuator/metrics tags later (S08). Without it, six replicas are a haystack.

Production Relevance

Latency spike: thread dump + Hikari metrics, not “restart Tomcat.” Graceful shutdown: Boot waits in-flight requests (server.shutdown=graceful) — K8s preStop should match.

Interview Articulation

“Embedded Tomcat runs the servlet container in-process. A worker thread (or virtual thread) runs the filter chain then DispatcherServlet, which maps to a controller. If the service blocks on JDBC, that thread stays occupied. I size Tomcat against downstream pools. Exhausted Tomcat with idle CPU often means all workers are blocked on I/O — dump threads, don’t add replicas blindly.”

Revision Notes

  • Worker thread held for entire blocking request.
  • DispatcherServlet = front controller.
  • Filters wrap servlet; interceptors wrap handlers.
  • Pool mismatch: Tomcat vs Hikari vs DB.
  • VT: more waiters, same DB capacity.

Interview One-Liners

  • “The servlet thread is the currency of a blocking API.”
  • “Hikari is often the real max concurrency.”
  • “MDC without finally is a lie in the next request.”

  3. Q3: Correlation ID in a Filter. Must also?

    Answer: A (Clear MDC in finally on the worker.)

  4. Q4: 200 busy Tomcat threads, Hikari 20. Likely?

  5. Q5: spring.threads.virtual.enabled=true helps most?

    Answer: A (Many concurrent blocking I/O requests.)

  6. Q6: HandlerInterceptor vs Filter?

    1. Interceptor is MVC; Filter is servlet API.
    2. Filter only runs after @ControllerAdvice.

    Answer: A (Interceptor is MVC; Filter is servlet API.)
