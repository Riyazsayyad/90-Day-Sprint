Deep Dive: Concurrent Collections & Atomics

~38 minutes · ties to mission · builds on L1–L5 · Fail-Fast lesson

Senior Interview Focus: You know locks (L4) and pools (L5). Production shared state usually lives in java.util.concurrent data structures — not Collections.synchronizedMap on a HashMap. Interviewers probe CHM computeIfAbsent, weakly consistent iterators vs CME, when CopyOnWrite wins, and atomics vs synchronized for hot counters.

Primary sources: Oracle — Concurrent Collections · ConcurrentHashMap · CopyOnWriteArrayList · BlockingQueue · AtomicInteger · java.util.concurrent.atomic

1. Why Synchronized Wrappers Are Often Wrong

Module 01: Collections.synchronizedMap(new HashMap<>()) wraps every method in synchronized (mutex). Sounds safe. Production problems:

  • Coarse lock — one mutex for the whole map. High read contention serializes everyone (Lesson 4's RW lock exists for a reason).
  • Compound ops not atomic — javadoc warns: you must manually synchronize on the wrapper for check-then-act: 
    // BUG — two threads can both see absent key
if (!map.containsKey(k))
  map.put(k, v);

// Required with synchronized wrapper:
synchronized (map) {
  if (!map.containsKey(k))
    map.put(k, v);
}
  • Iteration trap — must synchronize during the entire loop. Forget once → data races or CME on some paths.
  • Null keys/values — synchronized wrappers delegate to underlying collection rules; CHM disallows nulls by design (ambiguity under concurrency).
Senior line: synchronized wrapper = "I synchronized each method." Interview line: "That's not enough for iteration or check-then-act — use CHM or hold one lock for the whole invariant."

2. ConcurrentHashMap — Interview Internals (Java 8+)

History bite: Java 7 used segments — fixed array of sub-maps, each with its own lock. Java 8+ replaced segments with a single bin array (like HashMap) plus per-bin synchronization.

  • Bin — array slot holding a linked list of Nodes (key, hash, value, next).
  • Treeify — when a bin grows past 8 nodes (and table ≥ 64), list becomes a red-black tree for O(log n) lookups. Untreeify below 6.
  • Lock granularity — writers typically lock/synchronize on the first node of a bin (or CAS on empty bin). Different bins proceed in parallel.
  • Reads — usually lock-free volatile reads along bucket chains; no global reader lock.

Out of scope: full resize/rebalance proofs, AQS, lock-free skip lists.

Key APIs (production)

// Atomic "get or create" — one thread runs mappingFunction per key
cache.computeIfAbsent(userId, id -> loadFromDb(id));

// Atomic update
counters.merge(key, 1L, Long::sum);

// Bulk — may be more efficient than loop
map.forEach((k, v) -> ...);
map.reduceValues(1L, Long::sum);
  • computeIfAbsent — fixes the check-then-act race from Lesson 2 without external lock. Mapping function must be fast and must not recursively modify the same map on the same thread (deadlock risk).
  • putIfAbsent / replace — single-entry atomic ops.

size() and iteration semantics

OperationUnder concurrency
size() / isEmpty() Approximate — snapshot-ish count; fine for metrics, wrong for strict control-flow gates
Iterator / forEach / entrySet() Weakly consistent — never throws CME; may or may not see entries added after iteration started; won't reflect removals already passed
containsKey / get Point reads with happens-before from concurrent writes (volatile/CAS paths)

Tie to Lesson 16: CHM iterators are weakly consistent — not a snapshot copy like CopyOnWrite, not fail-fast like HashMap. They reflect some concurrent updates.

3. CopyOnWriteArrayList

Backing array is volatile. Read — no lock, direct array index. Write (add, set, remove) — copy entire array, mutate copy, publish new reference.

  • Wins: read-heavy, rare writes — listener lists, config subscribers, iteration-heavy snapshots where stale reads are OK.
  • Costs: O(n) copy per write; iterator holds snapshot from creation — won't see later adds; high write rate = GC churn + memory.
  • Iterator: snapshot at birth — no CME ever; won't see concurrent writes after iterator created.
// Spring-style listener list pattern
private final List<EventListener> listeners = new CopyOnWriteArrayList<>();

void fire(Event e) {
  for (EventListener l : listeners) // safe without lock
    l.onEvent(e);
}

Wrong tool: frequently mutating work queue — use BlockingQueue (L5).

4. BlockingQueue Family — Producer-Consumer

Lesson 5 introduced queues as executor work buffers. Here: the coordination API — block instead of spin or busy-wait.

ImplementationCapacityNotes
ArrayBlockingQueue Bounded (fixed array) One lock (or dual-lock variant) — predictable memory; fair optional constructor
LinkedBlockingQueue Bounded or unbounded Linked nodes — higher overhead; unbounded = heap growth risk (L5 trap)
SynchronousQueue Zero Handoff — producer blocks until consumer takes; newCachedThreadPool
PriorityBlockingQueue Unbounded heap Ordering by priority — know comparator stability
DelayQueue Unbounded Elements available after delay — scheduling patterns 
BlockingQueue<Task> q = new ArrayBlockingQueue<>(100);

// producer — blocks when full (backpressure)
q.put(task);

// consumer — blocks when empty
Task t = q.take();

// timed variants: offer(e, timeout), poll(timeout)

Lesson 4's manual Condition buffer is what these classes implement for you. Production: prefer the queue unless you own a special invariant.

5. Atomics — Visibility Without a Full Lock

Lesson 3: volatile gives visibility, not read-modify-write atomicity. i++ on volatile is still a race. java.util.concurrent.atomic wraps a volatile field with CAS operations.

ClassUse
AtomicInteger / AtomicLongCounters, sequence IDs, stats
AtomicReference<V>Atomic swap of object reference (immutable snapshot pattern)
AtomicIntegerArray etc.Striped atomic slots without boxing
LongAdder (bonus)High-contention counting — striping reduces CAS failures
 
AtomicInteger requests = new AtomicInteger();

requests.incrementAndGet();           // atomic ++
requests.addAndGet(5);

boolean ok = requests.compareAndSet(expect, update); // CAS

int current = requests.get();         // volatile read

CAS overview (interview level)

Compare-And-Set: atomically "if current == expect, set to update; else fail." CPU instruction (e.g. x86 CMPXCHG). On failure, retry loop — optimistic concurrency.

// conceptual CAS loop (AtomicInteger does this internally)
void increment() {
  for (;;) {
    int current = value;           // volatile read
    int next = current + 1;
    if (compareAndSet(current, next))
      return;                      // success — publish happens-before
    // else retry — another thread won
  }
}
  • ABA problem (interview mention): value goes A→B→A; CAS sees A and thinks nothing changed. AtomicStampedReference exists — deep dive out of scope.
  • Not a substitute for invariants spanning multiple fields — use locks or immutable snapshots.
  • Hot counter under extreme contention — consider LongAdder over hammering one AtomicLong.

7. Enterprise Framing

ScenarioPick
In-memory cache (per-key load once) ConcurrentHashMap.computeIfAbsent + bounded size policy / Caffeine for TTL
Request/metrics counters LongAdder or AtomicLong — not synchronized on every hit
Spring singleton with mutable map field ConcurrentHashMap or immutable copy-on-write snapshots — not raw HashMap
Event listener registry CopyOnWriteArrayList if rare register/unregister, frequent dispatch
Work handoff between pool threads ArrayBlockingQueue — bounded backpressure (L5)
CHM vs synchronized HashMap CHM when concurrent readers + writers, atomic compound ops, or iterator without global lock. Sync map only if truly low contention and you wrap compounds correctly.
Senior line: pick the structure that makes the invariant atomic — not "thread-safe" label on a wrapper.

8. Classic Bugs

  • check-then-act on synchronizedMap without synchronizing on wrapper — duplicate loads, lost updates.
  • CHM computeIfAbsent slow/blocking loader — holds bin lock; blocks other ops on that bin; recursive same-map call deadlocks.
  • Trusting CHM.size() == 0 for strict logic under live writers — approximate.
  • CopyOnWrite for hot writes — quadratic copying, memory blow-up.
  • i++ on volatile or plain int — not atomic; use AtomicInteger or synchronize.
  • Atomics on multiple related fields — CAS each field separately ≠ atomic invariant across fields.
  • Iterating synchronizedMap without synchronized(map) — javadoc violation, races.

Later sections (not here): CompletableFuture (S07), virtual threads (S08), deep AQS, lock-free skip lists, AtomicStampedReference deep dive.

9. Revision Notes

  • Sync wrapper = per-method lock; compounds + iteration need external sync.
  • CHM Java 8+: bins + treeify; per-bin locking; parallel writes different bins.
  • computeIfAbsent / merge — atomic compound ops.
  • Weakly consistent iteration — no CME; may see some concurrent updates.
  • CopyOnWrite — snapshot reads; expensive writes; stale iterator.
  • BlockingQueue — put/take coordinate producers/consumers.
  • Atomics — CAS retry; visibility + atomic RMW; not multi-field invariants.

10. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: synchronizedMap — containsKey then put if absent. Safe?

    1. No — compound needs outer sync.
    2. Yes — each method is synchronized.
    3. Yes — if map is final field.
    4. Yes — on single-thread only.
    View Answer & Explanation

    Answer: A (No — compound needs outer sync.)

    Two synchronized calls are not one atomic operation. Another thread can insert between them. Use one synchronized(map) block or ConcurrentHashMap.computeIfAbsent.

  2. Q2: CHM iterator during concurrent puts. Typical behavior?

    1. Weakly consistent; no CME thrown.
    2. Fail-fast CME on first change.
    3. Deadlock until writers finish.
    4. Snapshot of entire map frozen.
    View Answer & Explanation

    Answer: A (Weakly consistent; no CME thrown.)

    CHM iterators never throw CME. They may reflect some updates after creation — unlike CopyOnWrite snapshot, unlike HashMap fail-fast.

  3. Q3: CopyOnWriteArrayList — frequent add/remove. Main risk?

    1. O(n) copy per write cost.
    2. Iterator throws CME always.
    3. Reads block on global mutex.
    4. Null keys are disallowed only.
    View Answer & Explanation

    Answer: A (O(n) copy per write cost.)

    Every mutating op copies the backing array. Write-heavy workloads burn CPU and memory — wrong structure.

  4. Q4: volatile int count; count++ from many threads. Result?

    1. Lost updates — not atomic RMW.
    2. Fully atomic without any lock.
    3. Visibility only — count stays 0.
    4. CME on every increment call.
    View Answer & Explanation

    Answer: A (Lost updates — not atomic RMW.)

    volatile publishes writes but ++ is read-modify-write. Use AtomicInteger or synchronize.

  5. Q5: ArrayBlockingQueue full — put() on producer. Effect?

    1. Producer blocks until space.
    2. Queue throws CME immediately.
    3. Oldest element is dropped.
    4. Item goes to common pool.
    View Answer & Explanation

    Answer: A (Producer blocks until space.)

    put blocks — natural backpressure. Contrast offer (false if full) or unbounded queue (never blocks on capacity).

  6. Q6: computeIfAbsent mappingFunction does slow DB call. Risk?

    1. Blocks other ops on that bin.
    2. Iterator throws CME on load.
    3. Map rejects null keys only.
    4. CAS fails and skips the load.
    View Answer & Explanation

    Answer: A (Blocks other ops on that bin.)

    Loader runs under bin lock for that key's bucket. Slow I/O stalls concurrent access to keys in the same bin. Load outside then putIfAbsent, or use a dedicated cache library.

11. Reasoning Exercises

  1. Pick the structure: (a) per-user session cache with lazy DB load, (b) 50M/sec metric increment, (c) webhook listener list (10 listeners, 1 add/day, 100k fires/sec), (d) order buffer between ingest and worker pool. CHM, CopyOnWrite, Atomic/LongAdder, or BlockingQueue?
  2. Fix the cache bug: synchronizedMap + if (!cache.containsKey(k)) cache.put(k, load(k)). Two failure modes under load. Rewrite with CHM; explain what computeIfAbsent guarantees.
  3. Iterator semantics: Thread A iterates CHM. Thread B adds keys. Thread C removes keys. What can A see? Contrast with CopyOnWrite list iteration started before B adds 100 elements.
  4. CAS retry: Three threads incrementAndGet on one AtomicInteger from 0. Final value? Could it be 1 or 2? Why not?
  5. Producer-consumer sizing: 4 consumers, mean service 200ms, Poisson arrivals 100/sec. Bound ArrayBlockingQueue at 50 — what happens under spike when put blocks? Tie to L5 CallerRuns vs blocking producer thread.
  6. Spring bean: Singleton service holds HashMap<String, Config> mutated on admin API and read on every request. Production-safe redesign in one paragraph.
