Diagnostics, Profiling & Memory Leaks

~40 minutes · Module 04 capstone · ties to S01–S07, Thread Dumps, Pool Exhaustion, Locks

Senior Interview Focus: Under incident pressure, can you pick the right tool in 30 seconds? Thread dump for "all threads stuck" — GC logs for pause spikes — heap histogram/dump for growing Old gen. Can you walk an interviewer through latency spike → thread dump + GC log + histogram without opening MAT? Know leak patterns cold; production discipline: reproduce, one change, keep logs.

Primary sources: Oracle — jcmd · Oracle — Troubleshooting Guide · Eclipse MAT — Concepts

1. Diagnostic Toolbox Map

Tool Command / entry Answers
jps jps -l Which Java PIDs are running? Main class / JAR name
jcmd jcmd <pid> help Swiss army knife — thread dump, GC heap info, VM flags, JFR start (preferred modern entry)
jstat jstat -gc <pid> 1s Live GC pool sizes, GC counts, pause times — lightweight monitoring
jstack jstack <pid> or jcmd <pid> Thread.print Thread dump — what every thread is doing, lock states
jmap jmap -histo:live <pid>, jmap -dump Heap histogram (class instance counts) or full heap dump file
Modern preference: jcmd over legacy tools where equivalent. In K8s: kubectl exec into pod, find PID, run jcmd — or capture via sidecar/agent.

2. Thread Dump Reading

You met thread dumps in Thread Fundamentals. Under incident, scan for patterns:

State Often means Action
BLOCKED Waiting to enter synchronized monitor Find "waiting to lock <0x...>" and who holds that lock (S02)
WAITING wait(), park, join — no timeout Trace park target; pool queue empty?
TIMED_WAITING Sleep, timed wait, lock timeout Check if stuck in slow I/O or lock tryLock timeout loop
RUNNABLE Runnable or in native (socket read, JDBC) Many at socketRead0 → downstream slowness, not CPU 
"pool-3-thread-1" #42 prio=5 os_prio=0 BLOCKED
  waiting to lock <0x00000000e1234567> (a com.app.Cache)
  at com.app.Cache.get(Cache.java:88)
  ...

"http-nio-8080-exec-5" #31 RUNNABLE
  at java.net.SocketInputStream.socketRead0(Native Method)
  at org.postgresql.jdbc.PgStream.receive(...)

Pool exhaustion (Executors): all worker threads BLOCKED or in I/O → queue grows → timeouts. Thread dump shows 200 threads all waiting on same lock or DB.

Explicit locks (L04): look for ReentrantLock / AbstractQueuedSynchronizer frames.

3. Heap Dump — When & How

3.1 When to take

  • Old gen climbing, Full GC not reclaiming — Java heap space OOM imminent or occurred
  • Suspected retention leak — heap healthy at restart, grows over hours/days
  • Not first tool for pure CPU spike or thread deadlock — thread dump first

3.2 How (production-safe awareness)

# Histogram — lighter, triggers Full GC with :live
jcmd <pid> GC.class_histogram

# Full dump — STW pause, large file
jcmd <pid> GC.heap_dump /tmp/heap.hprof
# legacy: jmap -dump:live,format=b,file=heap.hprof <pid>

Enable on OOM automatically (S05):

-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/

3.3 MAT / dominator tree (concept — not click-by-click)

Dominator tree: for each object, which retention path would free the most memory if removed? Top dominators = leak suspects.

  • static HashMap holding millions of entries → dominator is map or static holder class
  • Leak detector report: "Problem suspect" — one big collection retaining 80% heap
  • Compare two dumps (baseline vs leak) — what grew?

4. Common Leak Patterns (S01–S07 Synthesis)

Pattern Symptom Find with
Static unbounded Map/List Old gen grows; Full GC poor reclaim Histogram: huge HashMap$Node[] or domain objects
Unclosed resources FD exhaustion, native memory, connection pool starved Heap + OS lsof; try-with-resources fix
Listener registries Objects never collected after "logout" Dominator: event bus / observer list holding subscribers
ThreadLocal Slow Metaspace/heap creep on pool threads Thread dump + heap; missing remove() (S06)
Classloader leak Metaspace stair-step; heap may be flat Metaspace OOM; redeploy without restart

5. Native Memory & Direct Buffers

Not in heap dump — ByteBuffer.allocateDirect, Netty pooled direct memory:

  • OOM: Direct buffer memory — not fixed by -Xmx
  • Netty PooledByteBufAllocator — leaks if buffers not released
  • Native Memory Tracking (awareness): -XX:NativeMemoryTracking=summary, jcmd <pid> VM.native_memory summary
  • RSS > heap + Metaspace → suspect direct/native (S01)

6. CPU vs Allocation Profiling — Flame Graph Mental Model

CPU flame graph (async-profiler, JFR CPU events):

  • X-axis = sample proportion (wider = more CPU time)
  • Y-axis = stack depth (bottom = entry, top = hot leaf)
  • Find wide plateau at HashMap.get or regex — optimize that path

Allocation profiling:

  • Answers "who allocates most?" — Young GC pressure, TLAB churn
  • Wide bar at new byte[] or JSON parser — reduce allocation rate
  • Different fix than CPU: object reuse, streaming, primitive arrays
Interview: CPU profile for "slow" — allocation profile for "GC thrashing but low CPU business logic."

7. JFR — Java Flight Recorder (Awareness)

  • Low-overhead event recorder built into JDK — safe for prod with tuning
  • jcmd <pid> JFR.start duration=60s filename=recording.jfr
  • Events: GC pauses, thread blocks, socket I/O, allocation samples, method hot spots
  • Analyze in JDK Mission Control (JMC) — timeline correlates GC + thread + CPU
  • Continuous profiling alternative to always-on APM — no vendor config lesson here

8. Production Discipline

  1. Reproduce under load — staging with prod-like traffic; thread dump alone on idle JVM misleads
  2. One change at a time — flag, code fix, pool size — measure before/after
  3. Keep GC logs — enabled from deploy (S05)
  4. Capture before restart — restart destroys evidence; dump/thread print first
  5. Time-correlate — APM p99 spike timestamp = GC log line = thread dump

11. Reasoning Exercises

  1. All 50 pool threads BLOCKED on same monitor. Queue size 10k. First tool?

    Answer

    Thread dump — identify lock holder thread and stack. Fix lock scope or deadlock — not heap dump.

  2. Heap 90% after Full GC. Histogram shows 2M char[]. Next?

    Answer

    Heap dump + dominator tree — find what retains char arrays (often giant JSON strings or caches).

  3. RSS 3 GB, -Xmx1g, heap dump 1 GB. Gap?

    Answer

    Off-heap: Metaspace, thread stacks, direct buffers, Code Cache. Check VM.native_memory and direct buffer OOM history.

  4. CPU 95%, GC logs quiet. Young GC normal. Tool?

    Answer

    CPU profiler / JFR CPU samples — hot method loop, not GC tuning.

12. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: First tool for suspected deadlock?

    1. Thread dump via jstack or jcmd.
    2. Full heap dump with jmap only.
    3. Disable garbage collection flags.
    4. Restart pod before any capture.
    View Answer & Explanation

    Answer: A (Thread dump via jstack or jcmd.)

    Thread dump shows BLOCKED threads, locks waited on, and holders. Heap dump doesn't show lock graph clearly.

  2. Q2: Dominator tree in MAT primarily shows?

    1. Objects retaining most heap memory.
    2. JIT compilation tier per method.
    3. Metaspace classloader hierarchy only.
    4. Thread stack depth histogram.
    View Answer & Explanation

    Answer: A (Objects retaining most heap memory.)

    Dominator analysis finds retention paths — top dominators are leak suspects.

  3. Q3: jstat -gc best for?

    1. Live GC pool and pause stats.
    2. Bytecode verify per class file.
    3. Decompiling hot methods only.
    4. Editing Spring bean definitions.
    View Answer & Explanation

    Answer: A (Live GC pool and pause stats.)

    jstat samples GC counters over time — lightweight compared to full dump.

  4. Q4: Direct buffer OOM fixed by raising Xmx?

    1. No — separate off-heap pool.
    2. Yes — Xmx covers all memory.
    3. Yes — if UseZGC enabled only.
    4. No — only StackOverflow applies.
    View Answer & Explanation

    Answer: A (No — separate off-heap pool.)

    Direct memory is outside heap. Fix release/pooling or MaxDirectMemorySize.

  5. Q5: CPU flame graph wide bar means?

    1. High proportion of CPU samples.
    2. Thread is in WAITING state.
    3. Object escaped to heap always.
    4. Class failed verification step.
    View Answer & Explanation

    Answer: A (High proportion of CPU samples.)

    Width = time in that stack frame and children — hot CPU path.

  6. Q6: Production incident best discipline?

    1. Capture dumps then one fix at time.
    2. Change ten flags and redeploy.
    3. Skip logs and restart first always.
    4. Profile only on developer laptop.
    View Answer & Explanation

    Answer: A (Capture dumps then one fix at time.)

    Preserve evidence; reproduce under load; single variable changes with GC logs retained.
