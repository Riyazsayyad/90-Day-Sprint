JIT Compilation & Runtime Optimizations

~35 minutes · ties to mission · builds on final & JIT hints, Escape Analysis, Stream JIT fusion, TLAB

Senior Interview Focus: Can you explain why the first 10k requests after deploy are slower than hour-two traffic? Can you describe tiered compilation, what OSR is, and why polymorphic call sites cause deoptimization? Know escape analysis at interview depth — not C2 IR graphs.

Primary sources: Oracle — JVM Compilers · OpenJDK — Tiered Compilation · JMH — Java Microbenchmark Harness

1. Interpreter → C1 → C2 — Why Warmup Matters

Bytecode starts in the interpreter — correct, flexible, slow. HotSpot profiles execution and compiles hot code to native machine code via JIT compilers:

Tier Compiler Trade-off
Interpreter None Startup fast; steady-state slow
C1 ("client") Quick compile, light optimizations Fast compile time; decent speed
C2 ("server") Slow compile, aggressive optimizations Best peak throughput/latency after warmup

Tiered compilation (default on server JVM): method starts interpreted → C1 compiles quickly → if still hot, promoted to C2 with deeper analysis. You pay compile CPU upfront for faster hot loops later.

Prod reality: cold JVM after deploy = interpreter + first C1/C2 compiles. p99 drops after warmup. Serverless scale-from-zero amplifies this.

2. Hot Methods, Thresholds & OSR

  • Hot method: invocation counter crosses threshold → scheduled for compilation.
  • Compilation threshold: ergonomics flags like -XX:CompileThreshold / tiered thresholds — JVM adapts; don't memorize numbers, know concept.
  • OSR (On-Stack Replacement): long-running loop still in interpreter mid-method → JVM compiles loop body and replaces active stack frame without waiting for method exit. Critical for hot loops inside rarely-called methods.
Normal compile: method exits interpreter → C2 native code next entry

OSR:              long loop running in interpreter → compile loop → swap frame in-place

3. Key Optimizations (Interview Level)

3.1 Inlining

Replace callee with callee body at call site — eliminates call overhead, enables further opts. HotSpot inlines small hot methods aggressively. You saw the effect in Stream Internals: fused pipeline can become one tight loop.

3.2 Devirtualization

Virtual call animal.speak() normally uses vtable dispatch. If profiler sees one implementation (monomorphic) or stable dominant type, JIT may inline direct call — huge win.

Tie final methods/classes: final methods cannot be overridden → compiler/JIT knows target at compile time for those callsites.

3.3 Dead code elimination & constant folding

Unreachable branches removed. static final compile-time constants inlined at use site.

3.4 Loop unrolling

Duplicate loop body iterations to reduce branch overhead — classic C2 transform on counted loops.

3.5 Lock elision (preview)

If JIT proves lock never contends (escape analysis + biased locking history), synchronized block may be stripped in compiled code. Not a license to skip synchronization — proof can fail → deopt.

4. Deoptimization — When Speculation Fails

JIT optimizes based on observed runtime behavior. Assumptions baked into compiled code:

  • Call site always hits Dog — then Cat appears → deoptimization
  • Field never changed — then reflection or another thread mutates → deopt
  • Lock elision invalid — contention appears → revert to locking

Deoptimization: discard optimized native code, return affected threads to interpreter (or recompile with new profile). Causes latency spike — "perf cliff" when workload changes.

Pattern JIT assumption Failure trigger
Monomorphic callsite Single receiver type 2+ types at same callsite (megamorphic)
Inlined virtual method Stable target New subclass loaded / different receiver
Scalar-replaced object Object doesn't escape Reference stored to heap / returned

5. Escape Analysis & Scalar Replacement

From Stack vs Heap: not all objects need heap allocation.

Escape analysis: JIT analyzes if object reference leaves method/thread scope:

  • No escape — object only used locally, not returned, not stored in field, not passed to unknown code
  • Scalar replacement — object fields become local variables (registers/stack slots); new Point(x,y) may never hit heap/TLAB at all
  • Stack allocation (term often used) — fields live in frame, not as heap object shell
int sumOfPairs(List<Pair> data) {
    int total = 0;
    for (Pair p : data) {
        Point local = new Point(p.x, p.y);  // may not allocate on heap if JIT proves no escape
        total += local.x + local.y;
    }
    return total;
}

Limits: large objects, escaping refs, debug flags off, unpredictable aliasing — allocation may still happen. Don't write "micro-benchmark clever" code expecting escape; measure.

6. JIT Logs — Awareness Only

Unified logging can surface compilation events (exact tags vary by JDK):

-Xlog:jit+compilation=info

Legacy (older material still in interviews):

-XX:+PrintCompilation

You'll see method signatures, compile level (e.g. 3 = C2), and OSR markers. Full flag cookbook not goal — know logs exist for "is this method compiled yet?"

7. Enterprise — Cold Start & Benchmarking

7.1 Cold start (K8s / serverless)

  • New pod: class loading + interpreter + JIT compile storm + Spring context init
  • First N requests pay warmup tax — autoscaling policies must account for this
  • Mitigations: readiness probes that warm critical paths, AOT/native image (GraalVM — mention only), keeping min replicas > 0

7.2 Benchmark after warmup — JMH nod

Never trust a single main() loop timing:

  • JMH — warms up JIT, forks JVMs, avoids dead-code elimination traps
  • Measure after warmup iterations; report percentiles
  • Microbenchmark ≠ production — allocation rate, GC, and concurrency differ

7.3 What seniors watch

  • Latency drop after deploy plateau (warmup curve)
  • Deoptimization spikes when traffic pattern changes (new code path, new types)
  • Code Cache fill — too many compiled methods → sweeps/recompiles (S01)

GraalVM / Native Image: ahead-of-time compile trades peak JIT optimality for instant startup — different trade-off space; not default HotSpot path.

Out of scope: C2 IR graphs, assembly reading, Module 07 perf engineering depth, GraalVM as primary lesson.

8. Revision Notes

  • Interpreter → C1 → C2 tiered; warmup required for peak perf.
  • OSR compiles hot loops inside long methods.
  • Inlining + devirtualization = big wins on monomorphic calls.
  • Deopt when profile assumptions break (polymorphism).
  • Escape analysis → scalar replacement may skip heap alloc.
  • Cold start hurts serverless/K8s scale-from-zero.
  • Benchmark with JMH after warmup — not naive loops.

9. Reasoning Exercises

  1. Deploy new version. p99 200 ms first 5 min, then 40 ms steady. GC normal. Explain?

    Answer

    JIT warmup — hot paths moving interpreter → C1 → C2. Also possible class data cache warming. Not necessarily a bug.

  2. Interface method with 5 implementations called randomly at one callsite. Inlining?

    Answer

    Megamorphic — JIT unlikely to inline all targets. Virtual dispatch remains. Deopt if earlier monomorphic assumption breaks.

  3. final class method called from known type. Devirtualization easier?

    Answer

    Yes. No subclasses → stable target. JIT can inline aggressively (oop-0015).

  4. Lambda in hot stream pipeline never escapes intermediate objects. Heap allocation?

    Answer

    JIT may fuse + escape-analyze — fewer heap objects than naive reading (streams-0006). Not guaranteed; measure under load.

10. 6 Senior-Level MCQs

Option lengths matched to prevent visual hints.

  1. Q1: Why first requests after deploy slower?

    1. Interpreter plus JIT not warmed.
    2. GC disabled until ten minutes.
    3. Heap fixed at one megabyte.
    4. Metaspace cleared every request.
    View Answer & Explanation

    Answer: A (Interpreter plus JIT not warmed.)

    Bytecode runs interpreted until hot methods compile to native code. Tiered compilation takes time.

  2. Q2: OSR primarily helps which case?

    1. Hot loop inside rare method.
    2. Static clinit running once.
    3. Class loading verify phase.
    4. Metaspace cap exceeded event.
    View Answer & Explanation

    Answer: A (Hot loop inside rare method.)

    On-Stack Replacement compiles and swaps an active long-running loop without waiting for method return.

  3. Q3: Deoptimization triggered when?

    1. JIT assumption no longer holds.
    2. Any Young GC cycle runs.
    3. Thread enters WAITING state.
    4. Compressed oops turned off.
    View Answer & Explanation

    Answer: A (JIT assumption no longer holds.)

    e.g. monomorphic callsite becomes megamorphic. Optimized code discarded; interpreter or recompile.

  4. Q4: Escape analysis enables what?

    1. Scalar replace non-escaping object.
    2. Move static fields to stack.
    3. Skip class loading entirely.
    4. Disable garbage collection.
    View Answer & Explanation

    Answer: A (Scalar replace non-escaping object.)

    If object doesn't escape scope, fields may live in registers/locals without heap allocation.

  5. Q5: C2 vs C1 trade-off?

    1. C2 slower compile deeper opts.
    2. C1 never compiles any code.
    3. C2 only runs in interpreter.
    4. C1 replaces garbage collector.
    View Answer & Explanation

    Answer: A (C2 slower compile deeper opts.)

    C1 compiles fast with lighter optimizations. C2 spends more compile time for aggressive peak performance.

  6. Q6: Reliable microbenchmark practice?

    1. JMH with warmup iterations.
    2. Single main timing loop only.
    3. Measure before any classes load.
    4. Disable tiered compilation always.
    View Answer & Explanation

    Answer: A (JMH with warmup iterations.)

    JMH accounts for JIT warmup and JVM pitfalls. Naive loops mislead.
