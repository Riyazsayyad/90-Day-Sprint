ApplicationContext, Bean Scopes & Bean Lifecycle

~35 minutes · Module 05 Lesson 2 of 9 · builds on Why Spring, Object lifecycle

Senior Interview Focus: Can you walk a bean from BeanDefinition to ready singleton without stuttering? Singleton vs Java enum singleton? Why injecting a prototype into a singleton does not give a new instance per method? Why constructor cycles fail in modern Spring? This is the container — not annotations yet.

Primary sources: BeanFactory vs ApplicationContext · Bean Scopes · Lifecycle Callbacks

1. What ApplicationContext Is

Must know: ApplicationContext is the IoC container you actually use. It holds bean definitions, creates beans, injects them, publishes events, and (in web apps) is the parent of request-scoped contexts.

Typical Boot: one root AnnotationConfigServletWebServerApplicationContext (name varies) per JVM process. Beans are heap objects rooted by that context — GC will not collect singletons until the context closes (GC roots).

2. BeanFactory vs ApplicationContext

BeanFactory ApplicationContext
Role Core DI: getBean, definitions BeanFactory + enterprise services
Messages No i18n MessageSource
Events No ApplicationEventPublisher
AOP Manual Integrated post-processors / auto-proxy
Eager singletons Typically lazy until getBean Pre-instantiates singletons at refresh (default)

You never new a raw DefaultListableBeanFactory in Boot. Context is-a BeanFactory.

3. Container Pipeline

Configuration (@Configuration, scan, auto-config)
        │
        ▼
BeanDefinition registry   (name, class, scope, deps)
        │
        ▼
Instantiate               (constructor / factory method)
        │
        ▼
Populate / DI             (fields, setters — after ctor)
        │
        ▼
Initialization            (BPP, @PostConstruct, InitializingBean)
        │
        ▼
Ready bean in singleton cache
        │
        ▼
Destruction on context close  (@PreDestroy, DisposableBean)

Mental model: Definitions first (metadata). Instances second. Refresh() runs this pipeline. Failures here are startup failures — better than 3 a.m. NPEs.

4–7. Lifecycle Step-by-Step

  new Target()                    // 1 constructor — only ctor-injected deps exist
       │
       ▼
  inject remaining                // 2 setter/field DI
       │
       ▼
  BeanPostProcessor.before        // 3 framework wrappers start (proxy often later)
       │
       ▼
  @PostConstruct / afterPropertiesSet / custom init-method
       │
       ▼
  BeanPostProcessor.after         // 4 often where AOP proxy replaces bean (S06)
       │
       ▼
  bean in use
       │
  context.close()
       │
       ▼
  @PreDestroy / destroy() / DisposableBean

@Component
public class CacheWarmer {
  private final CatalogRepo repo;

  public CacheWarmer(CatalogRepo repo) {
    this.repo = repo;
    log.info("1 ctor — repo injected, not ready to serve HTTP yet");
  }

  @PostConstruct
  void warm() {
    log.info("2 @PostConstruct — safe: all deps set, proxy may wrap after");
    repo.preload();
  }

  @PreDestroy
  void stop() {
    log.info("3 @PreDestroy — context closing, drain work");
  }
}

jakarta.annotation.PostConstruct / PreDestroy (Jakarta EE, Boot 3). Not a substitute for constructors: ctor still runs first.

Trap: calling other beans’ business methods from a constructor — they may not be initialized; you can see NPEs or half-proxies. Warm in @PostConstruct or ApplicationReadyEvent.

Nice to know: InitializingBean.afterPropertiesSet is the Spring interface equivalent of @PostConstruct. Prefer the annotation for app code.

8. Scopes

Scope How many instances When
singleton (default) One per context Services, repos, DataSource — 99% of beans
prototype New every getBean / injection at injection time Stateful helpers — rare; prefer immutable + args
request One per HTTP request Web only — request attributes
session One per HTTP session Web — avoid fat session state
application One per ServletContext Web — similar to singleton in one war
websocket One per WebSocket session Messaging apps

Web scopes need a web-aware context. Using request in a CLI Boot app fails at injection.

9. Singleton Mental Model

ApplicationContext
   singleton cache:  UserService@7a3  ←── Controller.service
                                      ←── OtherBean.userService
                         SAME reference (identity ==)

Many injection points, one instance. That instance must be thread-safe for shared mutable state — you studied this in threads and monitors. Stateless services are the easy path.

10. Spring Singleton ≠ Enum Singleton

Joshua Bloch enum singleton = one JVM-wide instance of that enum type. Spring singleton = one instance per ApplicationContext. Tests with two contexts → two UserService objects. Parent/child contexts → possibly two. Not enum INSTANCE.

11. Prototype Destruction

Container calls destroy callbacks on singletons it cached. Prototypes: after handing you the instance, Spring typically does not track them for @PreDestroy. You own disposal (or use a custom scope / DestructionAwareBeanPostProcessor — nice to know).

12. Singleton Injecting Prototype

@Controller (singleton)
    │ injects once at startup
    ▼
PrototypeBean instance_A   // frozen for the life of the controller

Must know: Injection happens once for the singleton. Every method call uses instance_A, not a fresh prototype. To get a new prototype per call: scoped proxy (@Scope(proxyMode = TARGET_CLASS)) or ObjectProvider (next).

13. ObjectProvider / Provider

@Service
public class JobRunner {
  private final ObjectProvider<PrototypeWorker> workers;

  public JobRunner(ObjectProvider<PrototypeWorker> workers) {
    this.workers = workers;
  }

  public void run() {
    PrototypeWorker w = workers.getObject(); // new prototype
    w.execute();
  }
}

jakarta.inject.Provider is the same idea. Prefer this over storing ApplicationContext and calling getBean (service locator smell).

14. @Lazy

Defers singleton creation until first use. Use for expensive beans or to break some cycles. Cost: first request pays init; failures move from startup to traffic. Prefer fixing the cycle.

15. Circular Dependencies

A ctor needs B, B ctor needs A  →  BeanCurrentlyInCreationException (typical)

Spring 6 / Boot 3: constructor cycles fail fast. Setter/field injection historically allowed a half-created singleton into the other bean (early reference). That hid design bugs. Interview framing: cycles mean muddled responsibilities — extract C that both depend on, or events, not “enable circular references.”

spring.main.allow-circular-references=true exists as an escape hatch. Treat as debt.

16. Ordering

  • @DependsOn("flyway") — this bean after that bean’s init.
  • Ordered / @Order — among list of same type (filters, listeners). Not a general “create A before B” for arbitrary beans — use @DependsOn or natural constructor deps.

Production Debugging

  • Startup hang in @PostConstruct that calls remote HTTP — blocks refresh; pod never Ready.
  • Prototype leak: creating prototypes in a loop without discard → heap growth (S08 + JVM dumps).
  • Request-scoped bean injected into singleton without proxy → exception or wrong instance.

Interview Articulation

“ApplicationContext is the IoC container: it registers BeanDefinitions, instantiates, injects, runs init callbacks, then caches singletons. Default scope is singleton — one instance per context, not a JVM enum singleton. A prototype injected into a singleton is resolved once unless I use ObjectProvider or a scoped proxy. Constructor circular dependencies fail at startup; that’s a design smell, not a flag to flip.”

Revision Notes

  • Context = BeanFactory + events + i18n + eager singletons + AOP integration.
  • Pipeline: definition → new → inject → init → cache → destroy.
  • Singleton: one per context; thread-safety is your problem.
  • Prototype: new at lookup; destroy not managed like singleton.
  • ObjectProvider for fresh prototype; ctor cycles fail.

Interview One-Liners

  • “Startup is refresh(); traffic is getBean from an already-warm cache.”
  • “Same singleton reference everywhere is a feature — mutable fields are the bug.”
  • “@PostConstruct is after injection, not after the HTTP server is up — use ApplicationReadyEvent for that.”
