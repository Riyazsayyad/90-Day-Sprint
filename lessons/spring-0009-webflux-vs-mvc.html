WebFlux: Reactive Model vs Servlet MVC

~35 minutes · Module 05 Lesson 9 of 9 · architecture choice, not a Reactor course · builds on S07, virtual threads

Senior Interview Focus: WebFlux is not “faster Spring.” It is an event-loop + non-blocking I/O model. Blocking JDBC on the event loop is an outage. Virtual threads give a second scalability story on the servlet stack. Can you pick MVC+VT vs WebFlux with a decision tree, not a buzzword?

Primary sources: Spring WebFlux · Reactive Spring · Boot Reactive Web

1. Why WebFlux Exists

Servlet MVC (S07): one thread per in-flight blocking request. High concurrency of slow I/O → huge thread counts, stack memory, context switches. WebFlux: small set of event-loop threads, I/O completion callbacks, many concurrent requests without 1:1 platform threads.

Born for gateways, streaming, high fan-out HTTP — if the whole stack is non-blocking.

2. MVC Path

request → Tomcat worker
              │  blocking JDBC / RestTemplate
              ▼
          thread waits  (stack allocated the whole time)
              │
          response

3. WebFlux Path

request → Netty event loop (N threads, N ≈ cores)
              │  register I/O, do not block
              ▼
          event-loop free for other connections
              │  completion → resume Mono/Flux
              ▼
          write response  (still on loop or scheduled worker)

4. Event Loops — Blocking Is Fatal

Must know: If you call JDBC ResultSet on the event-loop thread, that loop cannot process other connections. One slow query stalls a slice of the server. This is worse than occupying one Tomcat worker — you poison a shared loop.

publishOn / bounded elastic schedulers exist to offload blocking — you then have a thread pool again. At that point ask why you aren’t on MVC+VT.

5–7. Mono, Flux, Lazy, Backpressure (Roles Only)

  • Mono — 0..1 value (one JSON body, one user).
  • Flux — 0..N stream (SSE, chunked rows).
  • Lazy: assembling a pipeline does nothing until subscribe (HTTP response subscription).
  • Backpressure: consumer signals demand so a fast publisher doesn’t OOM the heap. Conceptual — not every operator.
@GetMapping("/users/{id}")
Mono<User> get(@PathVariable String id) {
  return userRepo.findById(id); // reactive repo — not JPA blocking
}

8. MVC vs WebFlux Table

Servlet MVC WebFlux
Threading Worker per request (or VT) Event loops + workers
I/O Blocking OK Non-blocking required on loop
Programming Imperative, simple stacks Declarative pipelines, harder dumps
Debug Thread dump maps to request Async stacks; need reactor debug / traces
Data access JDBC/JPA natural R2DBC / reactive drivers end-to-end
Tx @Transactional thread-bound (S06) Different story — don’t paste servlet tx on loop
Fit CRUD services, mixed blocking libs Gateway, streams, reactive DB

9. Misconception: “WebFlux Is Always Faster”

CPU-bound JSON + business rules: same cores, extra pipeline overhead. Blocking JDBC on WebFlux: slower and less stable than MVC. Benchmark your shape of work.

10. Blocking JDBC on WebFlux

JPA/JDBC calls socketRead on whatever thread you ran them. On the event loop = stall. On boundedElastic = hidden Tomcat. Mixing Hibernate Session (thread-bound) with reactive chains is a bug factory. Module 06 will deepen ORM; here: don’t.

11–13. Virtual Threads vs WebFlux

Two strategies for “lots of waiting I/O”:

  1. MVC + virtual threads — keep imperative style, JDBC, @Transactional; VT unmounts while blocking (pinning caveats, concurrency-0008).
  2. WebFlux — keep event loops; every I/O library must be reactive.

MVC+VT is simpler for most business services in 2026. WebFlux wins when: streaming, backpressure, reactive clients all the way, gateway routing.

14. Decision Tree

Need end-to-end non-blocking + streaming / gateway?
    YES → WebFlux (and reactive data access)
    NO  → Servlet MVC
            │
            Lots of concurrent blocking I/O, Java 21+?
            YES → consider spring.threads.virtual.enabled
            CPU-bound / simple CRUD / JPA?
            YES → MVC platform threads are fine; measure first

Cannot mix starter-web and starter-webflux as two competing servers without a clear choice — Boot picks one web application type. Wrong OnWebApplication conditions (S05) then surprise you.

Production Relevance

Teams copy a WebFlux template, keep JPA, page the CEO. Thread dumps show event-loop threads in socketRead0. Fix: move to MVC or extract blocking to a dedicated pool (and accept you lost the model).

Interview Articulation

“MVC occupies a worker for blocking I/O. WebFlux uses event loops and requires non-blocking I/O; blocking JDBC on the loop is an outage. WebFlux is not automatically faster. For JPA CRUD I pick MVC, and virtual threads if concurrency of blocking calls is the bottleneck. I pick WebFlux when the pipeline is reactive end-to-end.”

Revision Notes

  • Event loop ≠ worker pool.
  • Non-blocking all the way or don’t pretend.
  • VT: imperative blocking; WebFlux: reactive I/O.
  • JPA + WebFlux is a smell.

Interview One-Liners

  • “WebFlux multiplies concurrency only if I/O doesn’t block the loop.”
  • “Virtual threads scale blocking code; WebFlux scales callbacks.”
  • “Faster is a benchmark, not a stack name.”

  6. Q6: Assembling a Flux without subscribe?
