volatile & JMM Cheat Sheet

happens-before, visibility, DCL, publication

1. Core Idea

  • No happens-before → stale reads & reorderings allowed
  • JMM = contract, not "what my laptop did once"
  • CPU caches + compiler reordering are why plain fields fail

2. happens-before (Interview Set)

  • Program order within thread
  • Unlock → subsequent lock (same monitor)
  • volatile write → subsequent volatile read (same var)
  • start() → actions in new thread
  • Actions in thread → join() returns
  • Transitive chaining

3. volatile

  • Visibility + ordering for that field's read/write
  • Read sees latest write + prior writer actions (via hb)
  • NOT compound atomicity — count++ still broken
  • long/double need volatile (or sync) for atomicity

4. volatile vs synchronized

Need Pick
Status flag visibility volatile boolean
Multi-step invariant synchronized
Atomic counter AtomicInteger / LongAdder

5. Safe Publication

  • Static initializer (class init lock)
  • Store ref in volatile field
  • Store ref inside synchronized, then unlock
  • Pass to thread via start()
  • final fields safe if ref published safely

6. Double-Checked Locking

  • Broken without volatile on holder — partial construction visible
  • Correct: private static volatile Instance instance
  • Production: holder-class idiom or enum singleton

7. Enterprise Patterns

  • Shutdown flag → volatile boolean
  • Config reload → volatile ref to immutable snapshot
  • Metrics under contention → atomics, not volatile++
