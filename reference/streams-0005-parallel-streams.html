Parallel Streams Cheat Sheet

ForkJoinPool, ordering, safety, performance traps

1. Enable / Disable

API Effect
parallelStream() Parallel from source
stream().parallel() Switch to parallel mid-pipeline
sequential() Switch back to single-threaded
unordered() Drop ORDERED — faster parallel merges

2. Execution

  • Pool: ForkJoinPool.commonPool() (shared JVM-wide)
  • Parallelism: availableProcessors() - 1 (commonPool default)
  • Split: Spliterator.trySplit()
  • Schedule: work-stealing deques
  • Custom pool: pool.submit(() -> list.parallelStream()...).get()

3. Ordering Ops

Op Parallel behavior
forEach Unordered
forEachOrdered Encounter order — costly
findAny Any match — fast short-circuit
findFirst First in encounter order — may wait

4. Thread Safety Rules

  • Intermediate ops: stateless, no shared mutation
  • Never forEach into shared ArrayList / HashMap
  • Parallel collect: use CONCURRENT collectors when possible
  • reduce combiner must be associative

5. When Parallel Wins / Loses

Wins Loses
CPU-bound, large N
ArrayList / arrays
Primitive streams
Unordered collect 		Small N
LinkedList
I/O in lambda
Ordered terminals
Boxing overhead

6. Enterprise Red Flags

  • HTTP/DB inside parallelStream().map(...)
  • commonPool starvation under Spring load
  • Intermittent races on shared state
  • Assuming parallel without benchmark

7. Interview One-Liners

  • Parallel streams ≠ general concurrency — data parallelism only
  • No API to pick pool — submit trick only
  • Default sequential; parallel needs evidence
  • groupingByConcurrent for parallel map collect — see Collectors ref
