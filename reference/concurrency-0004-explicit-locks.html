Explicit Locks Cheat Sheet

Lock, RW, StampedLock, Condition, liveness

1. Core Idea

  • synchronized default — auto unlock, one wait-set
  • Explicit lock = tryLock / timed / interruptible / fair / many Conditions
  • You must unlock() in finally

2. Lock Contract

  • lock / unlock / lockInterruptibly / tryLock / timed tryLock
  • Successful unlock happens-before next successful lock (same as monitor)
  • Failed tryLock → no memory edge; do not unlock
  • Never synchronized on the Lock instance

3. ReentrantLock

  • Reentrant hold count; isHeldByCurrentThread(), getHoldCount()
  • new ReentrantLock() non-fair (throughput); (true) fair (less starvation, slower)
  • Untimed tryLock() barges even on fair locks

4. ReadWriteLock

  • Many readers or one writer
  • Write unlock happens-before later read lock
  • Downgrade write→read OK; upgrade read→write deadlocks
  • Hurts: write-heavy, tiny reads, frequent upgrades

5. StampedLock

  • Optimistic read: copy locals, then validate(stamp)
  • Not reentrant; no ownership
  • Skip validate = torn data
  • Prefer for short hot reads, rare writes — not a general mutex

6. Condition vs wait/notify

  • await / signal / signalAll
  • Must hold lock; loop on predicate
  • Two Conditions: bounded buffer notFull + notEmpty

7. Liveness

  • Global lock order; avoid nested inversion
  • tryLock both + release held + backoff (Safelock)
  • Fair lock ≠ scheduler fairness

8. Enterprise Picks

  • Read-heavy cache → RW lock or volatile immutable snapshot
  • Skip-if-busy metrics → tryLock()
  • Spring singleton rare mutate → private lock object, not this
