Synchronization & Monitors Cheat Sheet

Locks, wait/notify, races, traps

1. Why Sync

  • Data race: concurrent access + write + no sync
  • Lost update: count++ is read-modify-write
  • Check-then-act: compound actions need one lock

2. Monitor Model

  • Every object → one intrinsic lock + one wait set
  • Owner: one thread holds lock at a time
  • Entry queue: blocked on synchronized → BLOCKED
  • Wait set: wait() → WAITING
  • Mark Word: biased → thin → fat under contention

3. synchronized — Which Lock?

Form Lock object
Instance method this
Static method ClassName.class
Block Expression you specify

4. Reentrancy

  • Same thread may acquire same monitor multiple times
  • Each acquire matched by release on unwind

5. wait / notify / notifyAll

  • Must hold object's monitor — else IllegalMonitorStateException
  • wait() — release lock, enter wait set
  • notify() — wake one waiter (arbitrary)
  • notifyAll() — wake all; prefer default
  • Always: while (!condition) { wait(); }
  • sleep does not release monitors

6. Atomicity vs Visibility

  • synchronized → both (for guarded region)
  • volatile → visibility + ordering, not compound atomicity (S03)

7. Classic Traps

  • Wrong lock object — no mutual exclusion
  • synchronized ("literal") — shared interned monitor
  • Lock held during I/O — convoy / throughput collapse
  • notify without holding lock

8. When to Upgrade

  • Simple short guards → synchronized OK
  • Try/timed/fair locks, pools, concurrent maps → java.util.concurrent
